## `ParagraphProcessor` 新增"y 坐标大幅重叠的 TextBlock 合并"逻辑（原始记录）

背景：用户要求把同一行（y 范围重叠度大）但被拆成两个 TextBlock 的片段合并，例如 `202403201784967210628061686-6.pdf` 的 `「《中 央 結 算 系 統`(id7)↔`規範中央結算系統…`(id6)、`一 般 規 則》」`(id9)↔`改），在文義允許…`(id8)。根因是它们是定义列表里术语(左栏)/释义(右栏)两个独立 text run，中间是空栏，veraPDF 不合并。
实现（`ParagraphProcessor.java`）：
- 新增常量 `MIN_Y_OVERLAP_MERGE_RATIO = 0.7`（重叠长度 / 较小块高度）。
- 新增 `mergeVerticallyOverlappingBlocks(List<TextBlock>)`：用并查集把 y 重叠≥阈值的块 transitive 合并；合并块收集所有 lines，按 (topY 降序, leftX 升序) 排序后 `new TextBlock(lines[0])` 再 `add` 其余；因 `TextInfoChunk.add` 会 `unionBoundingBox`，合并块 bbox 正确覆盖全部行；firstLine 取左上角行→index 仍能在 `getContentsWithDetectedParagraphs` 正确映射。
- 在 `processParagraphs` 两个重载末尾（`processOtherLines` 之后、`getContentsWithDetectedParagraphs` 之前）各调用一次。
验证：`mvn -o -q compile` 与 `ParagraphProcessorTest` 均 exit 0。注意这是行为变更，可能影响所有"同行多栏"页面（如真实双栏正文），回归面需关注；阈值可调。

## `202403201784967210628061686-6.pdf` 两对文本未合并到同一 TextBlock —— 根因（解释性，未改代码）

用户问：① `「《中 央 結 算 系 統`(id7) 与 `規範中央結算系統使用的條款和條件（經不時修訂或修`(id6)；② `一 般 規 則》」`(id9) 与 `改），在文義允許的情況下…`(id8) 为什么 y 范围基本一样却不在同一 TextBlock。

结论（取自 `tmp_output/202403201784967210628061686-6.json` page1）：
- 两对 y **完全相同**（id7&id6: 279.290–293.118；id9&id8: 296.289–310.118），但**横向 gap 极大**：id7↔id6 = 44.35pt、id9↔id8 = 53.28pt（font_size=10.5，正常间距~2-3pt）→ 是**双栏/悬挂缩进版面**（左窄列术语《中央結算系統一般規則》+ 右宽列定义，右栏三行 x0 恒=212.598）。
- 这是"左术语/右释义"两个独立文本流，只是同高对齐，非同行连续文本。
- 代码层面：veraPDF chunk→line/column 检测把 44–53pt gap 当栏分隔 → 进 `ParagraphProcessor` 已是两独立 TextBlock（`ParagraphProcessor.java:65`）；`ParagraphProcessor` 只合并**上下相邻**连续行（`:155-159` JUSTIFY 合并、`prejudgeParagraphs :378-381` 横向 >20pt 断行），**无跨栏合并**；且块列表交错（右1/左1/右2/左2）使左栏两行永不相邻。
- 判定：预期行为，非 bug。若要合并需新增"跨栏合并"逻辑（按 y 配对左右栏），属增强改动，已向用户说明待其确认是否做。

### 根因（两条）

1. **PDF 内容流层**：单一 `/Contents` 流（无 Tr 渲染模式、无 BDC/BMC 图层），同一串字被以
   `-0.240148 -0.24 Td` / `0.240148 0 Td` / `-0.240148 0.24 Td` 的微位移**重复绘制 2~4 次**（伪粗体/重复打印），
   四个角为 (186.96|187.2)×(761.36|761.6)。统计：`-0.240148 -0.24 Td`×26、`0.240148 0 Td`×4、
   `-0.240148 0.24 Td`×4、`0 0.24 Td`×31。字体全是 `R9=LVVDUR+TT491A9C96tCID`，字号/字重(400)/颜色全同
   → **无法用"层级/渲染模式"区分，只能按坐标+内容去重**。
2. **ChunkParser 层**：各副本被**切分边界不同**（有的多吞前导空格/冒号、有的把同一字切成两半、还产生
   0.24pt 宽的"零宽幽灵字"），于是 `ContentFilterProcessor.getFilteredContents:56` 的
   `TextProcessor.removeSameTextChunks`（要求 `Objects.equals(value)` + bbox 交叠>0.5）只吃掉了值完全相等的整块副本，
   其余全留下。关键前提：`ChunkParser` 会填 **真实逐字形坐标 `symbolEnds`**（幽灵冒号宽 0.248 vs 真冒号 2.598），
   这是可实施修复的基础。

### 候选方案 A（推荐，待确认）

新增 `TextProcessor.removeOverprintedTextChunks(List<IObject>)`，在 `ContentFilterProcessor.getFilteredContents`
第 55~56 行之间、`removeSameTextChunks` 之前调用（hybrid 路径 `HybridDocumentProcessor:515` 同覆盖；tagged 路径不走此处）。
算法：展开 `symbolEnds` 为字形 → 按行聚类（baseline 差 ≤ max(0.5pt,0.05×字号) 且同字号同字体）→
**安全门**：仅当行内存在"退化字形"（宽 ≤ max(0.4pt,0.05×字号) 且同行同字有更宽者）或"同字 x0 差 ≤0.3~0.5pt"时才处理 →
(1) 去退化幽灵字形；(2) 按宽度从大到小贪心，x 区间被"同行同字已保留区间之并"覆盖 ≥0.7 则丢弃；
(3) 用 `TextChunk.getTextChunk(chunk,s,e)` 语义重建（同步 value/symbolEnds/textStart/textEnd 并收缩 bbox，全丢则置 null）。
阈值：覆盖比 0.7 / 退化宽 max(0.4pt,0.05×字号) / 行判定 max(0.5pt,0.05×字号)。
