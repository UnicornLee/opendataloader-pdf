### 结论（根因）
**不是"消费暂停"，而是订阅里 21~28 个消费槽位被同一条消息的多个副本占满。**
1. 卡住的消息：businessId=`1785145532722080227_1344599359112327168`，文件 `202504281785145532722080227.pdf`（HK 超大/扫描件，含 stream table 的页至少到 285，故 ≥300 页）。
   它在 `DocumentProcessor` 的**单线程逐页后处理循环**（`DocumentProcessor.java:685-724`：图表/流程图截图 → `LineArtProcessor.haveFormulas` → `ConsecutiveImageProcessor`）上极慢：
   实测**某些页 ~11~12 分钟/页**（同一 host+thread 相邻两页日志间隔 12.5/11.7/11.2/13.1 分钟；多个 host 一致），而**空闲页可在同一秒内连跑 8 页**；
   对照第 4 台 `192.168.0.136` 同循环可 1 秒内跑完 52~136 页 → 说明是该文档自身页面内容（扫描大图）导致，不是循环天生慢。
2. `pulsar.ack_timeout_seconds=60`（`application-prod.yml`，`receiverQueueSize=1`、`SubscriptionType.Shared`、`count=7`），远小于该消息的实际耗时
   → broker 不断把它**重投**给别的 consumer。**24h 内该消息被下载 21 次**（21 个不同 `in-<id>` 目录、跨 4 台主机 21 个消费线程），每次从头再算、数小时不返回、永不 ack。
3. 槽位被这条消息的副本占满后，订阅再无空闲 consumer → broker 不再投递 → `pulsar_subscription_msg_rate_out=0`、backlog 冻结 25257。
4. 量化旁证：近 24h 该订阅 `download pdf success` 7962 次，但 backlog 只从 26371 降到 25257（-1114）→ **约 7 倍重复劳动**；
   近 6h 672 次下载 / 650 次处理成功，唯一「下载了但从未完成」的业务 ID 就是这一条（另 `1785140450325050627_...` 在 02:30 因
   `UnsupportedOperationException: JPX color spaces don't support draw...` 失败 1 次，有 `handleReceiveMessage failed` 日志）。
5. **同一现象 09-14 已发生**：backlog 从 12:10 到 23:10 整整 11 小时一动不动（恒为 25775）。
6. 已排除：不是 broker 限流（`blocked_on_unacked=0`）、不是 CPU 死循环（pod CPU 4~5 核/8 核，属正常忙碌）、不是 ERROR/异常（近 3h ERROR=0，
   `haveFormulas failed`/`haveStreamTables failed`/`PaddleOcr` 失败均为 0）、不是 OCR/paddle 不可达（prod 为 `basicFormulaRecognize=false`，本就不发 OCR）。
   `pulsar-ocr-*` 与 OCR topic 全部 backlog=0、rate=0（链路整体空闲，因为主链路已堵死）。
   3 台主机 JVM 在 02:17Z 重启过（`process_start_time_seconds`），重启时 `SpringApplicationShutdownHook` 报 `thread pulsar-receive-N did not stop within timeout`
   → 佐证这些消费线程正卡在长耗时的文档处理里；堆 8G、峰值 99%、Young GC ~2 次/秒（压力大但非 OOM）。

## 实现：消费超时看门狗 + core 侧超时检查点（方案3+方案1，分支 ocr-unification-20260820）

用户确认口径：① 超时后**要**发结果消息 `jsonUrl=""`；② 采纳僵尸上限+告警/自愈；③ OCR 链路同样处理；④ 超时值配在 yml，键名 **`consum_timeout_min`**（40）；⑤ 采纳"超时自动打印 worker 线程栈"。

### 改动清单
core（`opendataloader-pdf-core`，源码级别 11，**不能用 Java16+ 的 `instanceof X x` 模式匹配**）：
- 新增 `org.opendataloader.pdf.utils.ProcessingDeadline`：ThreadLocal 存绝对 deadline（`NEVER=Long.MAX_VALUE`）+
  `start/clear/snapshot/inherit/remainingMillis/expired/check(stage)/check(deadline,stage)`，
  以及给 parallel lambda 用的**非受检**版本 `checkUnchecked(...)`（包成 `UncheckedIOException`）。
  关键坑：`ThreadLocal` 不会传播到 `ForkJoinPool` 工作线程，所以并行 phase 用 `snapshot()` 捕获值 + `check(deadline, stage)` 显式检查。
- 新增 `org.opendataloader.pdf.exceptions.ProcessingTimeoutException extends IOException`。
- `DocumentProcessor.processDocument`：捕获 `final long deadline = snapshot()`，在 Loop1 并行 lambda、OCR fallback 循环、hidden-text 循环、
  Loop2/Loop3/headings 并行 lambda、**685-724 的单线程逐页循环（本次故障的真正卡点，加了带页码/总页数/文件名的日志）**、
  ID 分配循环、跨页后处理前 各加检查点；`catch` 里若 cause 是 `ProcessingTimeoutException` 则**原样抛出**（不再包成 "Parallel page processing failed"）。
- `JsonWriter.rebuildBookmarksFromJson`（OCR 链路）：读 JSON 后 / 解析 related_ids 前 / 写回前 / OBS 上传前 各加检查点；
  `writeToCustomJson` 的逐页循环（"generating outputs" 可占 17 分钟）也加了。

server（`opendataloader-pdf-server`，JDK 17）：
- `PulsarProperties` 新增 `@DefaultValue("0") int consumTimeoutMin`（读取 `pulsar.consum_timeout_min`）。
- `PulsarService`：
  - 新增 `runWithWatchdog(consumer,msg,handler)`：**每个消息跑在独立 worker 线程**（`pulsar-work-<consumerName>`，daemon），
    消费线程 `future.get(consumTimeoutMin)`；worker 内 `ProcessingDeadline.start(同budget)` → 检查点通常会先干净退出。
  - `onMessageTimeout(...)`：`abandoned=true` → **发 `jsonUrl=""` 结果消息** → `acknowledge`（**不重投**）→ `shutdownNow()` → 打 error 日志（含 `ThreadMXBean` 导出的 worker 栈，不再需要人工 jstack）→ 升级判定。
  - 僵尸计数用**存活数**（worker 自然结束时 `decrementAndGet`）而非累计值：软阈值 `count+ocrCount` 报 error，硬阈值 2 倍则 `System.exit(1)` 交给编排重启。
  - `handleReceiveMessage`/`handleOcrReceiveMessage` 改为接收 `AtomicReference businessId/extend` + `AtomicBoolean abandoned`，尽早回填；被放弃后跳过"发结果/ack"避免重复上报。
  - `consum_timeout_min<=0` 时完全走原内联路径（线程数不变）；`validateTimeoutConfiguration()` 在启动时校验 ackTimeout 与看门狗不冲突。
  - 两个消费循环都加了 try/catch 包住看门狗调用（避免异常逃逸打死消费线程）。
- 8 个 `application-*.yml`：`ack_timeout_seconds: 60 → 0`，新增 `consum_timeout_min: 40`（含英文注释）。

### 定位过程中踩的 4 个坑（都很有价值）
1. `findProseBlocks` 的 `gap` 符号写反（应 `box.bottom - other.top`）→ 几乎每个"下方有文本"的块都被判为正文 →
   标签全被排除 → p7 下部图与 p8 标签集体消失。**症状与"改动过严"完全一样，容易误判为策略问题。**
2. 相邻阈值用 `max(两者高度)` 会放大到错误尺度（标题 23pt → 阈值 35pt，31pt 的间隙被当成"相邻行"）→ 改用 `min`。
3. 曾用"页面内容并集"当页面尺寸代理 → 内容少的测试页面 cluster/page ≈ 1 → 全被当成整页而拒绝（4 个单测红）。
   必须用真实 mediabox（`DocumentProcessor` 的 `pageWidths/pageHeights`）。
4. A/B 定位：把 `Config.setPages("2,34,35,52")` 传给 `DebugCorpusTmp` 可把单次实验从 ~150s 降到 ~20s。
   用此法确认 **A1、B2、ShapeRecognizer 都不是大文档 p2 出现整页截图的原因**（真因是"整页框架形状" + 正文块被收集后
   使 cluster 扩张），避免在错误方向上改判据。
