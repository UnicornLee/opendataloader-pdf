## 目录↔正文标题"相似性兜底匹配"（用户指定规则，已实现）

### 触发问题

`docs/pdf/202609031788435163969004864.pdf` 一级目录 `附錄一  －  購回授權之說明函件`（目录页第 2 页）
与正文页眉 `附錄一                  購回授權之說明函件`（第 11~14 页）**没匹配上**，
差异只有目录侧多出的 `－`（U+FF0D）。后者不在 `related_id` 解析范围内，于是 `附錄一` 的
`page_num` 停在印刷页 8、`related_id` 停在目录行自身的 item id。

### 根因

`CatalogBookmarkProcessor.matchBookmarkTitle`（主逻辑约 1878 行）只有两级判据：

```java
if (normalized.equals(normalizedTitle)) return MatchQuality.EXACT;
if (normalized.startsWith(normalizedTitle)) return MatchQuality.PREFIX;
return null;   // MatchQuality.CONTAINS 定义了但从未返回
```

`normalizeBookmarkText` 只删 `\s`，不删中间标点，所以"差一个 `－`"直接落空。

### 实现（用户给的规则）

- 新增 `MatchQuality.FUZZY`（枚举顺序 `EXACT, PREFIX, FUZZY, CONTAINS`；`ordinal()` 越小越优，
  所以相似匹配只在精确/前缀都失败后兜底）。
- `matchBookmarkTitle` 末尾追加 `isFuzzyTitleMatch(...)`。
- 判据：两条串必须有**非空的公共前缀**与**非空的公共后缀**，两侧中间"多出来的字符"之和 ≤
  `MAX_FUZZY_TITLE_GAP = 2`；再按差值套长度下限
  `FUZZY_MIN_LENGTH_SHORT = {0,4,8}` / `FUZZY_MIN_LENGTH_LONG = {0,5,10}`（下标 = 差值）。
- 辅助 `commonSuffixLength(a, b, prefixLength)`；所有 `(prefixLength, suffixLength)` 组合里取
  **最小差值**，用最小差值去套长度下限。

关于阈值归属：用户原文 2a 给"目录 4 / 内容 5"、2b 给"内容 4 / 目录 5"，二者自洽的读法是
**短的一侧 ≥ 4（差 1）/ ≥ 8（差 2），长的一侧 ≥ 5 / ≥ 10**，实现按此。

### 与用户原话的偏差（需用户确认）

用户说的是"把其中一侧拆成两段（A+B 相邻），另一侧 = A + 中间 + B"，即**必有一侧中间为空**。
实现按"两侧中间都要算进差值"实现，是原规则的**超集**：额外覆盖了
"1 个字符被替换"的情形（两侧中间各 1 个 → 差值 2，需要 ≥8/≥10 的长串）。
这个超集正好修好了 `20091006…` 里 `行`(U+884C) vs `行`(U+FA08 CJK 兼容表意文字) 的 self 书签。

### 验证

  差 2 字符的长度下限 8/10 通过而 6/8 拒绝、差 1 字符但长度 < 4 拒绝）。`-Dtest=*Bookmark*Test` 79/79 绿。
- 前后对比（临时探针，跑完已删）：把 `MAX_FUZZY_TITLE_GAP` 临时设为 0 关闭模糊匹配，对 `tmp_output`

  - 目标文档：`附錄一 8→11`、`附錄二 12→15`、`附錄三 15→18`（印刷页统一 +3 偏移，related 3→1）；
  - `200711131781638086275024718`：`新修訂之本集團其他財務資料 18→22`（正文页 22 的标题是
    `新修訂之本集團之其他財務資料`，中间多一个"之"）；
  - `200910061781738030852011943`：3 条 self 书签 `related_id` 0→2/1/3（`行`/`行` 兼容字差异）。

### 待确认/遗留

1. 差值定义：现为"两侧中间多余字符之和 ≤ 2"（含 1 字符替换=2）。若要严格按原文（必有一侧中间为空）
   只需在 `isFuzzyTitleMatch` 里追加 `title.length()==prefix+suffix || itemText.length()==prefix+suffix`。
2. 生效范围：`matchBookmarkTitle` 有 3 个调用方——目录→正文解析、self 书签 `related_id` 解析、
   self 书签 `page_num` 修复；本次**三处都生效**。
3. 归一化只删 `\s`（ASCII 空白），**全角空格 U+3000 不删**；若正文用全角空格分隔标题，仍会不匹配。
4. `責任聲明 .... ii` 这类**罗马数字**目录条目依旧不参与正文解析（`parseOriginalPageNum` 非纯数字返回 0
   → `resolveCatalogBookmarkTarget` 提前 return），所以仍是 `page=1`。

## 有线表格误判为 7 列 9 行 —— 根因定位（未改代码，等用户确认方案）

### 现象

`docs/pdf/200706271781617929794015618-1.pdf` 第 1 页表格：视觉是 **4 行 3 列**（`Ordinary Resolutions`
两行合并、`Number of Shares (%)` 两列合并），但 `tmp_output/...json` 里输出成 **9 行 × 7 列**，
多出 4 个宽 0.51pt 的空列与 5 个高 0.51/0.45pt 的空行，且合并单元格 span 被放大成 rowSpan 3 / colSpan 3。

### 根因（三段证据闭合）

1. **PDF 画法**：PDFBox `PDFStreamParser` dump 出每条表格线都是
   `m=(283.4610,6913.7002) l=(5669.2900,6913.7002) l=(5664.1802,6908.6001) l=(288.5660,6908.6001)`
   （**3 条边的开放路径**，坐标被 cm 放大 10 倍）→ `f*` → `w 0` + `S`。即"宽 0.51pt 的填充带 + hairline 描边"，
   视觉上是 0.5 磅（≈0.176mm）的单条表格线。
2. **解析层**：`ChunkParser.processf()` 里的 `parsingRectangleFromLines()` 要求**4 条首尾相接的边**才会把带子压成
   一条中心线；本 PDF 只有 3 条边（第 4 条靠 `f*` 隐式闭合）→ 返回 null，填充只 union bbox。
   `ChunkParser.processS()/processs()` **没有**任何压线逻辑，把 3 条边逐条转成 `LineChunk`（hairline，width 0.1）。
   → 探针实测 `LinesCollection` 里每个表格线位置都是**两根相距 0.51pt 的平行线**
   （如 `V x=28.3461` 与 `V x=28.8563`、`H y=427.1240` 与 `H y=426.6140`）。
3. **表结构层**：`TableBorder.calculateXCoordinates/calculateYCoordinates`（`TableBorder.java:91/276`）的聚类判据
   `x2 < v.getLeftX() - NodeUtils.VERTEX_TABLE_FACTOR * v.getRadius()`（factor=4、半径 0.05 → 阈值 0.2pt）
   小于 0.51pt 间距 → 每根线产生 2 个边界。实测
   `xCoordinates=[28.3463, 28.85645, 399.061, 399.5715, 482.74, 483.25, 566.4185, 566.929]`（8 个 → **7 列**）、
   `yCoordinates` 10 个 → **9 行**，与 JSON 完全吻合。

### 方案（已纸面推演，待用户选）

- **B（推荐，最小改动）**：在 `calculateXCoordinates/calculateYCoordinates` 的聚类阈值上加下限
  `max(VERTEX_TABLE_FACTOR*radius, MIN_BORDER_COORDINATE_GAP≈1.0pt)`，把间距 ≤1pt 的相邻边界合并（x1 取最小 leftX、
  x2 取最大 rightX）。推演结果：8→4 个 x 边界（3 列）、10→5 个 y 边界（4 行），`getCoordinateX/Y` 仍能覆盖原线位，
  `processMergedCells` 自动给出 rowSpan 2 / colSpan 2。
- **A（治本、风险大）**：改 `ChunkParser`，让 `processS/processs` 也走"细带压中心线"，并把
  `parsingRectangleFromLines` 从"必须 4 条边"放宽到"3 条边 + 隐式闭合"。
- **C（隔离在 opendataloader）**：在 `TableBorderProcessor`/`TableStructureNormalizer` 后处理里删除
  "宽/高 ≈ 线带厚度且无内容"的窄行窄列并修正相邻 span（`TableStructureNormalizer` 现在只对"行≤2 且列≥3"生效，不覆盖本例）。

### 调试痕迹

- 临时探针 `TmpBorderProbe` / `TmpContentProbe`（已删除，源码未留）；日志归档在
  `tmp_output/tmp_border_probe.log`（线条+坐标）、`tmp_output/tmp_content_probe.log`（ContentStream 操作）。
- 第 1 页渲染图：`tmp_output/page0_render.png`，视觉确认为 4 行 3 列。
- `DebugSample.java` 未改动（其第 45 行本已指向本 PDF）。

## 有线表格误判 —— 按方案 A 修复并验证（用户选定 A）

### 改动（仅 1 个文件）

`veraPDF-validation/wcag-validation/src/main/java/org/verapdf/gf/model/factory/chunks/ChunkParser.java`（+115/-1）

- 新增 3 个常量：`MAX_STRIPE_THICKNESS = 3.0`（最终坐标系的条带厚度上限，pt）、
  `MAX_STRIPE_THICKNESS_TO_LENGTH_RATIO = 0.2`（细长比，等价于长度 ≥ 5×厚度）、
  `MAX_STRIPE_JOINING_EDGE_FACTOR = 2.5`（连接边长度 / 厚度上限，45° 斜接约 1.41）。
- 新增 `parsingStripeFromLines(int i, int[] consumed)`：把"描边成一条路径的细长四边形"折叠成
  **一条带厚度的中心线**。支持**显式闭合 4 边**与**隐式闭合 3 边**两种形态；中心线端点取两条连接边的中点，
  宽度取两条平行长边的间距（与既有 `parsingRectangleFromLines` 同一公式）。
- `processS()` 从 for-each 改为索引循环，优先尝试 `parsingStripeFromLines`，命中则 `i += consumed[0] - 1` 跳过已消费的边。
- 新增辅助方法 `asLineChunk` / `getLineLength(LineChunk)` / `getLineLength(LineChunk, boolean)`。

**关键点**：`parsingRectangleFromLines` 原判据 `isHorizontalLine/isVerticalLine` 要求连接边是"竖线/水平线或退化点"，
而本类"斜接带"的斜边两者都不是（梯形），所以**即使放宽到 4 条边也匹配不上**；新方法去掉了连接边的类型约束，
改用"平行长边 + 细长比 + 连接边足够短 + 绝对厚度上限"四个判据。
另注意 `nonDrawingArtifacts` 里的线处于**变换前**坐标（本例被 cm 放大 10 倍），所以绝对厚度要用
`graphicsState.getCTM().getScaleValue()` 换算后再比 `MAX_STRIPE_THICKNESS`（比率类判据与缩放无关）。
`w 0` 不会写入 graphicsState（`ChunkParser` 里 `if (width > 0.0)`），所以 hairline 用的是 GraphicsState 默认线宽 1.0。

### 验证

- **端到端**：目标 PDF 的 `lattice_table` 从 `9 行 × 7 列`（含 4 个 0.51pt 空列、5 个空行）变为 **`4 行 × 3 列`**，
  `Ordinary Resolutions` = rowSpan 2、`Number of Shares (%)` = colSpan 2，空单元格全部消失；
  页面上那个"文本框"也从 **2 个 1x1 表格**合并为 1 个。
- **回归（77 个样本）**：`docs/pdf` 下 66 个 ≤2MB + 11 个 2~20MB，用临时探针只跑
  `DocumentProcessor.preprocessing` 后 dump 每个 `TableBorder` 的 `RxC` 与逐格 rowSpan/colSpan：
  **仅目标文档出现差异（且为改善），其余 75 个样本结构逐字不变**。
  结果文件 `tmp_output/table_shape_before_small.txt` / `_after_small.txt` / `_before_mid.txt` / `_after_mid.txt`，
  探针源码备份在 `tmp_output/probe_backup/TmpTableShapeProbe.java`（src 下的副本已删）。
- **单测**：`opendataloader-pdf-core` 改动前后均为 `Tests run: 893, Failures: 40, Errors: 17, Skipped: 1`
  （那 40+17 个失败全是图片/页分隔/AutoTagger 等环境相关的**既有失败**，与线条表格无关）；
  线条/表格相关的 `ShapeRecognizerTest`(22)、`TableBorderProcessorTest`(8)、`TextDecorationProcessorTest`(21)、
  `SpecialTableProcessorTest`(1) 全绿。`wcag-validation` 模块本身没有测试。
- 对比基线的手法：`git stash push -- <ChunkParser.java>` → `mvn -o -pl wcag-validation install` → 跑探针 → `git stash pop`。

### 遗留

- `processB()`（`B`/`b` 填充+描边）**没有**应用同样的条带折叠，同类 PDF 若用 `B` 画表格线仍会出双线；
  本次为控制影响面只动了 `processS()`（`S`/`s`）。若要一并处理，可复用 `parsingStripeFromLines`。
- 生产侧要让修复生效，必须把改过的 `wcag-validation` 一起构建/安装（本次已 `install` 到 `D:\Maven_Repo`）。
