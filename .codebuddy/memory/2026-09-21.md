## 目录↔正文标题"相似性兜底匹配"（用户指定规则，已实现）

### 触发问题

`docs/pdf/202609031788435163969004864.pdf` 一级目录 `附錄一  －  購回授權之說明函件`（目录页第 2 页）
与正文页眉 `附錄一                  購回授權之說明函件`（第 11~14 页）**没匹配上**，
差异只有目录侧多出的 `－`（U+FF0D）。后者不在 `related_id` 解析范围内，于是 `附錄一` 的
`page_num` 停在印刷页 8、`related_id` 停在目录行自身的 item id。

### 根因

`CatalogBookmarkProcessor.matchBookmarkTitle`（主逻辑约 1878 行）只有两级判据：

```java
if (normalized.equals(normalizedTitle)) return MatchQuality.EXACT;
if (normalized.startsWith(normalizedTitle)) return MatchQuality.PREFIX;
return null;   // MatchQuality.CONTAINS 定义了但从未返回
```

`normalizeBookmarkText` 只删 `\s`，不删中间标点，所以"差一个 `－`"直接落空。

### 实现（用户给的规则）

- 新增 `MatchQuality.FUZZY`（枚举顺序 `EXACT, PREFIX, FUZZY, CONTAINS`；`ordinal()` 越小越优，
  所以相似匹配只在精确/前缀都失败后兜底）。
- `matchBookmarkTitle` 末尾追加 `isFuzzyTitleMatch(...)`。
- 判据：两条串必须有**非空的公共前缀**与**非空的公共后缀**，两侧中间"多出来的字符"之和 ≤
  `MAX_FUZZY_TITLE_GAP = 2`；再按差值套长度下限
  `FUZZY_MIN_LENGTH_SHORT = {0,4,8}` / `FUZZY_MIN_LENGTH_LONG = {0,5,10}`（下标 = 差值）。
- 辅助 `commonSuffixLength(a, b, prefixLength)`；所有 `(prefixLength, suffixLength)` 组合里取
  **最小差值**，用最小差值去套长度下限。

关于阈值归属：用户原文 2a 给"目录 4 / 内容 5"、2b 给"内容 4 / 目录 5"，二者自洽的读法是
**短的一侧 ≥ 4（差 1）/ ≥ 8（差 2），长的一侧 ≥ 5 / ≥ 10**，实现按此。

### 与用户原话的偏差（需用户确认）

用户说的是"把其中一侧拆成两段（A+B 相邻），另一侧 = A + 中间 + B"，即**必有一侧中间为空**。
实现按"两侧中间都要算进差值"实现，是原规则的**超集**：额外覆盖了
"1 个字符被替换"的情形（两侧中间各 1 个 → 差值 2，需要 ≥8/≥10 的长串）。
这个超集正好修好了 `20091006…` 里 `行`(U+884C) vs `行`(U+FA08 CJK 兼容表意文字) 的 self 书签。

## 有线表格误判为 7 列 9 行 —— 根因定位（未改代码，等用户确认方案）

### 现象

`docs/pdf/200706271781617929794015618-1.pdf` 第 1 页表格：视觉是 **4 行 3 列**（`Ordinary Resolutions`
两行合并、`Number of Shares (%)` 两列合并），但 `tmp_output/...json` 里输出成 **9 行 × 7 列**，
多出 4 个宽 0.51pt 的空列与 5 个高 0.51/0.45pt 的空行，且合并单元格 span 被放大成 rowSpan 3 / colSpan 3。

### 根因（三段证据闭合）

1. **PDF 画法**：PDFBox `PDFStreamParser` dump 出每条表格线都是
   `m=(283.4610,6913.7002) l=(5669.2900,6913.7002) l=(5664.1802,6908.6001) l=(288.5660,6908.6001)`
   （**3 条边的开放路径**，坐标被 cm 放大 10 倍）→ `f*` → `w 0` + `S`。即"宽 0.51pt 的填充带 + hairline 描边"，
   视觉上是 0.5 磅（≈0.176mm）的单条表格线。
2. **解析层**：`ChunkParser.processf()` 里的 `parsingRectangleFromLines()` 要求**4 条首尾相接的边**才会把带子压成
   一条中心线；本 PDF 只有 3 条边（第 4 条靠 `f*` 隐式闭合）→ 返回 null，填充只 union bbox。
   `ChunkParser.processS()/processs()` **没有**任何压线逻辑，把 3 条边逐条转成 `LineChunk`（hairline，width 0.1）。
   → 探针实测 `LinesCollection` 里每个表格线位置都是**两根相距 0.51pt 的平行线**
   （如 `V x=28.3461` 与 `V x=28.8563`、`H y=427.1240` 与 `H y=426.6140`）。
3. **表结构层**：`TableBorder.calculateXCoordinates/calculateYCoordinates`（`TableBorder.java:91/276`）的聚类判据
   `x2 < v.getLeftX() - NodeUtils.VERTEX_TABLE_FACTOR * v.getRadius()`（factor=4、半径 0.05 → 阈值 0.2pt）
   小于 0.51pt 间距 → 每根线产生 2 个边界。实测
   `xCoordinates=[28.3463, 28.85645, 399.061, 399.5715, 482.74, 483.25, 566.4185, 566.929]`（8 个 → **7 列**）、
   `yCoordinates` 10 个 → **9 行**，与 JSON 完全吻合。

### 方案（已纸面推演，待用户选）

- **B（推荐，最小改动）**：在 `calculateXCoordinates/calculateYCoordinates` 的聚类阈值上加下限
  `max(VERTEX_TABLE_FACTOR*radius, MIN_BORDER_COORDINATE_GAP≈1.0pt)`，把间距 ≤1pt 的相邻边界合并（x1 取最小 leftX、
  x2 取最大 rightX）。推演结果：8→4 个 x 边界（3 列）、10→5 个 y 边界（4 行），`getCoordinateX/Y` 仍能覆盖原线位，
  `processMergedCells` 自动给出 rowSpan 2 / colSpan 2。
- **A（治本、风险大）**：改 `ChunkParser`，让 `processS/processs` 也走"细带压中心线"，并把
  `parsingRectangleFromLines` 从"必须 4 条边"放宽到"3 条边 + 隐式闭合"。
- **C（隔离在 opendataloader）**：在 `TableBorderProcessor`/`TableStructureNormalizer` 后处理里删除
  "宽/高 ≈ 线带厚度且无内容"的窄行窄列并修正相邻 span（`TableStructureNormalizer` 现在只对"行≤2 且列≥3"生效，不覆盖本例）。

- 临时探针 `TmpBorderProbe` / `TmpContentProbe`（已删除，源码未留）；日志归档在
  `tmp_output/tmp_border_probe.log`（线条+坐标）、`tmp_output/tmp_content_probe.log`（ContentStream 操作）。
- 第 1 页渲染图：`tmp_output/page0_render.png`，视觉确认为 4 行 3 列。

## 有线表格误判 —— 按方案 A 修复并验证（用户选定 A）

### 改动（仅 1 个文件）

`veraPDF-validation/wcag-validation/src/main/java/org/verapdf/gf/model/factory/chunks/ChunkParser.java`（+115/-1）

- 新增 3 个常量：`MAX_STRIPE_THICKNESS = 3.0`（最终坐标系的条带厚度上限，pt）、
  `MAX_STRIPE_THICKNESS_TO_LENGTH_RATIO = 0.2`（细长比，等价于长度 ≥ 5×厚度）、
  `MAX_STRIPE_JOINING_EDGE_FACTOR = 2.5`（连接边长度 / 厚度上限，45° 斜接约 1.41）。
- 新增 `parsingStripeFromLines(int i, int[] consumed)`：把"描边成一条路径的细长四边形"折叠成
  **一条带厚度的中心线**。支持**显式闭合 4 边**与**隐式闭合 3 边**两种形态；中心线端点取两条连接边的中点，
  宽度取两条平行长边的间距（与既有 `parsingRectangleFromLines` 同一公式）。
- `processS()` 从 for-each 改为索引循环，优先尝试 `parsingStripeFromLines`，命中则 `i += consumed[0] - 1` 跳过已消费的边。
- 新增辅助方法 `asLineChunk` / `getLineLength(LineChunk)` / `getLineLength(LineChunk, boolean)`。

**关键点**：`parsingRectangleFromLines` 原判据 `isHorizontalLine/isVerticalLine` 要求连接边是"竖线/水平线或退化点"，
而本类"斜接带"的斜边两者都不是（梯形），所以**即使放宽到 4 条边也匹配不上**；新方法去掉了连接边的类型约束，
改用"平行长边 + 细长比 + 连接边足够短 + 绝对厚度上限"四个判据。
另注意 `nonDrawingArtifacts` 里的线处于**变换前**坐标（本例被 cm 放大 10 倍），所以绝对厚度要用
`graphicsState.getCTM().getScaleValue()` 换算后再比 `MAX_STRIPE_THICKNESS`（比率类判据与缩放无关）。
`w 0` 不会写入 graphicsState（`ChunkParser` 里 `if (width > 0.0)`），所以 hairline 用的是 GraphicsState 默认线宽 1.0。

  探针源码备份在 `tmp_output/probe_backup/TmpTableShapeProbe.java`（src 下的副本已删）。

## `201804301783315258232046605-2.pdf` 第 4/5 列误判 —— 根因定位（未改代码，等用户确认）

### 现象

表格 id=6（14 行 × 5 列）。表头 r0 的最后一格是 `colSpan=2`（455.617–546.484）✓；最后一行 r13 也是 `colSpan=2` ✓；
**但 r1~r12（即用户说的"第 2 至 13 行"）**：`cells[3]` 与 `cells[4]` **都指向 colNumber=4 的对象**，
第 4 格输出成"bbox 未初始化（x0=Double.MAX_VALUE）、无内容"的空格，第 5 格（540.34–546.484）是独立空格 →
**PDF 里明明有数值（278,873,873.56 等）的内容全丢**。

### 根因（四级证据链）

1. **PDF 真实几何**（content stream + 300dpi 像素扫描双重证实）：

| 位置 | 横线实际延伸到 |
|---|---|
| 表头行上/下边界（y=354.29 / 313.49） | **x=547.204** |
| 数据行各分界线（y=295.13 … 84.12）与**底边**（y=65.16） | **x=540.220** |

   即**表格右侧是"阶梯状"**：表头行宽到 547.2，数据行 + 底边只宽到 540.2（差 6.98pt）。
   像素扫描：表头行 `rightMostDark=546.96/546.24`，数据行与底边 `540.00/539.04`。
   内容侧：数值文本右端 = **537.36**，右边距 2.86pt，与第 2 列（452.16→3.46pt）、第 3 列（352.08→4.27pt）同量级
   → **数值确实属于 col3（455.617–540.220）**，不是"溢出到 540.2 之外"。
2. **`processHorizontalLines`（`TableBorder.java:348`）** 用横线的 `lastColNumber = getCoordinateX(line.getRightX())`
   去切 rowSpan：数据行横线右端 540.220 → `lastColNumber=4`，只把 `cells[3].rowSpan` 置 1，
   **`cells[4].rowSpan` 从未被任何横线切过**（表头行分界线 y=313.49 有 `541.420–547.200` 段覆盖 col4，但那作用在 rows[0]）。
   于是 r1 的 `cells[4].rowSpan` 保持"一路到表底" = 13（`processMergedCells` 第一段还会显式累积最后一列的 rowSpan）。
3. **`processMergedCells`（`TableBorder.java:437-480`）的"跨度对齐"分支**：对 r1~r12 的 col3，
   `cells[3]`（rs=1, cs=2）与 `cells[4]`（rs=13, cs=1）的"行覆盖终点"不一致（2 vs 14）→ 走 badCell 分支执行
   `rows[rowNumber].cells[colNumber].setColNumber(rows[rowNumber].cells[colNumber + 1].colNumber)`
   → **`cells[3].colNumber` 被改写成 4**，同时 `setColSpan(1)`。
   （r0 与 r13 不触发：r0 的 cells[4].rowSpan 被 y=313.49 的 col4 段切成 1；r13 的 cells[4].rowSpan 初始就是 1。）
4. **输出层两个连带后果**：
   - `createMatrix` 只为 `cell.colNumber == 列号 && cell.rowNumber == 行号` 的格子设置 bbox
     → `cells[3]`（colNumber 已是 4）**bbox 保持未初始化**（JSON 里那个 `x0=1.797e308` 的空格就是它）；
   - `JsonWriter`（`JsonWriter.java:1033-1090`）按 `cumulativeColSpans` 步进、取文本时用
     `rows[cell.rowNumber + n].cells[cell.colNumber + k]` → 对 `cells[3]` 取到的是 `rows[1].cells[4]`（空）
     → **数值内容丢失**；随后 `i=4` 还输出独立的 `cells[4]`（540.34–546.484 空格）。

   内容归属确认：`getTableBorderCells` 里 `getClosestLeftX(500)=3`、`getClosestRightX(537.4)=4` → 只落进 `cells[3]` ✓。

### 方案（待用户选定）

- **方案 A（推荐，符合用户期望"第 4、5 列合成 1 列"）**：改 `processMergedCells` 的 badCell 分支 ——
  左右两格跨度冲突时**以左侧格为准**（保留 `cells[c]` 的 colNumber/colSpan，让 `cells[c+1]` 指向 `cells[c]`），
  而不是把 `cells[c]` 改写成 `cells[c+1]`。预期：r1~r12 每行输出 4 格，第 4 格含数值，第 5 列不再出现。
- **方案 B（保守）**：只去掉 `setColNumber` 那一行（保留 `setColSpan(1)`）→ 内容回来，但第 5 列仍是一个空白格。
- 两个方案都在 `veraPDF-wcag-algs`（跨仓库），影响所有有线表格，需要回归（可复用 77 样本 `RxC + span` 对比手法）。

### 待用户澄清

PDF 里"数据行的表格右边框（540.2）比表头（547.2）窄 6.98pt"是客观事实，所以"第 4、5 列是不是同一列"
属于**语义选择**：可以解释为"col4 在数据行是跨 13 行的空白合并格"（方案 B），
也可以解释为"col4 位在数据行不属于表格、应并入 col3"（方案 A，用户所述）。

## `201804301783315258232046605-2.pdf` 第 4/5 列误判 —— 按用户方案实施（右边界横向补齐）

### 用户给的规则（三点，已逐条确认过理解）

1. "右侧没有闭合竖线"**按整张表**判断，不逐行；
2. 竖线要算"有效边框"，必须**在它所覆盖的每一行上跨度 ≥ 该行高度的 2/3**（碎片不算）；
3. "右侧没有闭合竖线"的判据 = `右侧横线右端的最小值 − 整表最右侧有效竖线 x > 10pt`
   （竖线离最短的右侧横线右端 10pt 以上 ⇒ 右侧没有竖线封口）；
4. 满足 1~3 时，把**每一条右端距表格右边界 < 10pt 的横线**延长到表格最右端。

### 实施

`veraPDF-wcag-algs/.../tableBorders/TableBorder.java`（+108 / −1）：

- 新增常量 `RIGHT_EDGE_EXTENSION_GAP = 10.0`、`MIN_VERTICAL_LINE_ROW_COVERAGE = 2.0/3.0`；
- 新增 `extendShortRightHorizontalLines(builder)` + `isVerticalLineCoveringRows(line)`；
- **构造函数顺序改为 `calculateYCoordinates` → `extendShortRightHorizontalLines` → `calculateXCoordinates`**
  （判定有效竖线要用行高，所以 Y 必须先算；两者互不依赖，交换安全）。

### 两个必须记住的实现坑

1. **有效竖线判定不能用 bounding box**：`getTopY()/getBottomY()` 含半线宽，会让竖线"擦到"相邻行，
   于是每条竖线都因"某一行的覆盖不足"被判为碎片。改用 **`getStartY()/getEndY()` 端点** +
   **`yCoordinates` 的边界中心**（不用 `getTopY/getBottomY`）后正常。
2. **延长后必须用 `LineChunk.createLineChunk(..., BUTT_CAP_STYLE, color)` 重新构造，不能直接 `new LineChunk(...)`**：
   `transformLineChunk` 走的是 `createLineChunk`，它会把端点**内缩半个线宽**，于是 `getLeftX()/getRightX()`
   恰好落在原端点上；而直接 `new LineChunk` 会让 bbox 外扩半个线宽 → `getRightX()` 变成 `547.444`
   （超出最后一个边界带 `[545.764, 547.204]`）→ `getCoordinateX` 返回 **-1** → **整条横线被 `processHorizontalLines` 整条忽略**
   （症状：所有行边界都不生效，整列被当成跨行合并，数值全挤进一格，形如 `R14C1`）。

## 流程图识别：新增 `arrow_header` + 按箭头范围递归确定流程图区域（已实现并验证）

### 需求（用户）与澄清

1. `ShapeChunk` 新增 `arrow_header`（**只识别箭头头部**）；澄清：**`arrow` 保持"轴∪头"不变**，额外产出只覆盖头部的 `arrow_header`。
2. 存在 `arrow_header` 时，按**每个箭头的范围递归**吸收有交集的"线或其他图形"确定流程图范围；**范围相交则合并**。
   澄清：相交 = **bbox 相交 + 2pt 容差**；对象 = **`ShapeChunk` + 原始 `LineChunk`/`LineArtChunk`**。
3. 不存在 `arrow_header` 时**保持现有流程**。
4. 106/107 期望：**识别成流程图截图**，两个误判表格消失。
5. 箭头范围与 `isRegularTable`（0.3）冲突时：**箭头范围优先，跳过表格否决**（其余保护仍生效）。

### 关键现状发现

- **106/107 上箭头画了但现有 `arrow` 看不到**：`recognizeConnectorLines` 先要求 `isConnectorLine`
  （轴两端都要靠近两个已识别图形），不通过就直接 `continue`，**根本没机会找头**。
  106 上真正的小三角 `[265.53,475.49,270.52,479.81]`（5×4.3pt）因此被漏掉；整页只认出 2 条**无头**的 `arrow`。
  → 结论：`arrow_header` 的识别必须**独立于 `isConnectorLine`**，否则 106/107 不会产生任何头部（会走旧流程）。
- 106 的旧分组 `GROUP#8/[86.88,375.83,462.05,475.89]` 与 `GROUP#9/[126.46,484.28,508.39,531.89]`
  各自都被"常规表格否决"（0.62 / 0.34 > 0.3）挡住 → 无截图 + 2 个误判表格。

### 实现（4 主文件 + 3 测试文件，+539/−27）

- `ShapeChunk`：`TYPE_ARROW_HEADER = "arrow_header"`（`ShapeChunk` 不进 JSON，故不影响 JSON 结构）。
- `ShapeRecognizer`：
  - 对**每条**单段/共线链解析头部（不管 `isConnectorLine`）；`arrow` 的产生条件与范围不变（`findArrowBBox` 拆成 `findArrowhead`+`unionOf`）。
  - `arrowheadOnly(candidate, shaft)`：只取"**轴端之外**"的切片（很多 PDF 把整支箭头画成一个填充多边形）。
  - `isUsableArrowhead`：`面积 ≥ 4pt²` 且 `两边 ≥ 2pt`。
  - `filterCandidatesInsideShapes`：候选被已识别 `rectangle/bar_chart` **覆盖 ≥ 90%** 就丢弃。
  - `groupShapesByArrowHeaders(shapes, extraItems)`：以每个头部为种子，**反复**吸收与区域 bbox 相交（2pt）的项，范围相交的 region 合并。
  - 两个候选源的过滤**提到链循环外只做一次**（性能）。
- `FlowchartProcessor`：新增带 `arrowDriven` 的 7 参重载；`arrowDriven` 时跳过 `isRegularTable`；
  `collectCluster`/吸收后续组改用 `unionBoundingBoxes`（含原始线条）；`arrowCount` 把头部也算箭头。
- `DocumentProcessor`：新增 `collectRawLineChunks(page)`（普通 `LineChunk` 早在 Loop 2 已被从 `pageContents` 过滤掉）；
  `arrowDriven = containsArrowHeader(...)`；bar/pie **仍用旧分组**，只有流程图用 arrow 分组（空则回退）；把 `arrowDriven` 传下去。
