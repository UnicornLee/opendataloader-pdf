### 机制结论（已由 jstack 确证 —— 修正：不是"阻塞"，而是"线程死亡"）
`PulsarService.consumeReceiveLoop` = 「单线程同步：receive → handleReceiveMessage(download→processForPulsar→send→清理) → ack」，
`receiverQueueSize(1)`；**循环只 catch `Exception`**（`handleReceiveMessage` 内部也只 catch `Exception`）。

**真正根因：6 个消费线程被"未被捕获的 `java.lang.Error`"打死（`Error` 不是 `Exception`，两处 catch 都拦不住）→ 线程终止。**
- 线程虽死，它持有的 `Consumer` 仍注册在 broker（`consumers_count=7` 不变），但**再没有任何线程对它调 `receive()`/`acknowledge()`**
  → 它手上那条消息**永久 unacked**，且该消费者槽位**永久失效**。
- 所以 **未确认数 == 死掉的线程数（当前 6）**；`ackTimeout=60s` 无效（无代码再回到那个 consumer）；`blocked_on_unacked=0`、`redeliver=0` 由此解释。
- 症状"总是有几个不消费" = 每次 Error 事件永久吃掉一个槽位，累积增长。

**jstack 铁证（`docs/debuglogs/jstack-app088-20260914_163816.txt`，2026-09-14 16:38:16，共 78 线程）**：

### 决策（用户问："线程已不会被 Error 打死，后续两项还有必要吗"）
结论：**第 1 项（Error 后 nack/close）不需要、且不建议；第 2 项（线程存活看护）非必需、可选延后；真正该做的是第 4 项（查清/压掉 Error 本身）。**
- 第 1 项不必要：`catch (Throwable)` 后，Error 会被 `handleReceiveMessage` 内部吞掉并**继续走到末尾 `acknowledgeQuietly`** → 消息照样被 ack，**不会漏槽位**。
  且改成 nack 会让"确定性失败的大文件"陷入 `nack→重投→再 Error→再 nack` 毒消息循环；`close()` 更糟（丢整个 consumer）。
  现有契约"失败仍 ack、jsonUrl='' 让下游决策（可用 retry_pdf_parse 重试）"已覆盖。
- 第 2 项非必需：原死因（Error 逃逸循环）已被堵住。仅剩极极端情形（catch 块自身在 OOM 下再抛 Error、JVM 级问题）会退出线程 → 属纵深防御，优先级低。
- 关键副作用（正向）：改动把故障从「**永久停摆（可用性事故）**」降级为「**个别大文件解析失败并正常上报**」，
  且 Error **第一次能被记进日志**（`handleReceiveMessage failed ... <Error> + 栈`）→ 下次可从 Kibana 取到 OOM/SOE 实栈。
- 下一步建议：上线后先**不改代码**，在 Kibana 抓 `handleReceiveMessage failed` 里的 Error 实栈，再决定压堆/流式处理/限并发。
