## 排查：`... Error when generating JSON data of page 3: fallback to empty page: JsonMappingException: Character N ...`

用户报的警告来自 `202303251679660111823147.pdf`（正是上面阈值那件事的同一份文档）。**只定位，未改代码。**

- **直接原因（实测插桩）**：第 3 页唯一的 item 是 `ImageChunk`，其包围盒 `box=[-711.456543, NaN, 761.8010177000001, NaN]` —— **纵向坐标是 NaN**
  （`[NANDBG] pg=2 item ...ImageChunk ... marginTop=NaN prevBottomY=807.87 height=807.87 emptyBox=false`）。
  `JsonWriter` 写 `margin_top = prevBottomY - topY = 807.87 - NaN = NaN`。
- **崩溃点**：`DoubleSerializer.round()` 用 `new BigDecimal(Double.toString(value))`；`Double.toString(NaN)` = `"NaN"`，
  而 `BigDecimal(String)` **不接受 NaN/Infinity**（只有 `BigDecimal(double)` 那条路才有专门处理）→ `NumberFormatException: Character N ...`
  → `MapSerializer` 包装成 `JsonMappingException`。**"Character N" 就是 NaN 的首字母；Infinity 会报 "Character I"。**
- **被兜底吞掉**：`JsonWriter.writeToCustomJson()` 逐页 try/catch，异常时写 `placeholderPageJson()` → 该页输出成 `items: []` 空页，只留一行 WARNING。
  实测 `corpus_before` 里该文档 p3 同样是 0 items，p1–p6 与改动后逐项一致 → **与本轮流程图/表格改动无关**。
- **NaN 上游来源**：第 3 页内容流 **15.8 MB**，绘制 `Im0`（3840×2160）的矩阵为
  `1473.2575607 0 0 828.7073779 -711.456543 -9.1160693 cm`（图横跨 -711~762，远超页宽 595.28）。
  veraPDF `ChunkParser.parseImageBoundingBox()`（`veraPDF-validation/wcag-validation`，`Do`/`BI` 分支）直接用 CTM 分量算盒：
  x1=translateX=-711.456543 ✓（= e）、x2=x1+scaleX=761.801 ✓（= e+a），**但 y1=translateY=NaN、y2 也 NaN**（f=-9.116 明明有限）。
  内容流里没有任何 `nan/NaN/inf` 字面量（实测索引 -1）→ 是 veraPDF 侧累加 CTM（大量嵌套 q/Q + 透明组 Form）算出的 NaN，不是 PDF 显式写的。
- **两个放大器（bug 本体）**：① `BoundingBox.isEmpty()` 用比较判定，**NaN 参与比较恒 false** → 坏盒子被判为"非空"合法（`emptyBox=false`）一路通过；
  ② `DoubleSerializer` 只做四舍五入、没处理非有限值，而 JSON 标准本就不支持 NaN/Infinity 字面量。
- **修复方向（待用户定）**：上游 `parseImageBoundingBox()` 加 `Double.isFinite` 校验并回退到图像实际尺寸/跳过；core 的 `DoubleSerializer` 对 NaN/Infinity 定策略（写 0/null/省略字段）；
  各 `isEmpty()`/`isStillOnPage()` 判定补 `isFinite`；兜底从"丢整页"改为"丢该 item 重试"。
- **调试手法（可复用）**：`-DdbgNaN=1` 临时插桩 `JsonWriter.generateJsonPageContentData()` + 无 paddle 的临时入口 `DebugNaNTmp`；插桩已 `git checkout` 还原、临时类已删。
  dump 页面结构用单文件 `tmp_output/DumpPage.java`（pdfbox 3.0.4，注意 pdfbox 3 里 `PDPage.getContents()` 返回 `InputStream`，要 `IOUtils.toByteArray(...)`）。

## 排查：为什么 `catalog_bookmarks` 都没有子目录（`202303251679660111823147.pdf`）

用户疑问："catalog_bookmarks 都没有子目录，难道整个 page_bookmarks 不是最后一个 catalog_bookmark 的子目录吗？"

### 结论：不是父子关系，而是"三源择一"

- **三个并列来源**（`JsonWriter.writeToCustomJson` 第 220–230 行 / rebuild 路径第 432–440 行）：
  `catalog_bookmarks`（从目录页提取）/ `page_bookmarks`（从正文页候选构建的多级树）/ `self_bookmarks`（外部已有 JSON）。
- `BookmarkQualitySelector.select(...)` 按 `score = ln(1+effectiveCount) × (1−penalty)` **择一**（penalty = dup+unlinked+strange+nonMono+invalidLink 五项之和，≥0.5 淘汰），
  胜者写入 `bookmarks`，并把**胜者的那个 key 从 JSON 删除**（`map.remove(selectedSource)`，避免重复）。
  catalog 有"强胜率"保护：非 catalog 来源必须 `score ≥ catalog.score × 2.0` 才能赢（`CATALOG_STRONG_WIN_RATIO`）。
- **本文件实测日志**（`tmp_output/nan_verify.log`）：
  `catalog: total=10, score=2.398`；`page: total=199, effective=192, score=5.078`；`self: total=0 → eliminated`；
  `selected page_bookmarks: 5.078 is 2.12x catalog 2.398 (>=2.0x threshold), wins`
  → 所以 JSON 里 `bookmarks` 是 page 的树（`一、审计意见 > （一）商誉减值 > 1、事项描述`），`page_bookmarks` 键被删除，`catalog_bookmarks`（10 条扁平条目）保留。
- `catalog_page_range_start/end = 10`：目录页只有 10 行 → catalog 只有 10 条一级条目（`第一节…`），**扁平是正常的**。

### catalog 子目录本应被"补全"，但本文档补了 0 组

- 机制：`CatalogBookmarkProcessor.fillCatalogChildrenFromPageData()`（第 249–320 行）对没有 children 的 catalog 条目，
  用 `PageBookmarkProcessor.extractChildrenByRange(data, catalogStart, catalogEnd, anchorPage, anchorRelatedId, nextSiblingPage, nextSiblingRelatedId, level)`
  按 `[T, S)` 同级区间从页面候选里重建 L2/L3。
- **限制（根因）**：`extractChildrenByRange` 只接受固定模板 —— L2 接受 `第#节`/`第#条`（`TEMPLATE_SECTION`/`TEMPLATE_ARTICLE`），L3 只接受 `第#条`
  （文档注释第 498–502 行明确说这是为了过滤正文里的 `（#）` 残留）。
- 本文档目录一级本身就是"第X节"，正文二级是 `一、xxx`（`TEMPLATE_CHINESE_COMMA`）、三级是 `（一）xxx`（`TEMPLATE_PAREN`）→ **模板不匹配**。

### 澄清（用户问："难道不是按相邻同级的页码和 related_id 从 `*_page_bookmarks_collected.md` 收集子目录吗？"）

  其余情况沿用现有 `{第#节, 第#条}`/`{第#条}`。不要直接删闸门（会放进正文段落）；长度上限（200）与连续编号校验要保留。

### 实测："那把模板过滤去掉是不是就好了？" —— 不是（已实测并还原）

- 手段：给 `extractChildrenByRange` 的模板闸门加临时开关 `-DnoTemplateFilter=true`（用完已还原），重跑目标文档对比 `bookmarks`。
- **结果：能补出子目录，但质量不可接受**（`tmp_output/tmpl_scratch` vs `merge_scratch`）：
  | | 开闸门（现状） | 去闸门 |

  | 顶层数 | 10 | 10 |

- **两个致命副作用**：
  1. **层级混编**：同一层 children 里 `一、公司信息` 与 `1、股东及股东大会`、`（1）…` 平铺在一起（第三节同时出现 `一、报告期内…` 和 `1、医药外包服务行业…`），丢掉了父子关系。
  2. **正文段落混入**：第五节下出现 `（1）2022 年，长寿生产基地获取《重庆博腾制药科技股份有限公司技术中心建设项目环境影响报告书的批`（148 字符）等正文；
     `trimOverlongNodes` 的 200 字符闸门挡不住 100–200 字符的段落。
- 结论：必须"分层 + 模板"，即方案 A（按 catalog 锚点层级自适应模板），不能简单删闸门。
