# 2026-09-08

## JsonWriter 表格单元格文本行合并逻辑优化（cellTextLines）

文件：`java/opendataloader-pdf-core/.../json/JsonWriter.java`，表格写出分支（原 1030-1035 行附近）。

原逻辑：每个 `groupChunksByLine` 分组的文本只要非空且不重复就 `cellTextLines.add(...)`，
一行一元素，单元格内换行文本会被拆成多条。

新逻辑：
1. `cell.getRightX() - getGroupMaxRightX(group) > MAX_CELL_LINE_RIGHT_GAP(15)` → 独立成条；
   否则若 `cellTextLines` 为空 → 直接放入；不为空 → 拼接到最后一条末尾（`set(last, last + currentText)`）。
2. 例外：group 含 `ImageChunk`，或其中 `TextChunk.getValue()` 包含 `"<table"`（嵌套多行/多列
   `TableBorder` 经 `flattenCellContents` 渲染成 HTML 后包成单个 TextChunk）→ 强制独立成条，
   绝不拼到上一行（避免 `<img>`/`<table>` 粘到正文）。

新增：`private static final double MAX_CELL_LINE_RIGHT_GAP = 15`（常量在 `MAX_NESTED_TABLE_DEPTH` 旁）、
`getGroupMaxRightX(List<IObject>)`、`containsEmbeddedBlock(List<IObject>)`（均放在 `assembleGroupText` 之后）。

验证：`mvn -o -q -DskipTests compile`（core 模块）通过；未跑单测。

### 用户在其基础上的修正（最终版）

- gap 判断改用 **上一行** 的右边界决定 **当前行** 是否另起一条：`boolean nextNewLine` 在循环外声明，
  `newLine = containsEmbeddedBlock(group) || nextNewLine`；循环末尾再更新
  `nextNewLine = cell.getRightX() - getGroupMaxRightX(group) > MAX_CELL_LINE_RIGHT_GAP`。
  （修正了我原来的写法：我用的是当前行自己的 gap，会把"满宽折行 + 短行续行"的段落拆成两条。）
- 每个 `cellItem` 先算出独立的 `currentCellTextLines`，再合并进 `cellTextLines`（按文本去重），
  避免跨 cellItem 把 A 单元格末行与 B 单元格首行拼在一起。
- 拼接分支也加了 `!contains(currentText)` 去重 → 与 List 中已有整行完全相同的文本既不会新增也不会拼接。

### 已知待确认风险（未改，等用户决定）

1. 合并单元格（rowSpan/colSpan>1）用外层 `cell.getRightX()` 比较，跨列时 gap 偏大 → 基本每行都另起一条（不拼接）；
   如需按内层单元格宽度判断应改 `cellItem.getRightX()`。
2. 拼接分支的 `contains` 去重会静默丢弃"单元格内合法重复出现的同一行文本"。
3. 空文本 group（如仅含 TableBorder 的组）`continue` 时不更新 `nextNewLine`，沿用上一次的值。
