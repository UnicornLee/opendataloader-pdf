# 华为 OBS 上传集成

- 时间：2026-08-09
- 任务：在 `JsonWriter.writeToCustomJson` 中集成华为云 OBS 上传能力：当 `customOptions` 提供完整 OSS 配置时，把每页图片上传到永久桶并用 OSS URL 替换 JSON 中的本地图片路径；主 JSON 写入后上传到临时桶；返回上传后的 URL 与本地 OCR JSON 路径；上传成功后清理本地生成文件，并在资源释放后删除源 PDF。
- 状态：已实现 + `mvn compile` 通过；未运行真实 OBS 端到端验证。

## 目标（Goal）
- 让解析后的主 JSON 直接以 OBS URL 形式对外可用，避免下游再处理本地图片路径。
- 保留 `_ocr.json` 在本地，便于后续 OCR 流程消费。
- 上传完成后自动清理本地中间产物与源 PDF，减少磁盘占用。

## 用户偏好与约束（Constraints & Preferences）
1. 触发条件：`customOptions` 中必须同时存在 `businessId`、`basicEnv`、`pulsarReceiveTopicName`、`ossTempBucketName`、`ossPermanentBucketName`、`ossEndpoint`、`ossAccessKey`、`ossSecretKey`、`ossDomainName` 且非空；缺少任意一项则按原逻辑本地输出。
2. 图片上传路径：`public/{basicEnv}/{pulsarReceiveTopicName}_{businessId}/{imageFileName}`，上传到 `ossPermanentBucketName`。
3. 主 JSON 上传路径：`public/{basicEnv}/{pulsarReceiveTopicName}_{businessId}.json`，上传到 `ossTempBucketName`。
4. `pulsarReceiveTopicName` 取 topic 最后一级（去掉 `/` 前面部分）。
5. 上传成功后：删除 `outputFolder` 下与当前 PDF 相关的本地生成文件，但保留 `<pdfname>_ocr.json`。
6. 源 PDF 删除：OSS 上传成功且源 PDF 仍存在时，在 `DocumentProcessor.processFileWithResult` 的 `finally` 中释放资源后删除。
7. `OpenDataLoaderPDF.processFile` 返回 `ProcessingResult`，包含 `jsonUrlOrPath`（OSS URL 或本地绝对路径）和 `ocrJsonLocalPath`。

## 前置事实（已核实）
- `JsonWriter.writeToCustomJson` 主流程：
  - 先用 `JsonGenerator` 写出主 JSON。
  - 之后 `mapper.readValue(...)` 反序列化为 `Map<String, Object>`，再做目录书签处理与回写。
  - 图片项 `content[0]` 为本地图片绝对路径。
- `ProcessingResult` 原本只包含时间戳字段。
- `OpenDataLoaderPDF.processFile` 原本返回 `void`。
- 项目已依赖 `com.squareup.okhttp3:okhttp-jvm:5.4.0`；`esdk-obs-java` 会再引入 `okhttp`（空 metadata jar），需要显式排除。

## 已实现方案
### 改动 1：新增 `HuaweiObsClient.java`
位置：`java\opendataloader-pdf-core\src\main\java\org\opendataloader\pdf\utils\HuaweiObsClient.java`
- 封装 `ObsClient` 的上传能力。
- 方法签名：
  ```java
  public String uploadFile(String bucketName, String objectKey, File file, String domainName) throws IOException
  ```
- 实现：调用 `obsClient.putObject(bucketName, objectKey, file)`，成功后拼接 `domainName + objectKey` 返回 URL。
- 提供 `close()` 方法释放 OBS 客户端资源。

### 改动 2：新增 `CustomOutputResult.java`
位置：`java\opendataloader-pdf-core\src\main\java\org\opendataloader\pdf\json\CustomOutputResult.java`
- 字段：
  - `jsonUrlOrPath`：主 JSON 的 OSS URL 或本地绝对路径。
  - `ocrJsonLocalPath`：`_ocr.json` 的本地绝对路径。
  - `ossUploadSuccess`：OSS 上传是否成功。

### 改动 3：修改 `JsonWriter.java`
- `writeToCustomJson` 返回类型从 `void` 改为 `CustomOutputResult`。
- 在 `mapper.readValue(...)` 之后新增 OSS 配置解析：
  ```java
  OssUploadConfig ossConfig = OssUploadConfig.fromCustomOptions(config);
  boolean ossEnabled = ossConfig.isEnabled();
  ```
- 新增内部类 `OssUploadConfig`：负责从 `customOptions` 读取并校验 OSS 配置，提取 `pulsarReceiveTopicName` 最后一级。
- 若启用 OSS，调用 `uploadImagesToOssAndUpdateMap(map, obsClient, ossConfig)`：遍历 `data -> items`，对 `item_type == "image"` 的项，把 `content[0]` 本地路径上传到永久桶，并用返回的 URL 替换原路径。
- 目录书签处理与主 JSON 回写保持原逻辑（仍然写本地 `jsonFileName`）。
- 主 JSON 回写后，若启用 OSS：
  - 调用 `obsClient.uploadFile(tempBucket, jsonObjectKey, jsonFile, domainName)` 上传主 JSON，得到 `jsonUrlOrPath`。
  - 调用 `cleanupLocalFiles(outputFolder, inputPDF.getName(), ocrJsonLocalPath)` 清理本地文件，保留 `_ocr.json`。
  - `ossUploadSuccess = true`。
- 若未启用 OSS，`jsonUrlOrPath` 使用本地 `jsonFileName` 的绝对路径。
- 方法最后返回 `new CustomOutputResult(jsonUrlOrPath, ocrJsonLocalPath, ossUploadSuccess)`，并在 `finally` 中关闭 `obsClient`。

### 改动 4：修改 `DocumentProcessor.java`
- `processFileWithResult` 中捕获 `generateCustomOutputs` 返回的 `CustomOutputResult`。
- `ProcessingResult` 构造时传入 `customOutput.getJsonUrlOrPath()` 和 `customOutput.getOcrJsonLocalPath()`。
- 在 `finally` 原有资源释放逻辑之后，增加：
  ```java
  if (customOutput != null && customOutput.isOssUploadSuccess()) {
      // 删除源 PDF
  }
  ```
- 删除失败时记录 `WARNING`，不影响主流程异常。

### 改动 5：修改 `ProcessingResult.java`
- 新增字段 `jsonUrlOrPath`、`ocrJsonLocalPath` 及对应 getter。
- 新增包含这两个字段的构造函数，并保留原有构造函数做兼容转发（旧调用方传入 `null, null`）。

### 改动 6：修改 `OpenDataLoaderPDF.java`
- `processFile(String, Config)` 返回类型从 `void` 改为 `ProcessingResult`。
- 内部改为调用 `DocumentProcessor.processFileWithResult(...)` 并返回结果。

### 改动 7：修改 `DebugSample.java`
- 在 `customOptions` 中填入 OSS 配置示例（含真实 endpoint / bucket / ak / sk）。
- 调用 `OpenDataLoaderPDF.processFile` 后打印返回的 `jsonUrlOrPath` 和 `ocrJsonLocalPath`。

### 改动 8：依赖与配置
- `pom.xml`：新增 `com.huaweicloud:esdk-obs-java:3.24.3`，并排除 `com.squareup.okhttp3:okhttp` 以避免与现有 `okhttp-jvm` 冲突。
- `application-dev.yml` / `application-prepub-sz.yml` / `application-prod-back.yml`：将 `oss.template_bucket_name` 改为 `oss.temp_bucket_name`，与代码读取方式一致。

## 验证结果
- `mvn -pl opendataloader-pdf-core compile -am -DskipTests` BUILD SUCCESS。
- 运行 `mvn test -pl opendataloader-pdf-core` 发现项目当前基线已存在一批失败用例（如 `LineArtProcessorTest`、`AutoTaggerTest`、`ArrowE2ETest`、`IntegrationTest` 等）。
- 通过临时回退 `DocumentProcessor.java` 到 HEAD 验证：`LineArtProcessorTest` 在基线下同样失败，证明这些失败非本次改动引入。
- 失败原因大致分为：
  - 测试断言与当前实现不符（如 `LineArtProcessorTest` 期望合并为 1 个 image 但实际为 0）。
  - 测试依赖不存在的文件路径（如 `ArrowE2ETest` 指向 `D:\Code\JavaCode\opendataloader-pdf\docs\pdf\...`，而当前工作区为 `opendataloader-pdf-parse\opendataloader-pdf`）。
  - `AutoTaggerTest` 因 `config.getOutputFolder()` 为 null 导致 NPE。
- 未运行真实 OBS 端到端验证（需要实际网络与凭证，会实际上传文件）。

## 关键决策（Key Decisions）
- **OSS 配置放在 `customOptions` 中**：与现有 `paddleUrl` 等扩展参数保持一致，不新增 `Config` 字段，最小侵入。
- **返回 `CustomOutputResult` 而非直接改 `ProcessingResult`**：`JsonWriter` 作为底层工具类，返回独立结果对象更内聚；`DocumentProcessor` 再将其合并到 `ProcessingResult`。
- **主 JSON 先写本地再上传**：复用原有 `mapper.writerWithDefaultPrettyPrinter().writeValue(...)` 逻辑，上传后清理本地文件，避免改动主 JSON 生成路径。
- **图片路径替换发生在目录书签处理之前**：确保后续写回主 JSON 的已经是 OSS URL。
- **源 PDF 删除放在 `finally` 中资源释放之后**：避免在 PDDocument 仍打开时尝试删除导致 Windows 锁定失败。
- **排除 `esdk-obs-java` 的 `okhttp` 传递依赖**：项目注释已说明 `okhttp` 是空 metadata jar，真正类在 `okhttp-jvm` 中；不排除会在 classpath 造成冲突。

## 风险与已知限制
- **真实 OBS 端到端未验证**：仅保证编译通过，实际上传、URL 拼接、桶权限等未实测。
- **凭证暴露在 `DebugSample.java` 中**：当前示例代码包含真实 `accessKey` / `secretKey`，提交前应考虑移除或替换为占位符。
- **未配单测**：OSS 配置解析、图片路径替换、本地文件清理、源 PDF 删除等逻辑均无单元测试覆盖。
- **本地清理范围**：`cleanupLocalFiles` 按文件名前缀匹配删除 `outputFolder` 下文件，若多个任务共用同一输出目录可能误删；当前假设每次处理独立目录。
- **`_ocr.json` 不上传**：按当前口径仅保留本地路径，未上传到 OBS。
- **源 PDF 删除不可逆**：一旦 OSS 上传成功即删除源文件，若后续发现解析错误无法复现。
