### 阶段 4：规则选型

用户给的规则本身已经足够精确，方案把它落成两组**可选过滤**（各自"过滤后为空则退回上一步"），
而不是改成硬约束——这样在没有满足条件的命中时行为与旧版**完全一致**，把回归面压到最小：

- **C**（用户原话）：`≥ 原页码` 的命中存在时，丢弃其之前的命中；
- **D**（用户点 4 确认要加）：树按阅读顺序（DFS 先序）遍历，把"已出现的最大**已解析**页码"当 floor
  往下传，`≥ floor` 的命中存在时丢弃其之前的命中，形成"相邻目录条目页码非递减"的一致性校验。

另外还确认了 3 条 UI 细节：升格条目的 `original_page_num` 用**后一条目录条目的页码**；
判据不做更严格；重复的 `(1)~(9)` 消失符合预期。

## 根因

三条根因**互相独立、缺一不可**（只修其中任意一条都得不到正确树）：

1. **无页码的目录行被静默丢弃**（问题 1 的直接原因）
   `extractBookmarksFromJson` / `extractBookmarks` 里，非目录行先累积到 `pendingTitle`，
   遇到目录行时只有 `isJsonContinuation`（同页 + leftX 差 ≤ 2 + 字号同 + 垂直间距 ≤ 18）
   通过才会并入标题，否则 `pendingTitle.setLength(0); pendingLine = null;` **直接丢弃**。
   `董事會函件`（leftX 28.3）与 `緒言`（leftX 56.68）缩进差 28.38 → 既不算续行也没成条目 → 消失。
   （同一个机制也负责丢掉右对齐栏头 `頁次`，那是**正确**行为，必须保留。）

2. **"同前缀运行"把无前缀条目也算成一类前缀，抹平了缩进层级**（问题 2 的**真正主因**）
   `correctLevelsByPrefix` 第 2 步按 `prefixType` 相等切"连续运行"，`null` 也被当成一种类型，
   于是**全部 10 条无编号条目被当成一个运行**，整体被 `modeLevel` 强制成出现最多的层级
   （level2 有 7 条 > level1 有 3 条 → 全部 = 2）；`buildHierarchy` 见"全是 level 2 且没有 L1"，
   就把它们全部塞进 roots。阶段 2 的探针已实测证明（含"补上 `董事會函件` 后仍全部塌成 2"）。

3. **页码解析"取几何最近"，会取到原页码之前的匹配**（问题 3 的直接原因）
   `resolveCatalogBookmarkTarget` 用 `distance = |physicalPage − catalogHint|` 取最小者，
   在整体偏移 +2 的文档里，`股東特別大會`（印刷 6）命中的 p5（距离 1，PREFIX）必然击败
   p8 的真标题（距离 2，EXACT）。

## 修复实施

文件：`java/opendataloader-pdf-core/src/main/java/org/opendataloader/pdf/processors/CatalogBookmarkProcessor.java`

### A. 无页码目录标题升格为条目（两条路径）

在"不构成续行"的分支里，先判定它是否是一个**无页码的段落标题**，是则升格为目录条目，
`original_page_num` 取**紧随其后那一条目录条目的页码**，且必须插在**当前目录条目之前**（保持阅读顺序）。

判据三条同时成立：

1. pending 只有**一行**（`pendingLineCount == 1`，两条路径各自新增该计数）；
2. 紧随的目录行 `leftX` **更深**（更缩进）→ 说明它是一个父节点；这条同时排除 `頁次`
   （458.74 > 28.3，方向相反）；
3. pending 的 `leftX` ≤ 该页目录行的**最小** `leftX`（+容差）→ 排除右对齐栏头（双保险）。

```java
// 1565 行（JSON 路径）/ 1583 行（内容路径，孪生）
private static boolean isJsonPageNumberlessHeading(int pendingLineCount, JsonLineInfo pendingLine,
                                                   JsonLineInfo toc,
                                                   Map<Integer, Double> minTocLeftXByPage) {
    if (pendingLine == null || pendingLineCount != 1) {
        return false;
    }
    double tolerance = CONTINUATION_LEFT_X_DELTA + toc.fontSize * 0.5;
    if (toc.leftX <= pendingLine.leftX + tolerance) {
        return false;                      // 紧随目录行没有更深 ⇒ 不是父节点
    }
    Double pageMinLeftX = minTocLeftXByPage.get(pendingLine.pageIndex);
    return pageMinLeftX != null && pendingLine.leftX <= pageMinLeftX + tolerance;
}
```

配套新增：

- `collectJsonMinTocLeftXByPage`（1504 行）/ `collectMinTocLeftXByPage`（1522 行）：
  每页目录行的最小缩进，供判据 3 使用；
- `buildPageNumberlessHeading`（1615 行）：建 `Bookmark`，`originalPageNum = parseOriginalPageNum(info.rawPage)`、
  `pageNum = resolvePageIndex(...) + 1`（随后仍由 `resolveCatalogBookmarkTargets` 用正文标题纠正）、
  `relatedId` 取目录页那一行的 item id、字号取 pending 行字号（层级聚类要用到）；
- 两处调用点：内容路径 `699 行`、JSON 路径 `1388 行`，都在 `isContinuation` 的 `else if` 分支里。

### B. 无编号前缀条目不参与"同前缀运行"归并

```java
// 1015-1030 行（correctLevelsByPrefix 第 2 步）
int runStart = 0;
for (int i = 1; i <= n; i++) {
    BookmarkPrefixClassifier.PrefixType prev = candidates.get(runStart).prefixType;
    BookmarkPrefixClassifier.PrefixType curr = i < n ? candidates.get(i).prefixType : null;
    boolean prefixlessBoundary = prev == null || curr == null;   // ← 新增
    if (i == n || prefixlessBoundary || !Objects.equals(prev, curr)) {
        int runEnd = i - 1;
        int modeLevel = modeLevel(levels, runStart, runEnd);
        for (int j = runStart; j <= runEnd; j++) {
            levels[j] = modeLevel;
        }
        runStart = i;
    }
}
```

`prefixlessBoundary` 让无编号条目各自成为**单元素运行**（`modeLevel` 对单元素是恒等变换），
等价于完全不参与归并，从而保留 `clusterByLeftX` 的缩进层级。
顺序上也安全：运行在遇到无编号条目时**先关闭**（不影响前面真正的编号运行），无编号条目自身即刻关闭。

### C + D. 页码解析两条可选过滤 + 非递减校验

`resolveCatalogBookmarkTarget` 从"边扫边比"改成"**先收集全部命中，再过滤，再排序取值**"：

```java
// 1805 行起：收集
List<TargetMatch> matches = new ArrayList<>();
for (int pageIndex = 0; pageIndex < data.size(); pageIndex++) {
    ... // 跳过目录页、只取 isParagraphOrHeadingItem，匹配到就 add(new TargetMatch(pageIndex, relatedId, distance, quality))
}
if (matches.isEmpty()) {
    return 0;
}

// Constraint 1: the printed page number is a lower bound.   ← 规则 C
List<TargetMatch> preferred = matchesAtOrAfter(matches, catalogHint);
if (preferred.isEmpty()) {
    preferred = matches;               // 没有"在原页码及其之后"的命中 ⇒ 退回全部（与旧版一致）
}
// Constraint 2: catalog entries never resolve backwards.    ← 规则 D
List<TargetMatch> inOrder = matchesAtOrAfter(preferred, floorPage);
if (!inOrder.isEmpty()) {
    preferred = inOrder;               // 同上，过滤后为空则退回
}

TargetMatch bestMatch = null;
for (TargetMatch match : preferred) {
    if (bestMatch == null || isBetterMatch(match, bestMatch)) {
        bestMatch = match;
    }
}
```

- `isBetterMatch`（1912 行）严格复刻原有排序：**距离 → 更早的物理页 → 更优的匹配质量**（质量只在
  同页时才比较，与旧代码的 `quality.ordinal()` 比较位置一致）；
- `matchesAtOrAfter`（1894 行）：`lowerBoundPage <= 1` 时原样返回（非正/无意义的界不生效）；
- **规则 D 的 floor 只在 DFS 先序里向下传**（`resolveCatalogBookmarkTargets`，1759 行起）：

```java
private static int resolveCatalogBookmarkTargets(..., int floorPage) {
    int highestResolvedPage = 0;
    for (Bookmark bookmark : bookmarks) {
        int resolved = resolveCatalogBookmarkTarget(bookmark, data, catalogStartPage,
            catalogEndPage, Math.max(floorPage, highestResolvedPage));
        if (resolved > highestResolvedPage) {
            highestResolvedPage = resolved;
        }
        if (有子节点) {
            int childHighest = resolveCatalogBookmarkTargets(children, data, catalogStartPage,
                catalogEndPage, Math.max(floorPage, highestResolvedPage));
            highestResolvedPage = Math.max(highestResolvedPage, childHighest);
        }
    }
    return highestResolvedPage;
}
```

**关键取舍**：返回的 `resolved` 只统计**真正命中过正文段落**的节点（`0` = 没解析出来）。
`resolveCatalogBookmarkTarget` 原来失败时会把 `page_num` 留在
`resolvePageIndex(印刷页)+1` 或"目录页页码"这类**回退值**上，如果拿回退值当 floor，
会把后面本来正确的条目一起带偏。
另外，最终仍然违反非递减时**不改结果**，只打一条 INFO：

```
[CatalogBookmark] catalog entry 'X' resolved to page 3, earlier than the preceding entry's page 4
    (no matching paragraph at or after page 4)
```

## 调试方法与踩坑（下次直接复用）

- **反射探针比"复制逻辑到脚本"可靠**：把 JSON 里读出的坐标还原成 `Candidate`，反射调真实的
  `assignLevels` / `clusterByLeftX` / `buildHierarchy` / `matchBookmarkTitle`，
  得到的就是"真实代码跑出来的结论"，而不是推演。
  （`Candidate` 是包级静态嵌套类，`getDeclaredConstructor(...).setAccessible(true)` 即可。）
- **`cmd` 的 `set /p` / `for /f` 读 `cp.txt`（3971 字符单行）会截断（≈1024）**，
  表现为 `javac: 程序包 com.fasterxml.jackson.databind 不存在`——即使 jar 就在 classpath 里。
- **JDK 的 `@argfile` 里 `\` 是转义字符**，`d:\Code\...` 会被吃掉，导致 `ClassNotFoundException`。
- **PowerShell 里 `java -Dfile.encoding=UTF-8 ...` 会被拆成两个参数**（报
  `ClassNotFoundException: /encoding=UTF-8`），改用 `$env:JAVA_TOOL_OPTIONS`。
- **可行做法**（已固化成脚本）：
  ```powershell
  $deps = (Get-Content 'cp.txt' -Raw).Replace("`r", '').Replace("`n", '')
  $env:CLASSPATH = 'tmp_output\probe;java\opendataloader-pdf-core\target\classes;' + $deps
  $env:JAVA_TOOL_OPTIONS = '-Dfile.encoding=UTF-8'
  java org.opendataloader.pdf.DebugSample1
  ```
- PowerShell 的 `>` 重定向写的是 **UTF-16**，python 解析日志文件要按编码回退读取。

## 附带发现与遗留

1. 升格**只对单行 pending 生效**（多行 pending 仍按旧的丢弃处理），已在 `testMultiLineRunAboveIndentedEntries_isNotPromoted`
   里把这条边界固定住。若将来遇到"标题折成两行且无页码"的真案例，需要放开这条判据。
2. 升格条目的 `originalPageNum` 直接取"紧随其后那条目录条目"的页码。若那条也是罗马数字等
   `parseOriginalPageNum` 解析不出整数的值，则 `originalPageNum = 0`、`page_num` 停在目录页页码
   （既有回退行为），**没有做向后查找**。
3. 规则 D 的 floor 会**跨父级累积**（同级条目的已解析最大值 + 子级一起取最大）。对"目录顺序与页码顺序
   不一致"的文档（某些把 `附錄` 排在前面、或节选/合并 PDF），只会在日志里出现 INFO 提示，
   不改变结果（过滤后为空即退回）。
4. 内容路径 `extractCatalogBookmarks` 依旧没有 main 调用方；本次两条路径同步改动，纯粹是为了防止分叉。
5. `bookmarks` 的**来源选择会随目录质量变化**：本次 catalog 从 10 条平级变成 20 条带层级后，
   分数 3.045 > page 2.303，选源由 page 变为 catalog。这类"修好一条导致整体选源切换"的耦合，
   排查时容易被误认为新的回归，值得记住。
