# 2026-11-02 生产 `in-*` / `out-*` 临时目录残留：根因定位与四层清理兜底

## 0. 现象

生产 PDF 解析服务（`opendataloader-pdf-server`）运行一段时间后，pod 内
`/tmp/pdf_parse/` 下堆积 `in-*` 目录、`/tmp/pdf_parse/output/` 下堆积 `out-*` 目录，
磁盘被慢慢吃满。这些目录都是「一条 Pulsar 消息一个」的工作目录，正常情况下
消息处理完就该消失。

配置事实（`application-prod.yml`）：

```yaml
pdf:
  temp:   { path: /tmp/pdf_parse }          # in-* / ocr-*
  output: { path: /tmp/pdf_parse/output }   # out-*
```

## 1. 定位过程（从「谁创建」到「谁可能删不掉」）

### 1.1 全仓只有 5 处创建点

```
PdfProcessService.java:93   Files.createTempDirectory(inputBase,  "in-")    # HTTP 路径
PdfProcessService.java:94   Files.createTempDirectory(outputBase, "out-")   # HTTP 路径
PdfProcessService.java:179  Files.createTempDirectory(outputBase, "out-")   # Pulsar 路径
PulsarService.java:591      Files.createTempDirectory(resolveTempBase(), "in-")   # Pulsar 收消息
PulsarService.java:716      Files.createTempDirectory(resolveTempBase(), "ocr-")  # OCR 回包
```

### 1.2 对应的删除只有三处，且都是「尽力而为」

```java
// PdfProcessService:295 / PulsarService:941（改动前）
try (Stream<Path> paths = Files.walk(dir)) {
    paths.sorted(Comparator.reverseOrder()).forEach(path -> {
        try { Files.deleteIfExists(path); }
        catch (IOException ignored) { }      // ← 静默吞掉
    });
} catch (IOException ignored) { }            // ← 静默吞掉
```

`PulsarService.handleReceiveMessage` / `handleOcrReceiveMessage` 的清理还**不在
`finally` 里**，是方法体最后两行顺序代码。

### 1.3 逐个排除「能正常删」的路径

- 解析成功：HTTP 路径 `finally` 删；Pulsar 路径在 `processForPulsar` 返回后删。可行。
- 解析异常：`catch (Throwable)` 后仍会走到末尾清理。可行。
- 消息被看门狗判定超时：`abandoned` 分支仍会走到末尾清理。**前提是 worker 线程能回来**。

也就是说：**只要进程活着、worker 线程能返回，旧代码是能删的**。残留只可能来自
「线程回不来」或「删了但没删掉」两类。逐条对生产日志/代码确认后得到下面 5 个真实场景。

## 2. 什么情况下删不掉（5 个场景，按生产概率排序）

### 场景 A：进程直接消失，`finally` 根本没跑（最主要）

- K8s OOMKill、节点驱逐、滚动发布 `SIGKILL`、容器运行时重启；
- **本仓自己也会主动制造这种残留**：`PulsarService.escalateIfTooManyAbandoned()`
  到硬阈值时执行 `System.exit(1)`（异常 worker 数 ≥ 2×(count+ocrCount)），
  进程内没有任何 shutdown hook 去清目录。
- 结论：这类残留**在旧结构下 100% 必然发生**，只能靠「下次启动时扫」或外部清理。

### 场景 B：看门狗放弃了 worker，而 worker 是唯一会清理的人

`runWithWatchdog`（`pulsar.consum_timeout_min=15`）超时后：
发失败结果 → ack → `worker.shutdownNow()` → 继续消费下一条。
但 worker 线程可能卡在**不响应中断**的调用里（veraPDF 解码、`HttpClient` socket
读、GC/堆濒临耗尽），Java 无法杀线程。旧代码：

- 看门狗手上**没有目录路径**（`businessIdRef` / `extendRef` 只带业务标识），
  无法代为清理；
- worker 若永远回不来，末尾那两行 `deleteRecursively` 永远不执行；
- worker 还是 daemon 线程，进程退出时也不会等它。

### 场景 C：删除静默失败——一个文件删不掉，整棵子树留下

`out-*` 目录里不是单个文件，是 `<name>.json` + `<name>_images/`（内部还有上百张
png，见 `DocumentProcessor:647-660`）。旧实现：

- `Files.deleteIfExists` 失败只被 `catch (IOException ignored)` 吞掉，**无日志、无重试**；
- 单个 png 删失败 → `xx_images/` 非空删不掉 → `out-*` 非空也删不掉 → 三级全留；
- 触发条件：文件句柄尚未释放（Windows/NFS），只读属性，权限，
  `overlayfs`/`tmpfs` 瞬时 `EBUSY`/`ENOSPC`。

### 场景 D：异常发生在「第二个目录创建」时，第一个漏了

改动前 `PdfProcessService.process()`：

```java
Path inputDir  = Files.createTempDirectory(inputBase, "in-");   // ← 在 try 之外
Path outputDir = Files.createTempDirectory(outputBase, "out-"); // ← 第二个抛异常
try { ... } finally { deleteRecursively(inputDir); ... }
```

`out-` 创建失败（磁盘满 / inode 用尽 / 目录数上限）会直接抛出，`in-` 已经在磁盘上
且**没有任何代码会删它**。

### 场景 E：结果发布抛错，跳过末尾清理

`sendResultMessage` / `acknowledgeQuietly` 内部虽有 `catch (Throwable)`，但清理代码
不在 `finally` 中；只要这两个方法之间出现未被捕获的 `Error`（如 `OutOfMemoryError`），
末尾两行就执行不到。与场景 B 叠加时更明显。

## 3. 修复：四层兜底，任何一层生效都不留目录

新增 `org.opendataloader.pdf.server.workspace` 包（**不要**命名为 `temp` 包：`.gitignore` 第 78 行有 `**/temp/`，会把新代码整体排除在版本控制之外）。

### 3.1 `TempWorkspaces`（注册表 + 可重试删除）

- `create(base, prefix)`：`Files.createTempDirectory` + 登记 `Path -> {prefix, owner thread, createdAt, orphanedAt}`；
- `release(dir)`：删 + 注销。**永不抛异常**，失败时保留登记项并 WARN，交给清扫器重试；
- `deleteRecursively(dir)`：`walkFileTree`（先删文件后删目录），**单个文件失败不再中断整棵树**，
  失败项收集后统一报出；最多 3 次重试，重试前 `setWritable(true)`；最终失败打 WARN 带路径；
- `orphanOwnedBy(thread)`：把某线程创建的目录标记为 orphaned（看门狗放弃该线程时调用）；
- `sweepOrphans(grace)`：删除超过宽限期的 orphaned 目录；
- `sweep(base, prefix, grace)`：扫描 `base` 下**一级**目录，名字前缀匹配 + 空闲超过 grace +
  不属于本 JVM → 删除（上一实例的残留）；
- `releaseAll()`：清空本 JVM 仍持有的目录（shutdown hook / `@PreDestroy`）。

### 3.2 `TempWorkspaceSweeper`（Spring 组件，覆盖进程被杀）

- `@PostConstruct`：注册 JVM shutdown hook（覆盖 `System.exit(1)`）+ 启动 daemon 调度线程，
  **启动即扫一次**（清上一实例残留在同一 `/tmp` 挂载里的目录），之后每 10 分钟一次；
- 扫描范围：`pdf.temp.path` 下的 `in-*`、`ocr-*`；`pdf.output.path` 下的 `out-*`；
- 宽限期：`max(60min, 2 × pulsar.consum_timeout_min)`——保证「仍在处理中的目录」不会被误删；
- 删除动作一律打 WARN（`swept stale temp directory ...`），便于 Kibana 计数与告警；
- `@PreDestroy`：停调度 + 再清一次。
- 调度任务整体 `catch (Throwable)`，否则一次异常会让 `scheduleWithFixedDelay` 永久停摆。

### 3.3 调用点改造

| 位置 | 改动 |
| --- | --- |
| `PdfProcessService.process` | 两个目录都移进 `try` 内创建（修场景 D）；`finally` 改 `TempWorkspaces.release` |
| `PdfProcessService.processForPulsar` | `create/release` 走 `TempWorkspaces`（成功时仍交回调用方，其路径已登记） |
| `PulsarService.handleReceiveMessage` | ack/发布 + 清理包进 `try { ... } finally { release(out); release(in); }`（修场景 E） |
| `PulsarService.handleOcrReceiveMessage` | 同上（`ocr-*`） |
| `PulsarService.onMessageTimeout` | `worker.shutdownNow()` 后 `TempWorkspaces.orphanOwnedBy(workerThread)`（修场景 B） |
| `PulsarService.newWorkerExecutor` | 通过 `AtomicReference<Thread>` 暴露 worker 线程引用，供上面的孤儿标记使用 |
| 两处旧 `deleteRecursively` | 删除，统一走 `TempWorkspaces` |

`PdfProcessService` 新增 `inputBaseDir()` / `outputBaseDir()`，让清扫器与业务共用同一套
「配置为空则回退 `java.io.tmpdir`」的解析逻辑，避免两边算出不同基目录。

## 5. 影响面

- 只动 `opendataloader-pdf-server`，**core 零改动**，解析结果不带任何变化（同一样本 JSON 内容不变，本改动只碰目录生命周期）。
- 行为变化：
  1. 启动时会创建 `pdf.temp.path` / `pdf.output.path`（之前是首个请求时创建）；
  2. 启动后立刻扫描并删除**超过 60 分钟未变动**的 `in-*`/`ocr-*`/`out-*`——即历史残留，属预期行为；
  3. 新增一条 daemon 线程 `temp-workspace-sweeper`（每 10 分钟一次目录列举，开销可忽略）；
  4. 删除失败不再静默：日志新增 `could not be deleted on release` / `swept stale temp directory` /
     `handed N temp directories of the abandoned worker` 三个关键字。
- 不做的事：不动 `pulsar.consum_timeout_min`、不改 ack 语义、不引入新的 yml 开关（默认值即生产所需）。

## 6. 现网补救（本次发版前可先手动止血）

```bash
# 先看规模，别直接删
du -sh /tmp/pdf_parse /tmp/pdf_parse/output 2>/dev/null
find /tmp/pdf_parse -maxdepth 1 -type d -name 'in-*'  | wc -l
find /tmp/pdf_parse/output -maxdepth 1 -type d -name 'out-*' | wc -l
ls -ld --time-style=+%F_%T /tmp/pdf_parse/in-* 2>/dev/null | tail -5

# 只清「2 小时没动过」的，正在处理的目录不动
find /tmp/pdf_parse        -maxdepth 1 -type d \( -name 'in-*'  -o -name 'ocr-*' \) -mmin +120 -exec rm -rf {} +
find /tmp/pdf_parse/output -maxdepth 1 -type d -name 'out-*' -mmin +120 -exec rm -rf {} +
```

发版后建议：

- Kibana 对 `swept stale temp directory` 与 `could not be deleted on release` 建告警——
  前者出现说明还有别的残留源，后者说明文件系统层面删不掉（句柄/权限/NFS）；
- 若 `/tmp` 未做容量隔离，建议把 `/tmp/pdf_parse` 挂成 `emptyDir: { sizeLimit: ... }`，
  这样 pod 重建即回收，磁盘不会被无限吃；
- 磁盘水位告警阈值按「单文档 `out-*` ≈ 几十 MB（图片多时上百 MB）」估算。

## 7. 踩坑与经验

- 旧 `deleteRecursively` 用的是 `Files.walk(...).sorted(reverseOrder())`，**顺序本身是对的**，
  坑在于「单个失败被吞 + 父目录随后必然非空失败」，所以看起来像「顺序 bug」，其实是**吞异常**。
  改成 `walkFileTree` 收集失败再统一报，才能定位到底是哪个文件删不掉。
- 看门狗线程**拿不到**目录路径是本次最关键的结构缺陷：清理责任绑在「会消失的 worker」身上。
  修复办法不是猜路径，而是在创建时登记 owner 线程，按线程做所有权转移。
- 清扫器必须按「目录名 + 空闲时长」判活，不能只看「在不在登记表」：进程重启后登记表是空的，
  而磁盘上的残留恰恰全都不在登记表里。
- 若将来多个 pod 共享同一个 `pdf.temp.path` 卷，60 分钟宽限期是唯一保护；改成共享卷需重新评估。
- **本仓 `.gitignore` 第 78 行是 `**/temp/`**：新建 `server/temp` 包时 `git status` 里完全看不到文件，
  极易提交时漏掉。所以落点选 `server/workspace`。（`git check-ignore -v <path>` 可自查）
