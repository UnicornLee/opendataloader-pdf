## 1. 现象

Stage 1 之后，去旋转正文的页框已被"渲染宽自适应"加宽以吸收浏览器重排溢出，但实测：

| 页 | 页宽 width | margin_right（修复前） | 正文框右缘 x1 |
|---|---|---|---|
| 93 | 1055.6 | **344.6** | 711（=PDF 压缩 advance） |
| 94 | 1524.7 | **804.1** | 720 |

用户直观感受：右侧一大片空白。

---

## 2. 结论速览（TL;DR）

1. **估算偏高只是表象之一**：逐字符估宽用 `fontSize = rightX - leftX`（行墨迹厚度，含上升/下降部与行距，约为真实字宽的 1.2–1.4×），把"最宽行"放大（p94 达阅读长度的 ~2×），页框被开得过大。**已用比例钳制**（`MAX_RENDER_WIDTH_RATIO=1.2`）压回。
2. **真正的根因是页框与正文框不同步**：加宽的只是**页面**，而每条正文的框体（chunk / 由 ParagraphProcessor 聚合的行、段落）宽度仍是 PDF 压缩后的阅读 advance（~640pt）。文字在 640 的窄框内换行/占位，页面"多出来"的宽度对文字而言是不可用的**死白**，全部堆到右侧。
3. **修复**：让**正文框随页框按同一比例横向拉伸**——`readingScale = contentWidth / readingLength`，在 `derotate` 里把阅读轴 X（leftX/rightX/textStart/textEnd/symbolEnds）统一乘 scale。正文填满加宽区域后，右侧只剩按设计保留的页边距。
4. **不影响阅读顺序与纵向布局**：scale 只沿 X 摊开字形，纵向堆叠（stackOffset）与 topY 降序读序均不变。

---

## 3. 完整定位过程（从现象到根因）

### 3.1 第一层：先怀疑估算本身过宽（比例钳制）
读 `estimateMaxRenderedWidth`：逐字符估宽 `fontSize*(isFullWidth?1.0:0.5)`，其中 `fontSize=|rightX-leftX|` 是行墨迹厚度，非真实字宽，且 0.5em 对密集数字列偏大 → 最宽行被显著高估。
处理：新增常量 `MAX_RENDER_WIDTH_RATIO=1.2`，`contentWidth = Math.min(Math.max(readingLength, estimatedWidth), readingLength * MAX_RENDER_WIDTH_RATIO)`。
端到端复测：margin_right 345→245、804→322。确有收窄，**但右侧空白仍明显** → 说明估宽只是次要因素，另有主因。

### 3.2 第二层（决定性）：页框宽 ≠ 正文框宽
比对该页 items 的 `x1`：正文条目右缘始终是 **711 / 720**（= PDF 压缩阅读 advance），与页面被加宽到的 1055 / 1524 无关。
再看渲染模板 `announcementAnalysis.html`：`.page-item` 以 `marginLeft:x0` 左对齐、内容 `white-space:pre-wrap`。→ 文字被限制在**条目自身宽度（~640）**内，页框加宽并不给文字更多可占用的盒宽，于是页框多出的横向空间成为纯死白，堆在正文框右侧。
**根因确认：只加宽页面而不加宽正文框体，等于凭空造右侧留白。**

### 3.3 修复：正文框随页框同步拉伸
在 `processRotation` 计算 `readingScale = contentWidth / readingLength`（1.0–1.2），透传进 `derotate`，把去旋转后每个 chunk 的阅读轴坐标整体按 scale 缩放：
- CCW(+90)：`newLeftX=(bottomY-ry0)*scale+xOffset`、`newRightX=(topY-ry0)*scale+xOffset`、textStart/textEnd/symbolEnd 同理；
- CW(−90)：`newLeftX=(ry1-topY)*scale+xOffset` …；
纵向（stacking axis Y）不变，仍用 `stackOffset=ry1-(rx1-rx0)` 锚回原页顶。
因正文框体来自 chunk 几何，拉伸 chunk X 会自然传导到行 / 段落框宽 → HTML 条目盒随之变宽 → 文字填满 → 死白消除。

---

## 4. 根因归纳

| 层次 | 事实 | 定性 |
|---|---|---|
| 估宽 | `fontSize=rightX-leftX` 是行墨迹厚度，逐字符累加高估最宽行达 ~2× | 次要：已比例钳制 1.2 |
| 页框 vs 正文框 | 仅加宽 page，正文 chunk/行/段落框仍 = 压缩 advance(~640) | **主因**：多出的页宽文字用不到 → 右侧死白 |
| 渲染盒 | `.page-item` 宽取条目 `list.width`，左对齐 + pre-wrap | 佐证：条目不拉伸则死白必然出现 |
| 拉伸方案 | `readingScale` 沿阅读轴 X 缩放 chunk 坐标 | 页框与正文框同步，死白收敛为设计边距 |

## 5. 验证（真实 PDF 第 93/94 页，编译 + 端到端运行 exit 0）

| 页 | width | 正文框右缘 x1（拉伸前→后） | margin_right（初→钳制→拉伸后） |
|---|---|---|---|
| 93 | 956.6 | 711 → **839** | 344.6 → 245.5 → **117.4** |
| 94 | 1042.3 | 720 → **849** | 804.1 → 321.8 → **192.5** |

- 正文框填满加宽区后，右侧仅余"页设计右边距"（`pageWidth − rx1`）：p93=117、p94=192。
- p94 边距偏大是因其旋转区在竖排页里本就靠左（`rx1≈402`），属设计边距而非死白。
- 423 页仅 2 页被处理，其余零改动（`MIN_ROTATED_CHUNKS=8` 门槛）。

可调项：`MAX_RENDER_WIDTH_RATIO`（现 1.2）；若要 p94 边距更对称可把 `rightMargin` 设为 `min(pageWidth−rx1, leftMargin)`。

## 6. 任务二：JSON 保存原始坐标与旋转角度（实现 → 符号纠偏 → 回退）

用户随后要求"在最终 JSON 中保存原始坐标和旋转角度，像这种情况旋转角度为 -90"。已实现并验证，**但用户最终要求回退该任务全部代码**，故当前生产状态**不含**此特性。过程记录如下，供后续如需重启时复用。

### 6.1 实现（页面级）
- `RotationProcessor.processRotation` 在改写坐标**前**采样旋转区原始包围盒 `(rx0,ry0,rx1,ry1)`，返回值扩展为 `{width, height, rx0, ry0, rx1, ry1, angle}`。
- `DocumentProcessor` 登记表 `rotatedPageWidths(Map<Integer,Double>)` 升级为 `rotatedPageMeta(Map<Integer,double[]>)`，新增 `getRotatedPageMeta()`。
- `JsonName` 新增 `ROTATION_ANGLE="rotation_angle"`、`ORIGINAL_BBOX="original_bbox"`。
- `JsonWriter.writePageToGenerator`：用同一份 meta 驱动加宽页宽，并输出 `rotation_angle` 与 `original_bbox`（Y 按 `height−y` 翻转为左上原点，与条目坐标同约定）。

### 6.2 符号纠偏（重要）
首版把 `angle = counterClockwise ? 90 : -90`，实测输出 **+90**，与用户预期 **-90** 相反。根因：veraPDF 的 `slantDegree`（本例正文≈+90，bottom-up）与用户采用的"页面旋转方向"约定符号相反（用户把逆时针记为负）。
修正为 `angle = counterClockwise ? -90 : 90`，实测两页均输出 `-90.0`，符合预期。原始框示例：p93 `original_bbox=[70.4, 76.5, 477.9, 717.2]`。

### 6.3 回退
用户要求回退。已对 4 个文件精确逆向：`JsonName` 删两常量；`RotationProcessor` 返回值恢复 `{width,height}`、删 angle 与 javadoc；`DocumentProcessor` 恢复 `rotatedPageWidths`、删 `getRotatedPageMeta`；`JsonWriter` 恢复 `getRotatedPageWidth()`、删两字段输出块。回退后编译 exit 0，任务一的拉伸成果保持不变。同步删除两条相关长期记忆。

## 7. 经验教训

1. **"加宽容器"必须与"加宽内容盒"配套。** 只放大页面而条目盒仍是源几何，多出的宽度文字用不到，反而制造留白。判断依据：对比页面 width 与条目 `x1`——若 x1 恒定不随页面变，即说明内容盒未参与拉伸。
2. **坐标拉伸只沿阅读轴、且几何要传导到聚合层。** 用统一 `readingScale` 缩放 chunk 的 X，可经由 ParagraphProcessor 自然传导为行/段落框宽，无需在序列化层特殊处理。纵向锚定（stackOffset）与读序（topY 降序）保持独立不受影响。
3. **估算类"保守偏大"要先量化再钳制。** 逐字估宽的行墨迹厚度法天然偏高，宜设比例上限（clamp）而非全量采用。
4. **旋转角度符号要先对齐用户/业务约定，不能照搬内部几何量。** veraPDF `slantDegree` 的符号与"页面旋转方向"约定相反；输出前以"逆时针记为 -90"这类明确预期校验。
5. **临时特性要可精确回退。** 实现时保持改动集中、逆向清晰（本例 4 文件一次回退到位），避免与既有必要改动混淆。
