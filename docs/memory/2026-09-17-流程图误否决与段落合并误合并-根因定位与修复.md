**Step 6｜追到"为什么算正文"**：`containsBodyText` → `isBodyTextBlock` → `isDiagramLabel`：

**Step 7｜找到真正的矛盾点**：收集阶段其实**已经正确排除**了它
（`collectOverlappingContents` 里 `proseBlocks.contains(content) || isBodyTextBlock(content) → continue`），
但 9/16 新增的 `absorbInteriorText`（B3："图内文本只留截图"）**只判"是否完全落在 region 内"**，又把它吸收了回来：

```java

mergedCluster = absorbInteriorText(mergedCluster, mergedShapes, pageContents);   // 吸收图内文本
...

```

**即：吸收它的理由（图内标签）和否决它的理由（像正文）是同一个。**

### 修复

把 `containsBodyText` 从 `isFlowchartCluster` 里**移到 `processFlowchartGroups` 中 `dropBodyTextBlocks` 之后、`absorbInteriorText` 之前**：

```java
Cluster mergedCluster = dropBodyTextBlocks(new Cluster(mergedShapes, mergedContents, mergedBox), mergedShapes, proseBlocks);
if (coversWholePage(mergedCluster.boundingBox, pageBox)) { continue; }
// 正文保护必须在吸收之前判定：吸收本就会把"被收集阶段当作正文跳过"的短块拿回来
if (containsBodyText(mergedCluster)) { continue; }
mergedCluster = absorbInteriorText(mergedCluster, mergedShapes, pageContents);
...
if (isFlowchartCluster(mergedCluster)) { ... }      // 不再检查 bodyText
```

收集阶段与 `dropBodyTextBlocks` 已保证真正文进不了 region，因此"吞正文"的保护并未削弱。

## 问题 ③：第 248 页 3 个"单位：万元"挤成一个段落

### 现象

第 248 页有 **4 个表格**，每个表格右上方各有一个"单位：万元"。解析结果：

```
[452.98,132.19,505.66,142.75]   单位：万元                              ← 第 1 个正常
[452.98,290.74,505.66,618.48]   单位：万元 + 单位：万元 + 单位：万元      ← 后 3 个并成 1 个段落（跨 327.7pt）
```

### 定位过程

**Step 1｜插桩 `ParagraphProcessor`**（`-DdbgParagraph=1`）：

- 在 `processParagraphs(contents, width)` 的 8 个检测步骤后各加一次 `dbgUnits(blocks, step)`，
  打印"含`单位：万元`的 block 的行数/上下边界/各行 topY"；
- 在 `getDifferentLinesProbability` 外包一层打印，输出返回值与输入参数。

**Step 2｜定位到步骤**：

```
[PARA] step=justify lines=3 top=551.2 bottom=223.4 align=LEFT
       [单位：万元@551.2][单位：万元@392.5][单位：万元@234.0]
```

→ **第一步 `detectParagraphsWithJustifyAlignments` 之后就已经是 3 行了**。

**Step 3｜发现"概率判据"被短路**：

```
[PARA-PROB] result=0.0  leading=0.0  prevBase=700.66 nextBase=542.11 font=10.56 page=247
[PARA-PROB] result=0.0  leading=0.0  prevBase=542.11 nextBase=383.45 font=10.56 page=247
[PARA-PROB] result=1.0  leading=0.0  prevLines=2  nextBase=224.93 font=10.56 page=247
```

- 行距/字号 = `158.55 / 10.56 ≈ 15 倍`，远超 veraPDF `DATA_LOADER_DEFAULT_FONT_LEADING_INTERVAL = {0.7, 2.2}` →
  `mergeLeadingProbability` 返回 0（第一条、第二条 `result=0.0` 印证）；
- **但合并照样发生了** → 说明合并走的是**另一条路径**（`prejudgeParagraphs` 先返回 `true`，短路了后面的 probability 分支）。

**Step 4｜找到兜底分支**（问题真正的根因）：

```java
// ParagraphProcessor.prejudgeParagraphs(...)
} else if ((Math.abs(prevLastLineRightX - rightX) < 5 || width / 2 - (prevLastLineLeftX + prevLastLineRightX) / 2 < 10) &&
    prevLastLineLeftX - nextFirstLineLeftX > -5 && prevLastLineLeftX - nextFirstLineLeftX < MAX_PARAGRAPH_BEGINNING_INDENT) {
    if (rightX - nextFirstLineRightX > 20 && ...) { newBlocks.add(nextBlock); }
    else if (nextTwoFontSize != null && nextMargin != null && nextTwoLeftX != null &&
        Math.abs(nextFontSize - nextTwoFontSize) < 2 && Math.abs(margin - nextMargin) < 5 && nextFirstLineLeftX - nextTwoLeftX > 10) {
        newBlocks.add(nextBlock);
    } else if (BulletedParagraphUtils.isLabeledLine(nextBlock.getFirstLine())) { newBlocks.add(nextBlock); }
    else {
        previousBlock.add(nextBlock.getLines());      // ★ 兜底：直接合并，无任何绝对行距上限
        previousBlock.setTextAlignment(TextAlignment.LEFT);
    }
    hasJudge = true;
}
```

对"单位：万元"逐条命中：
- 右边界 ≈ 页面标准右边距（4 条完全同 x 452.98–505.66）✓
- 与下一行左缩进接近（差 0）✓
- 内层第 1 条要求"下一行有 `>10` 的缩进" ✗；不是列表标签 ✗
- → **落入 else 兜底合并**

**关键**：那条 `Math.abs(margin - nextMargin) < 5` 是"两段间距彼此一致"——
4 个表格间距恰好均匀（158.55 / 158.5 / 158.6），**"间距稳定"反而成了合并的理由**。

### 修复（同时落实用户追加的要求）

用户追加口径：**"如果两行之间有表格或图片，也是需要开始新的段落的。"**

1. **分隔符范围扩展**（`processParagraphs(contents, width)`）：

```java
List<IObject> separators = new ArrayList<>();
for (IObject content : contents) {
    if (content instanceof TextLine) { blocks.add(new TextBlock((TextLine) content)); }
    // 任何非文本内容都会把页面视觉上切开：装饰线、表格、图片
    if (content instanceof LineArtChunk || content instanceof TableBorder
            || content instanceof Table || content instanceof ImageChunk) {
        separators.add(content);
    }
}
```

`hasLineArtBetween` 相应改名 `hasSeparatorBetween`、参数类型 `List<IObject>`（10 处方法参数同步改名 `lineArts` → `separators`）。

2. **绝对行距上限**：

```java
private static final double MAX_LINE_SPACING_RATIO = 3.0;
...
// 放在 prejudgeParagraphs 判据链最前面
if (prevFontSize > 0 && margin > MAX_LINE_SPACING_RATIO * prevFontSize) {
    newBlocks.add(nextBlock);
    hasJudge = true;
    return hasJudge;
}
```

（段内行距通常 1.2–1.5 倍字号、跨段约 2 倍；本例 15 倍，会被干净挡住。）

## 问题 ③'：段落修复把第 248 页"整页"送进了截图

修完段落判据再跑，第 248 页从"4 个表格"变成了**一张整页图**：

```

```

### 定位过程（用户追问"改的是段落识别，为什么会影响到截图？"）

用 `git stash push -- <ParagraphProcessor.java>` **只回退这一个文件**，配合 `FlowchartProcessor` 插桩跑两次对照：

**第一环：flowchart 的输入就是段落对象**
`findProseBlocks(pageContents)` 与 `isDiagramLabel(...)` 处理的 `CustomSemanticParagraph`，正是 `ParagraphProcessor` 的产物。

**第二环：真正的开关是"段落高度"**（`LABEL_MAX_HEIGHT = 12.0pt`）

| | 改动前 | 改动后 |
|---|---|---|
| 后 3 个"单位：万元" | 合并成**一个高 326pt 的段落** | **各自独立**，高 10.5pt |
| 判定 | `isBodyTextBlock=true` → **被 flowchart 排除** | `isDiagramLabel=true` → **被 flowchart 收进 cluster** |

**第三环：收集 → cluster 膨胀**（那些标签离相邻表框只有 1.5pt，在 `COLLECTION_MARGIN=2.0` 内，
一旦被收集，就通过"生长一步"把相邻表格的 shape 组连锁并入）

| cluster[0] | 改动前 | 改动后 |
|---|---|---|
| box | `[88.5, 552.7, 516.4, 709.7]`（只包 1 个表格） | `[88.5, 76.8, 516.4, 709.7]`（整页） |
| shapes | 14 | 56 |
| table | 1 | 13 |
| **`regularTable`** | **true → 否决** ✓ | **false → 通过 → 截图** ✗ |

**第四环：表格判据失效** —— `isRegularTable` 用的是 `maxTableArea / clusterArea`（最大**单**表面积 ÷ cluster 面积）：
cluster 只包 1 个表格时是 1.0 → 判表格；膨胀到 4 个表格 + 全页后，最大单表占比只剩 ~0.22 < 0.3 → 判"不是表格"。

**结论**：之前是靠那个"错误的大段落"（高 326pt）意外挡住了 flowchart；
段落修好之后，这层偶然遮挡消失，暴露的是 flowchart 缺少"cluster 跨多个表格 / 覆盖整页"的护栏。

### 修复

`MAX_CLUSTER_PAGE_AREA_RATIO`：**0.7 → 0.5**

```java
/**
 * A cluster covering more than this share of the page is a page-level region — a table
 * block, a background frame or a full-page decoration — and is never cropped. ...
 * Measured values: a 4-table page reaches 0.55 while genuine diagrams stay low
 * (0.215 for the mid-page organisation chart, 0.047 for the page-83 chart).
 */
private static final double MAX_CLUSTER_PAGE_AREA_RATIO = 0.5;
```

（未采用"表格总面积/cluster 面积"的方案 C：第 7 页中部图有 6 个表格碎片，总面积占比可能超阈值而误伤。）

## 观测手法（可复用）

1. **单页 PDF 加速 A/B**：`docs/pdf/<name>-83(流程图).pdf` 这类单页抽取把一次实验从 ~2 分钟降到 ~15 秒；
   插桩开关用 0-based 页码参数（`-DdbgFlowPage=<n>`）避免全文档刷屏。
2. **分层插桩**：先在 `DocumentProcessor` 打印"这一页有哪些类型/几组 shape"（宏观），
   再在 `FlowchartProcessor` 打印每组 shape 明细（中观），最后打印判定各条件（微观）——
   三层定位比一次全打省很多轮次。
3. **单文件回退做 A/B**：`git stash push -- <单个文件>` 可以在不动其它未提交改动的前提下跑对照，完事 `git stash pop`。
4. **注意 PowerShell 陷阱**：`Out-File` 默认 80 列会截断长日志，必须 `-Width 100000`；
   java 输出的中文经管道会变 GBK 乱码，日志分析脚本**写文件再用 read_file 读**，不要直接 print 到控制台。
5. **回归产物完整性先校验**：`ProcessingDeadline` 超时会留下不完整 digest，先比文件大小/行数再看内容。
