### 阶段 4：锁定"内容为什么会丢"

1. **`processHorizontalLines`（`TableBorder.java:348`）** 用横线的 `lastColNumber = getCoordinateX(line.getRightX())`
   决定把哪些列的 `rowSpan` 置 1：

   ```java
   int lastColNumber = getCoordinateX(line.getRightX());
   if (rowNumber != -1 && firstColNumber != -1 && lastColNumber != -1) {
       if (rowNumber > 0 && rowNumber < numberOfRows) {
           for (int colNumber = firstColNumber; colNumber < lastColNumber; colNumber++) {
               rows[rowNumber - 1].cells[colNumber].rowSpan = 1;
           }
       }
   ```

   数据行横线右端 540.220 → `lastColNumber = 4` → **只把 `cells[3].rowSpan` 置 1，`cells[4].rowSpan` 从未被切**
   （表头下边界里那段 `541.420–547.200` 才覆盖 col4，但它作用在 `rows[0]` 上）。
   `processMergedCells` 的第一段还会把"最后一列"的 rowSpan 从下往上累积，于是 r1 的 `cells[4].rowSpan = 13`。

2. **`processMergedCells`（`TableBorder.java:437`）的"跨度对齐"分支**：对 r1 的 col3，
   `cells[3]`（rs=1, cs=2）与 `cells[4]`（rs=13, cs=1）的"行覆盖终点"不一致（2 vs 14）→ 走 `else`（badCell）：

   ```java
   rows[rowNumber].cells[colNumber + 1].setRowSpan(rows[rowNumber].cells[colNumber].rowSpan);
   rows[rowNumber].cells[colNumber].setColSpan(rows[rowNumber].cells[colNumber + 1].colSpan);
   rows[rowNumber].cells[colNumber].setColNumber(rows[rowNumber].cells[colNumber + 1].colNumber);  // ← 罪魁
   ```

   → **`cells[3].colNumber` 被改写成 4**，`colSpan` 也被缩成 1。
   （r0 与 r13 不触发：r0 的 `cells[4].rowSpan` 被表头下边界的 col4 段切成 1；r13 的 `cells[4].rowSpan` 初值就是 1。
   这正是"只有第 2~13 行错"的原因。）

3. **输出层两个连带后果**：
   - `createMatrix` 只为 `cell.colNumber == 列号 && cell.rowNumber == 行号` 的格子设置 bbox
     → `cells[3]`（colNumber 已变成 4）**bbox 永远没被设置**，这就是 JSON 里那个 `x0=1.797e308` 的空格；
   - `JsonWriter`（`JsonWriter.java:1033-1090`）按 `cumulativeColSpans` 步进输出、取文本时用
     `rows[cell.rowNumber + n].cells[cell.colNumber + k]` → 对 `cells[3]` 取到的是 `rows[1].cells[4]`（空）
     → **数值内容丢失**；随后还输出独立的 `cells[4]`（540.34–546.484 空格）。

内容归属也验证过：`getTableBorderCells` 里 `getClosestLeftX(500)=3`、`getClosestRightX(537.4)=4` → 数值只落进 `cells[3]`。

## 根因

**这份 PDF 的表格"表头行比数据行宽"，数据行（含底边）的横线只画到 x=540.220，而表头的横线画到 x=547.204，
右侧又没有贯穿竖线封口。** 由此：

1. `TableBorder` 按顶点聚类出 5 列（多出 col4 = 540.34–546.484）；
2. 数据行横线的 `lastColNumber = 4` → `cells[4].rowSpan` 从未被切分；
3. `processMergedCells` 的"跨度对齐"判定 `cells[3]`(rs1,cs2) 与 `cells[4]`(rs13,cs1) 冲突，
   执行 `setColNumber(4)` 把 `cells[3]` 的列号改写 → `createMatrix` 不给它设 bbox、`JsonWriter` 取不到它的内容
   → **数值丢失 + 多出一个空第 5 列**。

## 修复实施（用户给定的方案）

### 用户给的规则（已逐条确认理解）

1. "右侧没有闭合竖线"**按整张表**判断，不逐行；
2. 竖线要算"有效边框"，必须**在它所覆盖的每一行上跨度 ≥ 该行高度的 2/3**（碎片不算）；
3. "右侧没有闭合竖线"的判据 = `右侧横线右端的最小值 − 整表最右侧有效竖线 x > 10pt`；
4. 满足 1~3 时，把**每条右端距表格右边界 < 10pt 的横线**延长到表格最右端。

### 改动

`veraPDF-wcag-algs/src/main/java/org/verapdf/wcag/algorithms/entities/tables/tableBorders/TableBorder.java`（+108 / −1）

新增常量：

```java
private static final double RIGHT_EDGE_EXTENSION_GAP = 10.0;
private static final double MIN_VERTICAL_LINE_ROW_COVERAGE = 2.0 / 3.0;
```

构造函数顺序改为 **Y → 补齐横线 → X**：

```java
public TableBorder(TableBorderBuilder builder) {
    super(new BoundingBox(builder.getBoundingBox()));
    // Row coordinates are computed first because extending the short right horizontal borders
    // needs the row heights to tell real vertical borders from leftover stubs.
    calculateYCoordinates(builder);
    extendShortRightHorizontalLines(builder);
    calculateXCoordinates(builder);
    createMatrix(builder);
    setRecognizedStructureId(StaticContainers.getNextID());
}
```

新增 `extendShortRightHorizontalLines(TableBorderBuilder)`（挑出 `0 < rightEdgeX − line.getRightX() < 10`
的横线段、判定右侧无闭合竖线、延长到 `rightEdgeX`）与 `isVerticalLineCoveringRows(LineChunk)`。

### 两个必须记住的实现坑

1. **有效竖线判定不能用 bounding box。**
   最初用 `verticalLine.getTopY()/getBottomY()` 与 `getTopY(row)/getBottomY(row)` 求交叠，因两者都含半线宽，
   竖线会"擦到"相邻行（交叠 0.72pt vs 行高 18.36pt），于是**每条竖线都因"某一行覆盖不足"被判成碎片**，
   `rightmostVerticalX` 恒为空、延长根本不触发。改用
   - 竖线用端点：`Math.max(line.getStartY(), line.getEndY())` / `min(...)`
   - 行边界用中心：`yCoordinates.get(rowNumber)` / `yCoordinates.get(rowNumber + 1)`

   之后正常（`rightmostVerticalX = 455.14`）。

2. **重建横线必须用 `LineChunk.createLineChunk(..., LineChunk.BUTT_CAP_STYLE, color)`，不能直接 `new LineChunk(...)`。**
   `ChunkParser.transformLineChunk` 走的是 `createLineChunk`，它会把端点**内缩半个线宽**，所以原始线的
   `getLeftX()/getRightX()`（`BaseObject` 委托 `boundingBox`）恰好等于端点；而直接 `new LineChunk` 会让 bbox
   **外扩半个线宽** → `getRightX()` 变成 `547.204 + 0.24 = 547.444`，越过最后一个边界带
   `[545.764, 547.204]` → `getCoordinateX` 返回 **-1** → **整条横线被 `processHorizontalLines` 整条忽略**。
   症状极具迷惑性：所有行边界都不生效，整列被当成跨行合并，13 个数值全挤进一格，输出形如 `R14C1`

   ```
   r0: [… 'Opening balance after the adjustment278,873,873.56 / 752,464,775.39 / … / 13,465,325.20']
   r1~r13: 只剩 3 格
   ```

## 附带发现与遗留

1. **内部仍是 5 列**：延长后 `xCoordinates` 里 `540.34` 这个边界**依然存在**（因为 y=313.490 上还留着一个
   `0.48×0.48` 的小方块和两条 0.24/0.48pt 的短竖线碎片，它们贡献了 540~541 附近的顶点簇）。
   只是 col4 不再被任何 cell 指向、被 `detectRedundantColumns` 删掉，**输出完全正确**。
   如果希望内部也严格变成 4 列，需要另外处理那几个小图形（本次未做）。
2. **阈值 10pt 的取舍**：意味着"数据行右端与表头右端差 <10pt 就视为同一右边界"。风险是表格在数据行右侧
   真的有一个 <10pt 的独立窄列时会被并进来（现实中 ≈3.5mm 的列几乎没有）。
3. **`processMergedCells` 的 badCell 分支会改写 `colNumber`**：`setColNumber(...)` 会让格子"身份"与它在矩阵中的
   位置脱节，进而引发 bbox 未初始化 + 内容取不到。本轮是用"上游把横线补齐"绕开了它，**没有动那段通用逻辑**；
   如果以后还有别的文档出现"格子内容莫名消失 + JSON 里有 `x0=1.797e308` 的空格"，可以优先怀疑这里。
4. **`getLeftX()/getRightX()` 的线宽语义**（本轮踩坑，值得记住）：经 `ChunkParser.transformLineChunk` →
   `createLineChunk(BUTT_CAP_STYLE)` 处理的线，端点是内缩过的，bbox 恰好等于端点；而任何"手工 `new LineChunk`"
   都会让 bbox 外扩半线宽。凡是要拿 `getRightX()/getLeftX()` 去和坐标带比较的地方都要注意这个差异。
