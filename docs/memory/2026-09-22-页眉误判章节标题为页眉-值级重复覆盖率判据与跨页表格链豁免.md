# 2026-09-22 — 章节标题被误判为页眉：值级重复覆盖率判据 + 跨页表格链豁免 + previous_table 字段

## 任务背景（Goal）

用户提出：`docs/pdf/201501131782598903817032205.pdf`（長江和記實業/長江實業 2015 年港股招股书，193 页）
**页面最上面两条横线之间的内容不应判定为页眉**。理由：该内容是**章节标题**，最多在连续几页内相同，
并不是"大多数页都一样"。

同时用户明确两点附加要求：

1. 章节标题不再算页眉后，不要把跨页表格的 `previousTable` 链打断（为"页面顶部的标题"加豁免）；
2. 顺便把 `previousTable` 输出到 JSON，字段名 `previous_table`，值为 `true`/`false`；
3. 注意是否引入性能问题。

约定：先给方案、用户同意后才改代码（本次已获同意：**方案 A + 阈值 50%**）。

## 一、版面事实（pdfplumber 实测）

## 二、问题现象（改动前实测输出）

`DebugSample` 跑出的 `201501131782598903817032205.json`：

- 横线之上的警告文字（192/193 页）、页脚页码：**已剥离**（JSON 里 count = 0），符合预期；
- 两条横线之间的章节标题：**190 页里有 184 页被当作页眉丢弃**（P4–P6 預期時間表、P12–P17 董事會函件、
  P56–P73 附錄一、P96–P123 附錄四、P137–P161 附錄七 …）；
  只有 P2「此乃要件 請即處理」、P3「目 錄」、P53、P54 这类"相邻页标题不同"的孤立页保留了标题
  → **同一章节内前后不一致**。

## 三、根因定位

调用链：`processHeadersAndFooters` → `getHeadersOrFooters` → `getNumberOfHeaderOrFooterContentsForEachPage`
（按"层级"逐层剥离）→ `getIndexesOfHeaderOrFootersContents`（配对）→ `arePossibleHeadersOrFooters`。

```java
// HeaderFooterProcessor.arePossibleHeadersOrFooters（文本分支）
if (Objects.equals(textNode1.getValue(), textNode2.getValue())) {
    return true;   // ← 只要相邻两页该位置文字完全相同就判为重复页眉
}
```

1. **1-page style 判据太松**：只要求"相邻两页在同一位置有完全相同的文本"。章节标题在**章内每一对相邻页都相同**
   → 被逐页剥离，且因为每条页只与相邻页比较，才会出现"孤立页保留、其它页剥离"的不一致。
2. **2-page style 也拦不住**：2026-09-16 加的 chain/majority 收紧（要求 `pairStarts` 形成 chain）恰好会被
   "章内连续 N 页标题相同"满足——(p, p+2) 全等且 pairStarts 连续 → `isChainedLongPattern` 成立 →
   同样会把标题判为页眉。**所以只收紧 1-page style 无效，守卫必须落在两种 style 的并集上。**
3. **不能用"层级整体覆盖率"当判据**：迭代 bookkeeping 只按"层级序号"推进、**不区分"值"**，
   层级 2 的匹配页共 186 页（96%），里面混着 20 种不同标题 → 必须按**"文本值"**统计覆盖率。
4. 附带确认：`LineChunk/LineArtChunk/ShapeChunk` 已在 `processHeadersAndFooters` 入口被过滤掉，
   不参与页眉候选，所以那两条横线本身不会干扰判定。

## 四、已实现方案

### 4.1 `HeaderFooterProcessor.java` — 值级重复覆盖率判据（方案 A）

新增常量与守卫：

```java
/** 同一文本必须出现在 ≥ 该比例页面上，才允许按"完全相同文本"判为页眉/页脚。 */
private static final double MIN_REPEATED_VALUE_PAGE_RATIO = 0.5;
```

- `getIndexesOfHeaderOrFootersContents`：1-page style 与 2-page style 在配对成功时，
  用 `isIdenticalValueMatch(object1, object2, isHeaderDetection)` 标记"该页是**同值匹配**"；
  （同值 = 文本值相同；非文本对象 = bbox 相同；**递增序列匹配（页码 1,2,3…）不算同值**）
- 两种 style 合并后的 `result` 交给 `filterNonRepeatedValues(contents, result, identicalPages)`：
  - `identicalPages` 为空 → **直接返回**（快路径，零额外开销）；
  - 否则按值统计该层级每个候选值出现的页数，同值匹配的页只有在
    `出现页数 ≥ max(2, ceil(总页数 × 0.5))` 时才保留；
  - 非"同值匹配"的页（页码序列等）**保持原有行为**，所以页码页脚不受影响。

效果（本 PDF）：警告文字 192/193 通过 → 仍是页眉；章节标题最多 28/193 → 不再判为页眉。

阈值取 0.5 的依据：现有单测与现实模式都要兼容——奇偶页不同页眉天然各占 50%（`>=` 才能通过），
本 PDF 章节标题最大 14.5%，两者分离度足够（15% ~ 50% 之间的任何值都可行）。

### 4.2 `TableBorderProcessor.java` — 跨页表格链的"页面顶部标题"豁免

`checkNeighborTables` 里原本"任何非页眉页脚/非线条的内容"都会 `previousTable = null`。
章节标题回到正文后会把跨页表格链打断，因此新增豁免：

```java
} else if (isPageTop && content instanceof SemanticHeading) {
    // 页面顶部的标题（章节标题）：不算两表之间的内容
} else {
    isPageTop = false;
    previousTable = null;
}
```

`isPageTop` 为"本页尚未遇到会打断链条的内容"的标志，页眉/页脚/线条不会清除该标志，
故"本页开头连续的标题"整体被豁免；标题之后一旦出现真正的正文内容，链条照旧被打断
（`testHeadingAfterPageContentStillBreaksNeighborTableChain`）。

### 4.3 `previous_table` 输出字段

- `JsonName.PREVIOUS_TABLE = "previous_table"`；
- `JsonWriter.generateJsonPageContentData` 的 `lattice_table` 分支新增
  `tableMap.put(JsonName.PREVIOUS_TABLE, tableBorder.getPreviousTable() != null);`
  （即该表是否是上一个表的续表）。

## 六、后续：被覆盖率守卫拒绝的"页面顶部候选"不再参与段落合并（pre-wrap）

### 6.1 实现

`HeaderFooterProcessor` 新增：

- `LevelMatches`（`acceptedPages` / `nonRepeatingPages`）：`getLevelMatches`（原 `getIndexesOfHeaderOrFootersContents`）
  与 `applyRepeatedValueCoverage`（原 `filterNonRepeatedValues`）现在把"被覆盖率守卫拒绝"的页单独报出来；
- `getNumberOfHeaderOrFooterContentsForEachPage(..., Map<Integer, IObject> rejectedPageTopCandidates)`
  只对**页眉方向**记录这些页的候选对象（`Map.putIfAbsent`，每页最多一个层级被拒绝）；
- `splitRejectedPageTopCandidates(contents, rejectedPageTopCandidates)`：把候选对象按**对象身份**定位回页面内容，
  若是 `TextLine` 则用 `ParagraphProcessor.createParagraphFromTextBlock(new TextBlock(line))` 包成一个
  `CustomSemanticParagraph`（与 Loop 3 对单行段落产出的形状一致），使其不被 Loop 3 的
  `ParagraphProcessor` 合并；Loop 4 的 `HeadingProcessor` 随后仍按普通段落判定（多数会成为 heading）。
  记录一条 INFO 日志：`[HeaderFooterProcessor] kept N page-top candidate(s) out of paragraph merging ...`。

为什么需要它：`HeaderFooterProcessor`（DocumentProcessor 第 668 行）早于 Loop 3 的
`ParagraphProcessor`（第 691 行）；两条横线（`LineChunk`）已在 Loop 2 第 637 行被过滤，无法作为段落分隔符
（`ParagraphProcessor.processParagraphs` 的 `separators` 只收集 `LineArtChunk/TableBorder/Table/ImageChunk`），
所以章节标题会被并进本页第一个段落。

## 七、语料回归：跨页续表与 `previous_table` 字段（重要发现）

### 7.1 样本选择

用已有 `tmp_output/*.json` 全量扫描"上一页最后一个 item 是表、下一页第一个 item 是表、列数/表宽/首行列宽一致"
的严格候选，找到 **25 份样本、共 1130 处候选**（最多的是 `202302281677505819604328.pdf`，765 页、745 个表格）。

### 7.2 实测结果

用同一套配置（`TmpSampleRunner`）跑了 5 份样本（3/4/2/305/765 页）：

| 样本 | 表格数 | `previous_table=True` |
|---|---|---|
| `201804301783315258232046605.pdf` | 2 | 0 |
| `202609111789125045008092328.pdf` | 4 | 0 |
| `202609071788754789377063614.pdf` | 2 | 0 |
| `202304281682603453761936.pdf` | 361 | 0 |
| `202302281677505819604328.pdf` | 745 | 0 |

**全部为 0**。给 `TableBorderProcessor.checkNeighborTables` 加文件插桩后定位到原因：

- `checkNeighborTables pages=765 tables=744 textBlocks=1`；
- 744 次"链条被打断"全部是被 **`ShapeChunk`** 打断（`RESET chain from pN broken by ShapeChunk ...`，ShapeRecognizer
  在每页都会产出若干多段线/矩形 ShapeChunk）；
- 因此 `checkNeighborTables(previousTable, currentTable)`（真正的几何比较）**一次都没被调用** → 永远不会建立续表链接。

`checkNeighborTables` 目前忽略 `HeaderFooterProcessor.isHeaderOrFooter`、`LineChunk`、`LineArtChunk`，
以及本次新增的"页面顶部 heading"，但**没有忽略 `ShapeChunk`**（也不忽略 `ImageChunk`）。
`ShapeChunk` 不是 `LineArtChunk` 的子类，所以现有的 `instanceof LineArtChunk` 判断兜不住它。

### 7.3 已实施：把 `ShapeChunk` 纳入忽略列表（用户确认）

用户拍板：**把 `ShapeChunk` 加入 `checkNeighborTables` 的忽略列表，但不加入 `ImageChunk`**。

```java
} else if (HeaderFooterProcessor.isHeaderOrFooter(content) ||
        content instanceof LineChunk || content instanceof LineArtChunk
        || content instanceof ShapeChunk) {
    // Page furniture, rules and vector shapes: no content between two tables.
}
```

`ShapeChunk` 不是 `LineArtChunk` 的子类，因此必须单独列出；`ImageChunk` 与文本一样继续打断链条
（图或段落夹在两表之间说明它们是两张表）。

### 7.4 追加：链接必须跨页（用户要求）

`checkNeighborTables(TableBorder, TableBorder)` 增加首道判断：

```java
if (previousTable.getPageNumber() != null
        && Objects.equals(previousTable.getPageNumber(), currentTable.getPageNumber())) {
    // Two tables on the same page are separate tables, not a continuation.
    return;
}
```

即**同页的两张表即使几何完全一致也不链接**（例如招股书同一页里连续出现的多个同宽"释义"小表）。
只有页码都为 null（信息缺失）时才退回旧行为。

**实施后实测**（同一 runner/配置，逐页对比）：

| 样本 | 表格数 | `previous_table=True` 改动前 → 后 | 跨页 / 同页 | 逐页结构差异 |
|---|---|---|---|---|
| `202302281677505819604328.pdf`（765 页） | 745 | 158 → **157** | 157/157 → **157/0** | 49 页仅图片路径不同（并行非确定性），表格/文本无变化 |
| `202304281682603453761936.pdf`（305 页） | 361 | 0 → **96**（跨页判据后仍 96） | 96/0 | 2 页仅图片路径不同 |
| `201804301783315258232046605.pdf`（3 页） | 2 | 0 → **1**（跨页判据后仍 1） | 1/0 | 1 页仅图片路径不同 |

即：跨页判据只删掉了 765 页样本里那唯一一个同页链接（P188），**157 个真跨页续表全部保留**，
305/3 页样本的链接数不受影响。

**语义正确性证据**：

- 765 页样本 P16→P17→…→P21：3 列"术语 | 指 | 定义"釋義表连续 6 页，几何完全一致
  （x0=83.784、x1=511.68、width=427.896）；
- 305 页样本 P17→P18→P19：产品清单表**行号连续**——P17 末行首列 `23`、P18 首行 `24`…末行 `41`、

- 305 页样本 P6→P7（"联系地址" → "电话/电子信箱"）、P8→P9（"扣非基本每股收益" → "加权平均净资产收益率"）；
- 3 页样本 P2→P3：重复同一表头、4 列、width=482.740 一致。

单测新增 `testShapeChunkDoesNotBreakNeighborTableChain`（ShapeChunk 不打断）
与 `testImageChunkBreaksNeighborTableChain`（ImageChunk 仍打断，正向对照）。

### 7.5 本次改动的回归结论（5 份样本）

- 305 页样本：改动前后只有 2 页的图片文件名不同（并行非确定性），**361 个表格、结构完全一致**；
  且该样本上"覆盖率守卫"一次都没触发（无 pre-wrap 日志）→ 页眉相关改动对它零影响。
- 765 页样本：同上（结构与表格一致，差异只在图片路径与 `previous_table`）。
- 因此"页眉判定 + 表格链豁免 + pre-wrap"的可见影响仅落在带"页顶章节标题"的文档上（如 193 页样本）；
  而 `ShapeChunk` 豁免只影响 `previous_table`（与 `nextTable/previousTable` 关联的层级判定）。

## 八、遗留问题（待用户决定）

### 8.1 `ShapeChunk` 已纳入忽略列表 + 链接必须跨页（均已按用户要求实施）

见 7.3 / 7.4：`checkNeighborTables` 现在忽略 `ShapeChunk`、但**不忽略 `ImageChunk`**；
并且**同页两表不再链接**。实测 765 页样本 158 → 157（唯一同页链接已去掉，157 个跨页链接保留）、
305 页样本 96、3 页样本 1，逐页对比只有图片路径（并行非确定性）差异。
若后续仍发现误链接（例如跨页但不相关的同宽同列表），可再加"上一表末行与下表首行的行高分布相似"之类判据。

### 8.2 段落重新切分的小抖动（本次改动的固有副作用）

pre-wrap 让页面多了一个独立段落，`ParagraphProcessor` 的"按页统计"（左边界/字号/缩进/间距中位数）随之变化，
于是个别页面的其它段落会重新切分（193 页样本：P17、P52 各有一处；文本不丢）。
如果后续觉得这不可接受，可考虑"只把标题行包成段落但不让它参与该页统计"之类的更细方案，目前不做。

### 8.3 图片文件名编号的非确定性（与本次无关，观察记录）

同一份代码在 305 页样本上两次运行的图片路径也会不同（`imageFileN.png` 的 N 会变），
说明并行处理下图片编号本身不稳定，排查 JSON 差异时需要排除这一项。

环境坑（复用价值）：

- `java -cp "target/classes;$CP" org.opendataloader.pdf.DebugSample` 必须用 PowerShell
  `Get-Content cp.txt -Raw` 读 classpath —— cmd 的 `set /p` 只能读 1024 字符，会截断导致
  `NoClassDefFoundError`；
- 改了 DebugSample 指向的 PDF 后必须先 `mvn -o -pl opendataloader-pdf-core compile`，否则跑的是旧 class；
- 单测里 `StaticContainers.setKeepLineBreaks(true)` 必须显式设置（ThreadLocal，测试路径不会初始化），
  否则对 `SemanticTextNode.getValue()`（经 `TextBlock.toString()`）会 NPE；
- **PowerShell 跑批把 java 的 stdout/stderr 重定向到文件时，`System.out/err.println` 可能丢失**：
  临时插桩建议直接写文件（本次即用文件插桩才定位到 `ShapeChunk` 打断链条）；
- 行内 `python -c "..."` 在 PowerShell 里引号极易被吞，统一改成写 `.py` 文件再执行。
