## 完整定位过程（从现象到根因）

### 阶段 1：确认「谁给单元格写背景色」

全仓搜索 `setBackgroundColor|getBackgroundColor`，命中只有 3 处：

- `TableBorderProcessor.java:245` — **唯一赋值点** `entry.getKey().setBackgroundColor(entry.getValue().color)`
- `JsonWriter.java:1011` — 序列化为 `bg_color`（`#eaeaea` 十六进制）
- `TableCellSerializer.java:46` — 序列化为 `background color r/g/b`

结论：问题一定在 `assignBackgroundColorsFromRectangleShapes()`，其逻辑是「找 `TYPE_RECTANGLE` 的 `ShapeChunk`，与表格单元格求重叠，> 50% 就记录颜色」。

### 阶段 2：确认 PDF 原文到底有几块灰底（不信解析结果，直接看内容流）

没有 PyMuPDF / pypdf，用 Python 标准库 `zlib` 写临时脚本，正则找 `stream ... endstream` 并 inflate，再匹配 `([\d\. ]+rg)\s*\n?(... re)\s*\n?f`。

`-2.pdf` 结果 —— **12 处** `0.918 0.918 0.918 rg`（= 234 → `#eaeaea`）：

```
503.716 518.456 96.378 39.119 re f   ← 第4列 第1行
707.811 518.456 90.709 39.119 re f   ← 第6列 第1行
503.716 479.337 96.378 39.119 re f   ← 第4列 第2行
707.811 479.337 90.709 39.119 re f   ← 第6列 第2行
... 共 6 行 × 2 列
```

即：**6 行全部有灰底**，解析结果只有第 2 行 → 解析侧丢色。

### 阶段 3：看中间产物 —— ShapeRecognizer 的 INFO 日志

`ShapeRecognizer.recognize()` 本身就会在 INFO 级打印识别到的形状。运行 `DebugSample` 得到：

```
Page 1: recognized 12 shape(s)
Page 1: shape type=rectangle, components=6, bbox=[503.716, 322.861, 600.094, 557.575]
Page 1: shape type=rectangle, components=6, bbox=[707.811, 322.861, 798.520, 557.575]
```

**6 个同色、紧贴（gap=0）的单元格灰块被 `clusterRects()` 合并成了 1 个贯穿整列的 `ShapeChunk`（`components=6`）**。

于是矛盾点变成：一个覆盖整列（6 行）的形状，为什么只有 1 行拿到颜色？

### 阶段 4：定位真正的 bug —— veraPDF 的 `getTableBorderCells()` 只返回一行

`assignBackgroundColorsFromRectangleShapes()` 原本这样取「形状覆盖了哪些单元格」：

```java
Set<TableBorderCell> cells = tableBorder.getTableBorderCells(shapeChunk);
for (TableBorderCell cell : cells) {
    double overlap = cell.getBoundingBox().getIntersectionPercent(shapeChunk.getBoundingBox());
    if (overlap > CELL_BACKGROUND_OVERLAP_THRESHOLD) { ... }
}
```

去 veraPDF 源码仓库（`..\veraPDF-wcag-algs`，用户提示这才是实际打包来源）读实现：

```java
// TableBorder.java:885
public Set<TableBorderCell> getTableBorderCells(IObject object) {
    ...
    Set<TableBorderCell> cells = new HashSet<>();
    int rowNumber = getRowNumber(yTopIndex, yBottomIndex, box);   // ← 只有一个行号
    for (int xIndex = xLeftIndex; xIndex < xRightIndex; xIndex++) {
        TableBorderCell cell = rows[rowNumber].cells[xIndex];     // ← 只取这一行
        cells.add(cell);
    }
    return cells;
}

private int getRowNumber(int yTopIndex, int yBottomIndex, BoundingBox box) {
    double maxPercent = -Double.MAX_VALUE;
    int rowNumber = 0;
    for (int yIndex = yTopIndex; yIndex < yBottomIndex; yIndex++) {
        double percent = box.getVerticalIntersectionPercent(rows[yIndex].getBoundingBox());
        if (percent > maxPercent) { maxPercent = percent; rowNumber = yIndex; }   // ← 严格 >，相等取最小索引
    }
    return rowNumber;
}
```

**根因 A**：`getTableBorderCells()` 把跨多行的对象**塌缩成单行**（取纵向重叠最大的那一行），跨行背景矩形只会给 1 行上色。

**为什么恰好是第 2 行**（本来以为应该是最匹配的某一行，看起来很随机）：

- `BoundingBox.getIntersectionPercent` / `getVerticalIntersectionPercent` 对 6 行算出来的值完全相同（整列形状纵向覆盖每行 100%）。
- 关键在 `getClosestTopY(557.575)`：**表格外框线的 topY = 557.825 也进了 `yCoordinates`**（外框 `re S` 加了 0.5 线宽后 bbox 为 `[20.443, 322.611, 798.77, 557.825]`，而灰块 topY = 557.575）。
- `getClosestTopY` 从下往上找第一个满足 `y <= getTopY(i) + EPSILON` 的索引 → 命中 `yCoordinates[1]` → `yTopIndex = 1` → `rows[1]` → JSON 里的**第 2 行**。

到此，「只有第 2 行有灰底」完全解释通。

### 阶段 5：第一版修复（用户批准的方案）

只改 `TableBorderProcessor`，不动 veraPDF、不动 `ShapeRecognizer`：

- 不再调用 `getTableBorderCells()`，改为**直接遍历表格全部单元格**（`getNumberOfRows()` × `getNumberOfColumns()`）；
- 跳过 `null` 与被 rowSpan/colSpan 覆盖的单元格（`cell.getRowNumber() != rowNumber || cell.getColNumber() != colNumber`），避免合并单元格被重复处理；
- 保留原有的「每个单元格取重叠最大的形状颜色」逻辑（`Map<TableBorderCell, BestShapeMatch>`），天然的按 cell 去重。

验证 `-2.pdf`：12 格 `#eaeaea`（6 行 × 第4/6列），与内容流 12 处填充完全一致 ✅

### 阶段 6：用户反馈 `-1.pdf` 第 8 行多出灰色 —— 第二个根因

同样先 dump 内容流，`-1.pdf` 的灰底填充共 **5 处**（`y-up` 坐标）：

| # | bbox | 对应单元格 |
|---|---|---|
| 1 | `[407.338, 206.334, 503.716, 227.310]` | 第7行 第3列 |
| 2 | `[600.094, 206.334, 707.811, 227.310]` | 第7行 第5列 |
| 3 | `[707.811, 142.723, 798.520, 206.334]` | **第8行 第6列（该行唯一一处）** |
| 4 | `[407.338, 121.747, 503.716, 142.723]` | 第9行 第3列 |
| 5 | `[600.094, 121.747, 707.811, 142.723]` | 第9行 第5列 |

但 `ShapeRecognizer` 只识别出 3 个 rectangle：

```
rectangle, components=1, bbox=[407.338, 206.334, 503.716, 227.31]
rectangle, components=3, bbox=[600.094, 121.747, 798.52,  227.31]   ← #2 #3 #5 被合成一个
rectangle, components=1, bbox=[407.338, 121.747, 503.716, 142.723]
```

**根因 B**：`ShapeRecognizer.clusterRects()` 里的 `areAdjacentOrOverlapping()` 对 x、y **两个方向各自**用 `ADJACENCY_GAP = 2.0` 容差判断，因此**只在一个角点相接**的矩形也会被合并：

```java
boolean xOverlap = a.getLeftX() <= b.getRightX() + ADJACENCY_GAP
                && b.getLeftX() <= a.getRightX() + ADJACENCY_GAP;
boolean yOverlap = a.getBottomY() <= b.getTopY() + ADJACENCY_GAP
                && b.getBottomY() <= a.getTopY() + ADJACENCY_GAP;
return xOverlap && yOverlap;
```

- #2 `[600.094,206.334 → 707.811,227.310]` 与 #3 `[707.811,142.723 → 798.520,206.334]`：只在角点 `(707.811, 206.334)` 相碰；
- #3 与 #5 `[600.094,121.747 → 707.811,142.723]`：只在角点 `(707.811, 142.723)` 相碰。

合并后 union bbox = `[600.094, 121.747, 798.52, 227.31]`，凭空覆盖了三块**从未填充**的区域：第7行第6列、第8行第5列、第9行第6列。

2. `assignBackgroundColorsFromRectangleShapes()` 重写：

```java
private static void assignBackgroundColorsFromRectangleShapes(List<IObject> rawPageContents, TableBorder tableBorder) {
    if (tableBorder == null || tableBorder.isTextBlock() || rawPageContents == null || rawPageContents.isEmpty()) {
        return;
    }
    List<ShapeChunk> rectangleShapes = new ArrayList<>();
    for (IObject content : rawPageContents) {
        if (!(content instanceof ShapeChunk)) { continue; }
        ShapeChunk shapeChunk = (ShapeChunk) content;
        if (!ShapeChunk.TYPE_RECTANGLE.equals(shapeChunk.getShapeType())) { continue; }
        double[] color = shapeChunk.getColor();
        if (color == null || color.length != 3) { continue; }
        rectangleShapes.add(shapeChunk);
    }
    if (rectangleShapes.isEmpty()) { return; }

    Map<TableBorderCell, BestShapeMatch> bestMatches = new HashMap<>();
    for (int rowNumber = 0; rowNumber < tableBorder.getNumberOfRows(); rowNumber++) {
        TableBorderRow row = tableBorder.getRow(rowNumber);
        for (int colNumber = 0; colNumber < tableBorder.getNumberOfColumns(); colNumber++) {
            TableBorderCell cell = row.getCell(colNumber);
            // 跳过 null 与被 rowSpan/colSpan 覆盖的单元格
            if (cell == null || cell.getRowNumber() != rowNumber || cell.getColNumber() != colNumber) { continue; }
            for (ShapeChunk shapeChunk : rectangleShapes) {
                for (BoundingBox fillBox : getFillBoxes(shapeChunk)) {          // ← 关键：用组件框，不用 union 框
                    double overlap = cell.getBoundingBox().getIntersectionPercent(fillBox);
                    if (overlap > CELL_BACKGROUND_OVERLAP_THRESHOLD) {
                        BestShapeMatch current = bestMatches.get(cell);
                        if (current == null || overlap > current.overlap) {
                            bestMatches.put(cell, new BestShapeMatch(shapeChunk.getColor(), overlap));
                        }
                    }
                }
            }
        }
    }
    for (Map.Entry<TableBorderCell, BestShapeMatch> entry : bestMatches.entrySet()) {
        entry.getKey().setBackgroundColor(entry.getValue().color);
    }
}
```

3. 新增私有方法 `getFillBoxes(ShapeChunk)`：

```java
private static List<BoundingBox> getFillBoxes(ShapeChunk shapeChunk) {
    List<BoundingBox> componentBBoxes = shapeChunk.getComponentBBoxes();
    if (componentBBoxes == null || componentBBoxes.isEmpty()) {
        return Collections.singletonList(shapeChunk.getBoundingBox());
    }
    return componentBBoxes;
}
```

**未改动**：`ShapeRecognizer`、`veraPDF-wcag-algs`、`CELL_BACKGROUND_OVERLAP_THRESHOLD = 0.5`、`JsonWriter` / `TableCellSerializer`。

## 关键决策（Key Decisions）

1. **不动 `ShapeRecognizer`**：`clusterRects()` 的合并语义还要服务柱状图/流程图识别，改相邻判定会改变全站 shape 输出，影响面太大。改为在消费侧（`TableBorderProcessor`）用 `getComponentBBoxes()` 还原「真实填充区域」。用户也明确选了这条路。
2. **用 `getComponentBBoxes()` 而非 union bbox**：`ShapeChunk` 已经携带每个原始填充矩形的 bbox（`createShape()` 里 `parts.add(bb)`），这正是「PDF 里真正被填充的区域」，是解决根因 B 的最精确数据源。
3. **保留 union bbox 作为回退**：`getComponentBBoxes()` 为空时（理论上 `TYPE_RECTANGLE` 不会，但防御）回退到 `getBoundingBox()`。
4. **只处理 `TYPE_RECTANGLE`**：`TYPE_BAR_CHART` 的 union bbox 语义与单元格背景无关，用户明确要求不扩大范围。
5. **直接遍历单元格而非 `getTableBorderCells()`**：后者单行塌缩语义对「文本块归属某行」是合理的，但对「背景色覆盖哪些单元格」是错的；在消费侧绕开它，而不是改 veraPDF。
6. **跳过 span 覆盖单元格**：`row.getCell(col)` 对合并单元格会返回同一个对象，用 `getRowNumber()/getColNumber()` 与下标比对来去重，避免重复计算（且 `HashMap` 以 cell 为 key 本身也能兜底）。

## 排查技巧备忘（可复用）

- **验证 PDF 真相不要靠解析结果**：Python 标准库即可 dump 内容流（`re` 找 `stream\r?\n` … `endstream`，`zlib.decompress`，再匹配 `<color> rg` + `re` + `f`）。本项目没有 PyMuPDF / pypdf。
- **`ShapeRecognizer` 自带 INFO 日志**（`Page N: shape type=..., components=..., bbox=...`），JUL 默认级别就能看到，是定位「形状被误合并」最快的入口。
- **A/B 对比用 `git stash push -- <单文件>`**，跑完 `git stash pop`，不会牵动同文件外的其它未提交改动。
- **解析坐标是 y-up，JSON 输出是 y-down**：换算 `y_up = pageHeight - y_down`。`-1.pdf` / `-2.pdf` 页高 `595.276`。
- **列号要在内容流里核对**：`-1.pdf` 第 5 列（600.094–707.811，内容 `HKD 6.4486`）在 PDF 里并没有灰底，`-2.pdf` 第 5 列也没有——用户最初说的「第4、5列」实为**第4、6列**，是靠内容流坐标纠正的。
