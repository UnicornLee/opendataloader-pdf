### 2. `ShapeRecognizer`：新增 `recognizePieChartsFromFillBoxes(...)`（核心）

在 `recognizePage` 中于 `recognizeBarChartsFromFillBoxes` **之后**调用。相关常量：

```java
private static final double PIE_CORNER_TOLERANCE = 2.0;              // 角点重合容差
private static final int    MIN_PIE_WEDGE_COUNT = 3;                 // 共角点簇最小楔形数
private static final int    MIN_PIE_WEDGE_COUNT_WITHOUT_DISC = 5;    // 无整圆框时的最小楔形数（新增，抑误检）
private static final double PIE_MIN_SIZE = 30.0;                     // 饼图最小边长
private static final double PIE_SQUARE_TOLERANCE = 4.0;              // 正方形绝对容差
private static final double PIE_SQUARE_RATIO = 0.08;                 // 正方形相对容差
private static final double PIE_CENTER_TOLERANCE = 2.0;              // 共角点≈中心 容差
private static final double PIE_DISC_CENTER_TOLERANCE = 8.0;         // 整圆框中心≈共角点 容差（新增）
private static final double PIE_MAX_WEDGE_AREA_RATIO = 0.6;          // 单框最大占比
```

算法（最终版）：

1. `candidates = filterShapeCoincidentFills(fillBoxes, existingShapes)`（只过滤与**矩形/柱状图**重合的填充，楔形不受影响）；
2. 按「4 个角点」把 `candidates` 分桶（`cornerKey = round(x/2)+"_"+round(y/2)`），得到多个 `CornerCluster`；
3. 对每个簇去重后 `wedges`：
   - `wedges.size() < MIN_PIE_WEDGE_COUNT` → 跳过；
   - **`disc = findDiscBox(candidates, hubX, hubY)`**：在所有候选里找**中心≈共角点且近正方形**的框（即"整圆填充框"）。
     - 若 `disc == null` 且 `wedges.size() < MIN_PIE_WEDGE_COUNT_WITHOUT_DISC(5)` → 跳过（**新增的误检抑制**）；
   - `pieBox = disc != null ? disc : boxAroundCorner(hub, wedges, pageNumber)`；
     - `boxAroundCorner`：以共角点为心、半边长 = 扇形角点到共角点的最大距离（对整圆饼图恰等于半径 → 得到圆盘 bbox）；
   - 单框面积 > `0.6 * pieBox.area` → 跳过（防把整圆框自身当楔形）；
   - `isValidPieDisc(pieBox, hub)`：近正方形 + 尺寸 ≥ `PIE_MIN_SIZE` + 中心≈共角点；
   - 通过则产出 `new ShapeChunk(pieBox, TYPE_PIE_CHART, null, wedges.size(), wedges)`。
4. 新增辅助方法：`findDiscBox`、`boxAroundCorner`、`isSquare`、`isValidPieDisc`（**取代**了原 `isValidPieUnion`）。
5. 命中时打印：`Page N: recognized pie chart with X wedges at bbox=[...]`。

## 定位过程（从问题到根本原因）

> 这一节是本轮最有价值的部分：原本以为"照着 2026-09-11 的方案实现即可"，实际实跑后发现**根本识别不出来**，根因是上一轮方案的判据本身错误。

### 第 0 步：单页跑 `-18.pdf`，看不到任何 `pie_chart`

`DebugSample1` 指向 `-18.pdf`，`mvn exec:java` 跑完日志里只有 22 个 shape：**12 个 `rectangle`（图例色块）+ 10 个 `polyline`（引导线/框线）**，**没有 `pie_chart`**。

### 第 1 步：先排除"没重编译"

`mvn exec:java` 用的是 `target/classes`；若源码改动后未重编译，跑的还是旧类 → **假阴性**。
（后续证实 `exec:java` 会触发 `compile` 阶段，增量编译会重编改动文件。）

### 第 2 步：加临时插桩，确认识别函数被调用、并 dump 候选

在 `recognizePieChartsFromFillBoxes` 里加 `LOGGER` 打印候选数与每个候选 bbox，重编译后再跑：

```
DEBUG pie: page 1 candidates=68
DEBUG pie candidate: [...]
...
DEBUG pie candidate: [285.1400146484375,555.1300048828125,325.6700134277344,636.219970703125]
...（共 10 个以 (285.1400146484375,555.1300048828125) 为“左下角”的框）
DEBUG pie candidate: [204.0500030517578,474.04998779296875,366.2300109863281,636.219970703125]
```

**两个关键事实被实测确认**：

- 候选里确实有 **10 个扇形填充框**，全部以 **`(285.14, 555.13)` 为左下角**；
- 另有一个 **整圆填充框 `[204.05, 474.05, 366.23, 636.22]`（162.18×162.17，近似正方形）**，其中心 `((204.05+366.23)/2, (474.05+636.22)/2) = (285.14, 555.135)` **正好等于该共角点**（= 饼图圆心）。

### 第 3 步：关键的"反直觉"数据 —— 共角点簇存在，但并集不是正方形

加插桩打印每个簇的校验细节，得到：

```
DEBUG pie skip: hub=(285.1400146484375,555.1300048828125) unique=10
                union=[285.1400146484375,555.1300048828125,353.1099853515625,636.219970703125]
                w=67.969970703125  h=81.0899658203125  dominated=true  validUnion=false
```

**簇内确实有 10 个楔形（`unique=10`），但并集只有 `68×81`，不是正方形 → `validUnion=false` → 被跳过 → 饼图识别不出来。**

### 第 4 步：为何并集不是正方形 —— 找到根本原因

几何解释：一个扇形（从圆心到弧的填充多边形）的 **bbox** 取决于扇形的角度范围。**当所有扇形都在圆心的右上方向时，圆心恰好是每个扇形 bbox 的「左下角」**；此时 10 个 bbox 的并集只会覆盖圆盘右上的一块，**永远不会等于圆盘**。

本例中 10 个扇形框的 `leftX/bottomY` 恒为 `(285.14, 555.13)`（即圆心），`rightX/rightY` 各不相同 → 并集 `[285.14, 555.13, 353.11, 636.22]`。

**上一轮方案第 2 条「扇形并集 ≈ 正方形（圆盘）」是基于"扇形的 bbox 会覆盖到圆盘四周"的错误假设 —— 实际上圆心是每个扇形 bbox 的一个角点，并集只能覆盖一个象限扇面。**

### 第 5 步：确定正确做法 —— 用"独立的整圆填充框"当 bbox

数据里那个 `[204.05, 474.05, 366.23, 636.22]`（162.18×162.17）才是圆盘本身，且它的**中心恰为共角点/圆心**。于是改为：

- 找"中心 ≈ 共角点且近正方形"的候选框（`findDiscBox`），**直接用它作饼图 bbox**；
- 若没有整圆框，用 `boxAroundCorner`：以共角点为心、半边长 = 扇形角点到共角点的最大距离 —— 对整圆饼图该值恰为半径，得到同样的圆盘 bbox。

### 第 6 步：修完出现"3 楔形误检"，再加一道闸

改完后单页日志变成：

```
recognized pie chart with 10 wedges at bbox=[204.05,474.05,366.23,636.22]     ← 真饼图 ✓
recognized pie chart with  3 wedges at bbox=[285.14,489.14,417.12,621.12]     ← 误检 ✗（与真饼图重叠）
```

假簇是 3 个恰好共角点、且兜底正方形通过的填充框。修正：**无整圆框时要求楔形数 ≥ `MIN_PIE_WEDGE_COUNT_WITHOUT_DISC = 5`**（真饼图有整圆框，不受影响）。再跑 → 只识别出 1 个饼图。

### 第 7 步：整册 PDF 实跑验证

`DebugSample1` 指向整册 `354cb7d4-8f79-4429-8768-e3b0e3fcc4e3.pdf`，重编译后跑完整链路（含 OCR）。参见下节结果。

## 根本原因（Root Cause）

### A. 饼图识别"落地即失效"的根因

**矩形/多边形填充框的 bbox 会把"顶点"放在角上；当多个填充框共用同一个顶点（饼图圆心）时，各框的 bbox 会以该顶点为各自的一个角点，导致各框并集只覆盖"从该顶点张开的那个象限扇面"，而非整圆。**

因此：**"扇形框并集 ≈ 圆盘(正方形)"这一判据本质错误**（在"扇形分布覆盖整个圆周"的想象下才成立，实际渲染不会这样）。正确做法是**用独立存在的整圆填充框（或其中心=共角点这一事实）来确定圆盘 bbox**。

### B. 单页/多页差异（沿用上一轮结论，本轮从机制上规避）

原链路：跨页页眉页脚识别 → `leftX/rightX` 分位变化 → 饼图区段落合并变化 → `FlowchartProcessor` `mergedBox` 高度 40.601 vs 门限 40 的 0.6pt 边缘翻转。
本轮通过"饼图成为一等 chart、在流程图前消费 + 跳过含饼图组 + `MIN_HEIGHT` 降到 20"**从机制上切断**了饼图对该边缘的依赖（方案 3 的全局耦合未动）。

## 环境坑（供后续复现，避免重复踩）

1. **本沙箱 Maven 仓库在 `D:\Maven_Repo`**（不是 `~/.m2`）。
2. **`mvn compile` 会失败**：编译期 classpath 解析到的 veraPDF `wcag-algorithms` 版本偏旧，报
   `JsonWriter.java` 找不到 `SemanticHeading.getColumns()`。
   但**用运行时 classpath**（`mvn dependency:build-classpath` 产物，`wcag-algorithms-1.31.33`，含该方法）**以 `javac` 全量编译可通过**。
   → 结论：`JsonWriter` **无需改动**（期间临时加过的 `SemanticTextNode` 上转已**全部回退**）；本环境请用
   `javac -encoding UTF-8 -cp "<运行时classpath>" -d target/classes @sources.txt` 编译，再 `java -cp "target/classes;<运行时classpath>" org.opendataloader.pdf.DebugSample1` 运行。
3. **cmd 的 `set /p` 读 classpath 会截断到 1023 字符**（导致 veraPDF 等 jar 丢失、javac 报"程序包不存在"）；
   必须改用 `for /f "usebackq delims=" %%a in ("cp.txt") do set "CP=%%a"`。
4. 早期 `exec:java` 能跑通，是因为用了**上次正确构建的缓存 `.class`**（增量编译跳过 `JsonWriter`）；一旦 `mvn compile` 失败清空了 `target/classes`，就会暴露第 2、3 条问题。
5. **插桩排查时务必确认目标类已重编译**（`target/classes` 是否更新），否则会得到"改了没效果"的假阴性。
