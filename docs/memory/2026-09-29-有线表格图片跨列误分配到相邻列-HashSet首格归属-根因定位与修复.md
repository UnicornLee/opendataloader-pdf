# 2026-09-29 有线表格图片跨列被误分配到相邻列（HashSet 迭代顺序取首格）——根因定位与修复

样本：`docs/pdf/202304201681906512315204.pdf` 第 17 页（JSON 的 `page_index=17`），
`lattice_table` 7 行 × 5 列（表头：产品类型 | 产品系列 | 产品型号 | 产品图示 | 主要应用领域）。
入口：`org.opendataloader.pdf.DebugSample`（输出到 `tmp_output/`）。

## 1. 现象

第 2 行（MAS 系列）与第 4 行（NEX 系列）的"产品图示"图片没有落在第 4 列，而是跑到了第 5 列，
第 4 列变成空单元格；其余行（3/5/6/7 行）的图片归属正常。

修复前 JSON 关键证据（cell 按 x 坐标辨认列）：

| 行 | 第4列 x=[258.8,390.3] | 第5列 x=[390.3,536.3] |
|---|---|---|
| 2 | `text=''`（空） | `<img ... imageFile2.png>`（错位）+ 应用文字消失 |
| 4 | `text=''`（空） | `<img ... imageFile4.png>`（错位） |
| 3/5/6/7 | `<img ...>` 正常 | 应用描述文字正常 |

## 2. 定位过程

### 2.1 读现有输出 JSON，锁定"错位只发生在特定行"

写探针脚本 `tmp_output/inspect_p17.py` 解析 `tmp_output/202304201681906512315204.json`
（结构：顶层 `data` = 页列表，每页 `items[]`，表格 `item_type=lattice_table`，
`content` = 行数组，每格 `{x0,y0,x1,y1,text,cell_type,row_len,column_len}`，
`text` 可能是字符串或行列表，图片以 `<img src='...' style='height:...pt;width:...pt'/>` 内嵌）。
对比发现：错位的两张图（imageFile2/4）`width` 均为 139.56pt，**大于第 4 列列宽 131.5pt**；
正常行的图片宽 109~129pt，均小于列宽。→ 嫌疑：图片越过了列分界线 390.31。

### 2.2 追代码：图片入格的链路

- 表格内容由 `TableBorderProcessor.addContentToTableBorder(content)`（loop2，DocumentProcessor L636 调）分配进单元格；
- 候选单元格来自库方法 `TableBorder.getTableBorderCells(IObject)`（veraPDF-wcag-algs 1.31.33，
  本地 jar `D:\Maven_Repo\org\verapdf\wcag-algorithms\1.31.33\` 即兄弟仓库源码本地 install 的版本）：
  按内容 bbox 找左右上下最近的列/行分界线索引，把跨到的**所有列**单元格放进 **`HashSet<TableBorderCell>`** 返回
  （行则由 `getRowNumber()` 取垂直重叠最大的单行，行归属没问题）；
- `addContentToTableBorder` 对多格命中只特判 `TextChunk`（按列边界切分），其余类型（含 `ImageChunk`）走
  else 分支：`for (cell : cells) { cell.addContentObject(content); break; }` ——**取 HashSet 迭代的第一个，
  完全不看重叠面积**。`<img>` 文本本身是后续 `CustomChunksMergeUtils.convertImageChunkToTextChunk` 才生成的，
  归属错误发生在更早的 ImageChunk 入格阶段。

### 2.3 写 Java 诊断类实锤

`tmp_output/scratch_diag/scratch/DiagP17.java`：复用 `DocumentProcessor.preprocessing` +
`ContentFilterProcessor.getFilteredContents` 拿第 17 页（0-based 16）的 `ImageChunk`，
对每个图片打印 bbox、`getTableBorderCells` 返回的候选单元格（按迭代顺序）及各自重叠率。
关键输出：

```
IMAGE bbox=(263.52,737.76)-(403.08,633.12)          ← 第2行图片，右边界 403.08 > 列分界 390.31，越界约12.8pt
  candidate cells (HashSet iteration order):
    [#0] row=1 col=4 overlapOfImage=0.086            ← 第5列沾边 8.6%，却排在 HashSet 第一位
    [#1] row=1 col=3 overlapOfImage=0.951            ← 第4列重叠 95.1%，排第二
  -> addContentToTableBorder would put image into row=1 col=4（第5列）← 与最终 JSON 一致
```

第 4 行（0-based row=3）同型；其余 4 张图片只命中单格 → 正常。
（`getIntersectionPercent` 语义：`a.getIntersectionPercent(b)` = a 自身面积被 b 覆盖的比例，已核库源码。）

## 3. 根因

PDF 源文件里第 2/4 行的产品图本身就比"产品图示"单元格宽、右缘压过列分界线（不是提取误差）。
图片 bbox 跨列时 `getTableBorderCells` 返回多个候选单元格且为 **`HashSet`（迭代顺序依赖对象 identity hash，无逻辑意义）**，
而 `addContentToTableBorder` 对非文本内容**取迭代第一个单元格直接放入**，不比较重叠面积——
本例第一个恰好是只覆盖 8.6% 的第 5 列单元格。该缺陷还意味着跨运行结果可能不稳定。

## 4. 修复（方案 A，用户选定；veraPDF-wcag-algs 库不动）

改动**仅 `java/opendataloader-pdf-core/.../processors/TableBorderProcessor.java`**：

1. `addContentToTableBorder` else 分支：不再 for+break 取首个，改调新方法
   `getBestOverlappingCell(tableBorderCells, content.getBoundingBox())`；
2. 新增 `getBestOverlappingCell(Set<TableBorderCell>, BoundingBox)`：
   以 `contentBox.getIntersectionPercent(cellBox)`（**内容有多少落在格内**，而非格被内容覆盖的比例，
   避免不同宽度单元格之间比较不公平）取最大者；完全平局按 `rowNumber`、`colNumber` 升序，保证确定性；
3. `LineArtChunk` 的 >`LINE_ART_PERCENT`(0.9) 吞线特判保留，只是判据对象从"首个单元格"改为"最优单元格"
   （覆盖 >90% 的格必然也是重叠最大者，语义等价或更准）；
4. `TextChunk` 跨列切分分支未动。

放弃的方案 B（库内 `HashSet`→`LinkedHashSet` 按列序）：只对"向右越界"正确，向左越界仍错，
且需重建 install 兄弟仓库 jar。
