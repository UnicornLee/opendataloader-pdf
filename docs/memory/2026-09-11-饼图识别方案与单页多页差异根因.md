## 结论速览（TL;DR）

- **饼图在当前流水线里"看不见"**：veraPDF artifact 层完全没有饼图扇形本体（只有被 `ShapeRecognizer.isWhite()` 过滤掉的 1.5pt 白色分界线、0.72pt 灰色引导线、图例色块和文本）。饼图唯一可用的数据源是 `DocumentProcessor.extractPageFillBoxes()` 产出的 **PDFBox 闭合填充路径 bbox 列表**（目前只用于柱状图/箭头的兜底）。
- **"单页/多页差异"不是文件差异，而是"跨页页眉页脚识别 → 段落对齐参考量分位 → 段落合并 → 流程图门限边缘翻转"这条链**：
  1. 单页时页眉/页码仍是顶层 `TextLine`；多页时被 `HeaderFooterProcessor` 包进 `SemanticHeaderOrFooter`；
  2. `ParagraphProcessor.processParagraphs` 的 `leftX/rightX` 是 **TextBlock 集合的分位数**：27 块 → `rightX=473.88`，25 块 → `rightX=456.94`；
  3. 参考量左移 16.94pt → 饼图区 3 组"百分比 ↔ 图例文字"段落合并结果不同（只在多页合并）；
  4. `FlowchartProcessor` 的 `mergedBox` 高度 **40.601pt，仅比 `MIN_HEIGHT=40` 高 0.60pt** → 多页通过、单页不通过；
  5. 于是同一页"单页文件无图、放进多页文档才有（且被裁掉一大半）图"。

## 定位过程（Investigation）

### 第 1 步：饼图在 artifact 层到底有什么

`DBGD|artifacts|page=0`（共 375 项，含 ShapeRecognizer 追加的 shape）。只筛饼图区域 `x∈[195,375] y∈[465,650]`：

- 全是 `stroke=1.000/1.000/1.000`（**白色**）的 `LineChunk`，例如
  `idx=238 LineChunk bbox=(285.01,554.80)-(352.68,600.53) thickness=1.500 stroke=1.000/1.000/1.000`、
  `idx=242 LineChunk bbox=(284.39,555.13)-(285.89,636.22) w=1.50 h=81.09 stroke=1.000/1.000/1.000`

- 灰色引导线 `stroke=0.651/0.651/0.651 thickness=0.720`（idx 244–251），最终识别成 4 条 `polyline`；
- 文本 `TextChunk`（`8.33% 1.61%`、`84.18%` …）。

按饼图扇形填充色（`0.039/0.243/0.333` … `0.788/0.816/0.839`）过滤：**命中的全部是 x=396.81 的图例色块**，饼图区域一个都没有。

### 第 4 步：段落合并为何会被"页眉页脚"影响（量化验证）

`ParagraphProcessor.processParagraphs(contents, width)`：

```java
for (IObject content : contents) {
    if (content instanceof TextLine) { blocks.add(new TextBlock((TextLine) content)); }
}
List<Double> leftXList  = blocks.stream().map(b -> b.getBoundingBox().getLeftX()).collect(...);
leftX  = leftXList.size() < 6 ? sorted.get(0)          : sorted.get(leftXList.size() / 4);      // 25% 分位
List<Double> rightXList = blocks.stream().map(b -> b.getBoundingBox().getRightX()).collect(...);
rightX = rightXList.size() < 6 ? sorted.get(size - 1)  : sorted.get(3 * size / 4);              // 75% 分位
blocks = detectParagraphsWithJustifyAlignments(blocks, leftX, rightX, width, lineArts);   // 后面还有 7 个检测器
```

`leftX`/`rightX` 是**页面级对齐参考量**，喂给后续 8 个段落检测器。用 `para_stats.py` 对 `L2` 的 TextLine 集合复算：

```
single (含页眉/页码)      n=27  leftX=113.90  rightX=473.88     (rights[20])
multi  (页眉/页码被包走)  n=25  leftX=113.90  rightX=456.94     (rights[18])
removed: [(316.54,789.05)-(505.54,798.05), (293.18,49.78)-(302.18,57.96)]
```

→ 仅因为少了 2 行（页眉、页码），`rightX` 就**左移 16.94pt**（`leftX` 恰好不变）。饼图区那些短数字标签（rightX≈389.91 / 392.59 / 262.17）与图例文字（438.56）的"是否右对齐 = 是否属于同一段"判定随之翻转 —— 这就是 3 组合并差异的来源。

**即：文档页数 → 页眉页脚识别 → 顶层 TextLine 集合 → 段落对齐分位参考 → 段落合并结果。**

## 根本原因（Root Cause）

### A. 饼图无法被识别（缺数据源 + 缺类型）

- artifact 层没有饼图扇形（只有被过滤的白色分界线），`ShapeChunk` 里没有任何"饼图/曲线填充"类型；
- 唯一完整的饼图信息在 `pageFillBoxes`（PDFBox 闭合填充 bbox），但它目前只被 `recognizeBarChartsFromFillBoxes` / 箭头兜底消费，**没有被用于饼图**；
- 于是饼图截图只能由 `FlowchartProcessor` 的"引导线 + 邻近文本"启发式顺带产出 → 必然只覆盖局部（本例只覆盖饼图右上角 + 前两条图例）。

### B. 单页/多页差异（文档范围耦合 + 门限边缘）

链条（全部有实测数据）：**跨页页眉页脚识别**（`HeaderFooterProcessor`，≥2 页才生效）→ 顶层 `TextLine` 集合变化 → **`ParagraphProcessor` 的页面级对齐参考量 `leftX/rightX` 是集合分位数**（27→25 块使 `rightX` 从 473.88 变 456.94）→ 段落合并结果变化（3 组"百分比↔图例文字"）→ `FlowchartProcessor` 簇的 `mergedBox` 高度 **40.601 vs 门限 40** → 有图/无图翻转。

换言之：**决策依赖"整本文档的页眉页脚识别结果"，而判决边界只有 0.6pt 余量。**

## 解决方案

### 方案 1：实现真正的饼图识别（推荐，从根上消除 B）

**数据源**：`DocumentProcessor.extractPageFillBoxes()` 的 `pageFillBoxes`（已存在、已经是 y-up、已按页返回）。

**识别规则（只用 bbox，不需要曲线几何）**：

1. **共角点法**：对每个闭合填充框取 4 个角点；统计"有角点重合（容差 ≈1pt）的框数"，取最大的一簇；
2. **判为饼图条件**：
   - 该簇框数 ≥ 3；且
   - 簇内框的并集 `U` 近似正方形（`|U.w − U.h| ≤ max(4pt, 8%)`），`U` 的尺寸在 `[30pt, 0.5·页宽]`；且
   - 共点角 ≈ `U` 的中心（±2pt）；且
   - 每个簇内框面积 ≤ `0.6·U.area`（防止把嵌套的框当成扇形）；
3. **佐证（可选，用于压误判）**：`U` 附近存在 ≥2 个短百分比文本（`\d+(\.\d+)?%`）或 ≥2 个 ≤12pt 的近方形图例色块，或从 `U` 边缘伸出的细长灰色引导线；
4. **截图区域**：`U` ∪ 引导线形状 ∪ 百分比标签 ∪ 图例（色块列 + 其标签），沿用柱状图那套 region 扩张口径（不含标题 / `单位：` / `数据来源：`）。

**落点（两种）**：

- **A（推荐）**：在 `ShapeRecognizer` 中仿照 `recognizeBarChartsFromFillBoxes` 新增 `recognizePieChartsFromFillBoxes`，产出 `ShapeChunk(union=U, TYPE_PIE_CHART, color=null, components=n, parts=各扇形框)`；再新增 `PieChartProcessor`（或把 `BarChartProcessor` 抽成通用的 `ChartProcessor`，共享 `expandToChartRegion` 一类的区域扩张代码），在 `BarChartProcessor` 之后、`FlowchartProcessor` 之前调用。
  - 优点：完全复用既有"组 → 截图 → 移除被覆盖元素"机制；饼图成为一等公民，不再依赖 `FlowchartProcessor`；`BoundingBoxGroupUtils` 增加 `containsPieChart` 即可。
  - 需要同时让 `FlowchartProcessor` 跳过含饼图的组（与现在跳过 `bar_chart` 同理）。
- **B（轻量）**：新增独立 processor 直接吃 `pageFillBoxes`，需把 fillBoxes 从 `DocumentProcessor` 传下去（改动调用签名）。

**风险**：环形图（donut）、装饰性圆点阵列、雷达图等可能误判；靠"≥3 共角点 + 并集正方形 + 佐证"可压住，建议先用现有样本集回归。

### 方案 2：消除"门限边缘"（与方案 1 互补，解决 B 的脆弱性）

- 把 `FlowchartProcessor` 的 `MIN_HEIGHT/MIN_WIDTH` 硬门限换成更稳健判据（如：形状数 ≥2 + 连接线 ≥2 + 文本 ≥3 + 高度 ≥20pt），不再让 0.6pt 决定成败；
- 顺带理清 `mergedBox` 与 `screenshotBox` 的 ±1pt 差值来源（吸收后续簇时两者都被 union，比值不再等于 margin）；
- 给增长循环加"面积上限 / 不得吞并正文段落"的保护，避免 `[18,18]` 那种把标题+正文吞进图片的情况。

### 方案 3（可选、影响面大）：切断"文档页数 → 段落合并"的耦合

把 `ParagraphProcessor` 的 `leftX/rightX` 改为基于**页眉页脚识别前的文本集合**（或至少把页眉/页脚文本计入统计）。这样任何页面的段落合并都不再随文档页数变化。
**注意**：这是全局行为改变，会影响所有文档的段落/表格/标题合并结果，必须跑回归基线，建议单独排期。
