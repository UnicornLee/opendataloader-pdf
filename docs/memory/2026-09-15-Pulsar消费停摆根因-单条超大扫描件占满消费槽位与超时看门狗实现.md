# opendataloader-pdf 任务记忆 — 2026-09-15（Pulsar `hk_announcement_parse_all` 消费停摆：**一条消息被复制 21 份占满所有消费槽位** + 超时看门狗落地）

> 现象：Pulsar 消费暂停（`hk_announcement_parse_all` 待消费 **25257**），最近 1 小时无消费。
> 结论：**不是"消费者被暂停"，而是 21 个消费槽位被「同一条消息的 21 个副本」占满**——肇事消息只有一条
> （`businessId=1785145532722080227_1344599359112327168`，文件 `202504281785145532722080227.pdf`，超大扫描件），
> 它在 `DocumentProcessor` 的**单线程逐页后处理循环**里要 **11~12 分钟/页**，永远跑不完；
> 而 `ack_timeout_seconds=60` 让 broker 在第 60 秒就把它重投给下一个 consumer，如此 21 次 → 再无空闲 consumer → `msg_rate_out=0`、backlog 冻结。
> 已实施：**方案3（core 侧协作式超时检查点）+ 方案1（消费侧硬看门狗）**，并同时把 `ack_timeout_seconds` 改为 `0`。

## 结论速览（TL;DR）

- 卡住的是订阅 **`hk_announcement_parse_all`**（同 topic）：`back_log=25257`、`unacked_messages=11`、
  `blocked_on_unacked_messages=0`、`consumers_count=21`、`msg_rate_out≈0`、`msg_rate_redeliver≈0`、
  **`pulsar_rate_in=0`（近 24h 完全没有新生产，backlog 全是历史积压）**。
- **根因**：一条超大扫描件消息（见上）在
  `DocumentProcessor.java` 的**单线程逐页循环**（图表/流程图截图 → `LineArtProcessor.haveFormulas` → `ConsecutiveImageProcessor`）中
  **实测 11~12 分钟/页**（同一 host+thread 相邻两页的日志间隔 12.5 / 11.7 / 11.2 / 13.1 分钟，多台主机一致），
  而同环境下另一台健康实例 `192.168.0.136` 跑**同一个循环**可以 **1 秒内完成 52~136 页** → 慢的是**该扫描件的页面内容**，不是循环本身。
- `application-prod.yml` 里 `ack_timeout_seconds=60`、`receiverQueueSize=1`、`SubscriptionType.Shared`、`count=7`
  → **broker 在第 60 秒就把这条消息重投给下一个 consumer**，每个拿到它的线程都从头再算、数小时不返回、永不 ack。
  **24h 内同一个 businessId 被下载 21 次**（21 个不同 `in-<id>` 目录、跨 4 台主机 21 个消费线程）。
- 21 个槽位（3 pod × 7）被这一条消息的副本占满后，订阅里**再无空闲 consumer** → broker 不再投递 →
  `msg_rate_out=0`、`backlog` 冻结在 25257、Kibana 里只剩这些"卡住线程"每 11 分钟吐一行
  `Page N - LineArtChunk count ...`。
- **量化旁证**：近 24h 该订阅 `download pdf success` **7962 次**，但 backlog 只从 26371 降到 25257（**-1114**）→ **约 7 倍重复劳动**；
  近 6h `download=672` / `process pdf success=650`，其中"下载了但从未完成"的业务 ID **只有 1 条**（就是它）。
- 同一现象**在 09-14 已发生过一次**：backlog 从 `12:10` 到 `23:10` 整整 **11 小时恒为 25775**。
- 已实施（用户确认的 5 条口径见后）：
  - **core 侧检查点（方案3）**：新增 `ProcessingDeadline` + `ProcessingTimeoutException`，在
    `DocumentProcessor` 各 phase 边界与**逐页循环**、`JsonWriter`（OCR 链路 + 输出生成）内埋检查点 → 超时**干净回卷**走既有失败路径；
  - **消费侧硬看门狗（方案1）**：`PulsarService` 每条消息跑在独立 worker 线程，`future.get(consum_timeout_min)`；
    超时 → **发 `jsonUrl=""` 结果消息 → ack（不重投）→ 打印 worker 栈（自动 jstack）→ 僵尸计数与升级**；
  - **`ack_timeout_seconds: 60 → 0`**（若不改，看门狗还没到 40 分钟，broker 早就重投了）。

## 定位过程（从问题到根本原因）

### 第 1 步：量化订阅状态，确认是"冻结"而非"慢"

查 `hk_announcement_parse_all`：`back_log=25257`、`unacked=11`、`blocked_on_unacked=0`、`consumers=21`、
`msg_rate_out=0`、`rate_redeliver≈0`、`pulsar_rate_in=0`。

→ 消息"已投递但长期不 ack"；`blocked=0` 排除 broker 端限流；**`rate_in=0` 说明 backlog 不是"消费跟不上生产"，而是"存量彻底不动"**。

### 第 2 步：看趋势，拿到"冻结起点"和一次历史冻结

24h 曲线（`pulsar_subscription_back_log`，UTC）：

```
06:10(昨) 26371 → 12:10 25775 → 23:10 25775 → 00:10 25764 → 03:10 25350 → 04:10 25261 → 05:10 25257 → 06:10 25257
```

→ **`12:10`~`23:10` 整整 11 小时一动不动（25775）**，说明"完全冻结"是**可复现的既有现象**，不是本轮偶发；
→ 本轮冻结起点 ≈ **04:20**（`msg_rate_out` 最后一次非 0 在 04:25 之前，backlog 最后一次变化在 04:20）。

### 第 3 步：先排除"性能型卡住"和"异常打死线程"

- JMX（3 台）：`rate(ProcessCpuTime[1m]) ≈ 4.5` 核（8 核机器）、`ProcessCpuLoad 0.3~0.5`、
  Young GC ≈ **2 次/秒**、heap Max 8.6G / 峰值 99%（`8499470696`）、**无 G1 Old Gen GC**。
  → 线程**在干活**（不是死锁、不是等待），但有明显 GC 压力。
- 进程重启：`process_start_time_seconds` 显示 3 台在 **02:17Z** 重启过；重启日志里
  `SpringApplicationShutdownHook ... thread pulsar-receive-N did not stop within timeout`
  → 佐证这些消费线程当时正卡在长耗时处理里（连关停都 join 不回来）。
- Kibana：近 3h **ERROR = 0**；`haveFormulas failed`、`haveStreamTables failed`、`PaddleOcr` 失败均 **0**；
  4h 内仅 1 条 `handleReceiveMessage failed ...: Parallel page processing failed (UnsupportedOperationException: JPX color spaces don't support draw...)`。
  → **排除**"被异常打死线程"（2026-09-14 那次的病因）和"OCR 服务不可达"。

### 第 4 步：逐线程看日志，发现"大家都在动，但都不前进"

按 `host.name` + `thread_name` 拆开后（`.26/.215/.232` 三台一致），7 个 `pulsar-receive-*` 线程都在活动，
但每 ~5 分钟只吐 **1~2 行**页级日志且**页码在回跳**：

```
.26 / pulsar-receive-0 : p12(05:44) p12(05:50) p10(05:51) p13(05:56) p13(06:02) p14~16(06:07) p11(06:11)
```

单独看某台没问题——**页码回跳**是因为 `pulsar-receive-N` 这个名字在 4 台主机上重名（第 3 步的坑），
按 `host+thread` 分组后页码就严格单调了（见第 6 步的量化）。

### 第 7 步：坐实"ackTimeout 重投 → 副本占满槽位"的因果

- 客户端侧证据：4h 内 **187 条** `[ConsumerBase{subscription='hk_announcement_parse_all' ...}] N messages have timed-out`
  （来自 Pulsar 客户端 `UnAckedMessageTracker`，即被 `ackTimeout` 触发的重投），最后一条在 04:22。
- 服务端侧证据：同一 businessId 在 24h 内被**不同** consumer 下载 21 次（第 5 步清单）。
- 结果：`SubscriptionType.Shared` + `receiverQueueSize=1` + 每个消费线程同步处理 →
  **一旦 21 个线程各自都握着一份"跑不完的副本"，就再没有任何 consumer 有空闲 permit 接收新消息** →
  `msg_rate_out=0`、backlog 冻结、OCR/结果 topic 全部 `rate=0`（整条链路只是"主链路被堵"，不是下游挂了）。

### 第 8 步：量化"重复劳动"总量

| 窗口 | 下载次数 | backlog 变化 | 比值 |
|---|---|---|---|
| 近 24h | **7962** | 26371 → 25257（**-1114**） | **≈7×** |

即：**每推进 1 条消息，平均要重复解析 7 次**。这与"投递 21 次才最终 ack 一次"的机制完全吻合。

### 第 9 步：排除"其他可能"

| 假设 | 证据 | 结论 |
|---|---|---|
| broker 限流/暂停 | `blocked_on_unacked=0` | 排除 |
| 消费线程被 Error 打死（2026-09-14 病因） | 近 3h ERROR=0；线程都在活动 | 排除 |
| CPU 死循环/死锁 | `ProcessCpuTime rate≈4.5` 核，是"在干活"；无 deadlock | 排除 |
| OCR/paddle 服务不可达或超时 | prod `basicFormulaRecognize=false`、`is_immediate_ocr=false`；`haveFormulas failed=0`、`haveStreamTables failed=0`、`PaddleOcr` 失败=0 | 排除 |
| 下游堵塞导致反压 | `hk_announcement_ocr_image_analysis`、`..._result`、`hk_announcement_parse_all_result` backlog/rate **全为 0** | 排除（下游空闲，是上游堵死） |
| 消息本身丢失/未投递 | `pulsar_rate_in=0` 且 backlog 未增长；`producers_count=2` 稳定 | 排除（存量卡死，非生产问题） |

### 第 10 步：把结论写成可验证的判定条件

> **订阅"冻结" = `msg_rate_out=0` 且 `backlog` 长时间不变 且 `consumers_count` 仍等于预期 且 消费线程仍在活动。**
> 此时应当用「**下载了但从未完成**」的业务 ID 去定位毒消息（`download pdf success` 有、`process pdf success` 无），
> 再按 `host.name`+`thread_name` 去数它被复制了几份。

## 根本原因（Root Cause）

**订阅 `hk_announcement_parse_all` 中一条超大扫描件消息（`businessId=1785145532722080227_1344599359112327168`，
`202504281785145532722080227.pdf`）在 `DocumentProcessor` 的"单线程逐页后处理循环"里需要 11~12 分钟/页（全文 ≥300 页，合计数十小时），
永远无法在 ack 超时内完成；`ack_timeout_seconds=60` 于是让 broker 反复把同一条消息重投给其它 consumer，
每个副本都永久占用一个消费线程/槽位；当 21 个槽位被同一条消息的 21 个副本占满后，订阅再无空闲 consumer，
broker 不再投递任何消息 —— 表现为 backlog 冻结、`msg_rate_out=0`、
以及"看起来所有消费线程都活着、却什么都不消费"。**

### 为什么"不是暂停、却像暂停"

| 现象 | 解释 |
|---|---|
| `consumers_count` 一直是 21 | 21 个 `Consumer` 都**连接正常**（线程也没死），只是都在处理"跑不完的副本" |
| `blocked_on_unacked=0` | 远未到 broker 的 unacked 上限，broker 认为一切正常 |
| `unacked=11`（< 21） | 被 `ackTimeout` 重投过的消息会从客户端跟踪器移除，只有当前在跟踪的那部分计入 |
| `msg_rate_redeliver≈0` | 重投是**稀疏事件**（约 1 次/分钟量级），在 5~10 分钟粒度的图上看着像 0 |
| 线程仍在打日志 | 逐页循环每完成一页就吐一行 `LineArtChunk count`，所以"有日志"≠"在前进" |

### 与既往两份记忆的关系（重要修正）

- `2026-09-10-Pulsar消费者ackTimeout兜底防止卡死消息.md` 引入 `ackTimeout=60s` 时，**已知限制第 3 条**就写了：
  > "60s 可能误触……一旦触发重投，原消息会被重新派发到另一个 consumer 实例，与'正在卡死的实例'并行处理，可能产生重复消费。"
  → **本轮就是这条限制被现实放大**：不是"偶尔重复"，而是"一条毒消息把 21 个槽位全部换成它的副本"。结论修正为：
  **ackTimeout 不能短于最坏单条处理时长；当"最坏时长"无法给出上界时，应改为关闭（0）并由消费侧看门狗统一负责超时。**
- `2026-09-14-Pulsar消费停摆根因-消费线程被未捕获Error打死.md` 的病因（`Error` 打死线程 → 槽位永久丢失）与本轮**不同**，
  两者症状相似（都表现为"总有几条不消费"）但机制、证据、修法都不一样，排查时要先分清：
  - 上一次：**线程不在** jstack 里 / 日志静默 → 线程死亡；
  - 这一次：**线程都在** 且每分钟都在打页级日志 → 线程被"跑不完的消息"占住。

## 已实施改动（方案3 + 方案1）

用户口径：① 超时后**要**发结果消息 `jsonUrl=""`；② 采纳僵尸上限 + 告警/自愈；③ **OCR 链路同样处理**；
④ 超时值放 yml、键名 **`consum_timeout_min`**（40）；⑤ 采纳"超时自动打印 worker 线程栈"。

### core 模块（`opendataloader-pdf-core`，源码级别 **11**）

| 文件 | 内容 |
|---|---|
| `utils/ProcessingDeadline.java` **新增** | 协作式处理预算。`ThreadLocal<Long>` 存**绝对** deadline（`NEVER=Long.MAX_VALUE`）；API：`start(ms)`/`clear()`/`snapshot()`/`inherit()`/`remainingMillis()`/`expired()`/`check(stage)`/`check(deadline, stage)`，以及供 `parallel()` lambda 使用的**非受检**版本 `checkUnchecked(...)`（包成 `UncheckedIOException`，与既有 `ContentFilterProcessor` 的失败方式一致）。**关键点：`ThreadLocal` 不会被 `ForkJoinPool` 工作线程继承，所以并行 phase 用 `snapshot()` 在属主线程捕获值、再用显式重载检查。** |
| `exceptions/ProcessingTimeoutException.java` **新增** | `extends IOException`，语义为"预算耗尽（受控中止）"而非"管线故障" |
| `processors/DocumentProcessor.java` | 在 `processDocument` 开头 `final long deadline = ProcessingDeadline.snapshot();`，随后在 **Loop1 / Loop2 / Loop3 / headings 的并行 lambda**、**OCR fallback 循环**、**hidden-text 循环**、**`685-724` 的单线程逐页循环**（本次真正卡点，日志带页码/总页数/文件名）、**ID 分配循环**、**跨页后处理前** 各埋检查点；`catch (Exception e)` 里若 cause 是 `ProcessingTimeoutException` 则**原样抛出**（不再包成 `Parallel page processing failed`），便于上游识别"超时"而非"管线坏了" |
| `json/JsonWriter.java` | OCR 链路 `rebuildBookmarksFromJson`：读 JSON 后 / 解析 related_ids 前 / 写回前 / OBS 上传前 各一个检查点；`writeToCustomJson` 的**逐页输出循环**也加（"generating outputs" 实测最长占过 16 分 47 秒） |

> 为什么"检查点"是必要的（不能只靠看门狗）：Java **无法安全地强杀线程**，
> `Thread.interrupt()`/`shutdownNow()` 只对阻塞在 IO 的代码有效，对 PDFBox/veraPDF 的纯 CPU 循环无效。
> 检查点让"跑不完的文档"在**下一个页边界**干净回卷：走既有 `catch → jsonUrl="" → ack` 路径，
> **不留下孤儿线程**；被放弃的 worker 最多再多跑一页（≈12 分钟）就会自己退出，而不是继续跑几十小时。

### server 模块（`opendataloader-pdf-server`，JDK 17）

| 文件 | 内容 |
|---|---|
| `config/PulsarProperties.java` | 新增 `@DefaultValue("0") int consumTimeoutMin`（读 `pulsar.consum_timeout_min`，0=关闭）；类注释说明它与 `ack_timeout_seconds` 的关系 |
| `pulsar/PulsarService.java` | 见下 |
| `application-*.yml`（8 个） | `ack_timeout_seconds: 60 → 0`，新增 `consum_timeout_min: 40`（带英文注释说明原因） |

`PulsarService` 的具体做法：

```java
// 消费循环：receive 之后交给看门狗（看门狗内部再决定内联还是起 worker）
msg = consumer.receive();
try { runWithWatchdog(consumer, msg, this::handleReceiveMessage); }   // 包 try/catch，异常不逃逸
catch (Throwable e) { log.error("pulsar receive watchdog error: {}", ...); sleepBriefly(); }
```

- `runWithWatchdog(...)`：
  - `consum_timeout_min<=0` → **完全走原内联路径**（线程数、行为都不变，方便随时关掉）；
  - 否则为每条消息起一个 worker（`pulsar-work-<consumerName>`，daemon），worker 内先
    `ProcessingDeadline.start(同一 budget)`，消费线程 `future.get(consum_timeout_min)`。
- `onMessageTimeout(...)`（看门狗触发）：
  1. 打 `log.error("message processing TIMEOUT after {} min, force-ack and skip (no redelivery): businessId=..., consumer=..., abandonedWorkers=... Stuck worker stack:{}")`，
     其中栈来自 `ThreadMXBean.getThreadInfo(..., Integer.MAX_VALUE)` 过滤 `pulsar-work-` 前缀——
     **下次不用再人工上 pod 跑 jcmd**（本轮定位就靠人工 jstack/日志拼出来的）；
  2. **发结果消息 `jsonUrl=""`**（与其它失败一致的语义，下游可自行 `retry_pdf_parse`）；
  3. **`acknowledgeQuietly(...)` —— 不重投、不落地 DLQ**；
  4. `worker.shutdownNow()`（尽力而为）；
  5. `escalateIfTooManyAbandoned(...)`：**存活**僵尸数 ≥ `count+ocrCount` 打 error；≥ 2 倍则 `System.exit(1)` 交给 K8s 重启换干净堆。
- 僵尸计数用**存活数**而非累计数：被放弃的 worker 若最终自己结束，会在 `finally` 里 `decrementAndGet()` 并清理 executor 引用。
- `handleReceiveMessage` / `handleOcrReceiveMessage` 改为接收
  `AtomicReference<Object> businessIdRef`、`AtomicReference<Map<String,Object>> extendRef`、`AtomicBoolean abandoned`：
  解析出 payload 后**尽早回填**两个引用（看门狗据此报告身份，即使 worker 已卡在下载阶段也有兜底重新解析）；
  被放弃后**跳过"发结果 / ack"**，避免同一条消息被上报两次。
- `validateTimeoutConfiguration()`（启动时）：若 `ack_timeout_seconds > 0` 且**短于** `consum_timeout_min`，
  打一条明确的 error，指出"broker 会在看门狗之前把消息重投给别的 consumer"。这是刻意的防呆（本轮故障的配方）。

### 行为对照

| 场景 | 改前 | 改后 |
|---|---|---|
| 正常消息 | 内联处理 → ack | 多一层 worker，但预算远未到，行为等价 |
| 慢但能跑完（< 40 分钟） | 可能被 ackTimeout 重投 → 多副本 | 单副本跑完 → ack（且 7962/1114 ≈ 7 倍重复劳动消失） |
| **跑不完（如本条）** | 被重投 N 次，直到占满所有槽位 → **订阅冻结** | **40 分钟到点：发 `jsonUrl=""` → ack → 继续下一条**；core 检查点通常在下一个页边界先行干净回退 |
| 被放弃的 worker | — | 日志留栈；最多再多跑一页后自行退出；存活僵尸超阈值时 error / 重启 |

## 关键决策（Key Decisions）

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| 1 | 是否只把关掉的 `ackTimeout` 当作唯一修法 | 否。**方案3（检查点）+ 方案1（看门狗）** 双管 | 检查点能干净回卷不留孤儿；看门狗是机制无关的硬边界，兜住检查点失效的残余场景 |
| 2 | 超时后的下游语义 | **发 `jsonUrl=""` 结果消息**（用户明确要求） | 与既有"失败也上报"契约一致，下游可自行决定是否重试 |
| 3 | 超时后是否重投 / 进 DLQ | **不重投**，只打日志 + ack | 符合用户要求；也避免"毒消息循环"（nack→重投→再超时） |
| 4 | OCR 链路 | **同样加**看门狗与检查点 | 两条链路共用 `ack_timeout_seconds`/连接池与线程模型，问题同源 |
| 5 | 配置键与默认值 | **`pulsar.consum_timeout_min`，默认 0（关闭）**，8 个 yml 显式设 `40` | 默认关闭保证"不改配置就不改变行为"；生产显式 40 |
| 6 | `ack_timeout_seconds` | **60 → 0** | 只要它短于看门狗，broker 就会抢先重投；两者不能并存（已加启动校验） |
| 7 | 僵尸上限与自愈 | 软阈值 `count+ocrCount` 告警、硬阈值 2 倍 `System.exit(1)` | 一个毒消息占 1 个僵尸是正常的；成堆出现说明在滑向 OOM，重启比慢死好 |
| 8 | 是否顺手把逐页循环并行化 | **不做**（另立任务） | 用户本轮只要"不再堵"，且并行化需要独立回归基线与性能验证 |

## 遗留 / 后续

1. **根因本身（逐页循环 11~12 分钟/页）未修**：本轮只是让"堵"变成"跳过"。建议单独排期：
   对该循环并行化 / 对巨型扫描件设页数或时间上限并转异步 OCR 通道 / 定位页内哪个子步骤慢（需要一次带 CPU 采样的 jstack 或 async-profiler）。
2. **临时目录泄漏**：被放弃且**永不返回**的 worker 不会执行到临时目录清理，`/tmp/pdf_parse` 会残留；
   需要补一个"陈旧临时目录 GC"（按 mtime 清理）。
3. **`abandonedWorkers` 的软/硬阈值目前按 `count+ocrCount` 推导**，未做成配置项；若线上需要调整再补 key。
4. **上游可观测性**：建议给"超时被跳过"的消息加一个业务侧计数/告警（现在只有 error 日志），
   并考虑把超时事件的 `businessId` 也写进结果消息的 `extend`，方便下游区分"失败原因"。
5. **确认 namespace 策略**：`pulsar-admin namespaces get-policies capital/pdf_parse` 应确认 `ackTimeoutMillis` 也是 0/未设置，
   否则 broker 侧仍可能独立触发重投（客户端 `ackTimeout` 与 namespace 策略是两条不同的通道）。
6. **部署动作（需人工）**：本次改动上线后，**已被占住的 21 个槽位不会自动恢复**，需滚动重启 3 台 pod（或按名跳过那条毒消息）才能立刻恢复消费。
7. 未定论：`program=opendataloader-pdf-server-hk` 在 `192.168.0.136` 上跑的是不是 `prod-inc`（增量链路）——若确认，
   说明本次 3 台是 `prod`、`.136` 是 `prod-inc`，两者不要混在一起分析。
