## 1. 现象

用户报告：第 5 页 `預 期 時 間 表` 这行解析出来的 **font_size 偏小**，怀疑是右边的上角标导致的；
要求"设置该行文本字体大小时忽略角标的字号，除非整行都是角标"。

跑 `DebugSample` 拿到的基线 JSON 里，这一行是：

```
content   = '預 期 時 間 表 <sup>( 1 )</sup>'
font_size = 7.579          ← 明显偏小，正是右侧角标 "( 1 )" 的字号，而非标题字号
x0=251.404  x1=343.872  y0=37.895  y1=50.61
source_type = heading（父段落同样被带偏为 7.579）
```

`7.579` 是右侧上角标 `( 1 )` 的字号；标题 `預 期 時 間 表` 本身是更大的字号（修复后确定为 **13.0**）。

---

## 2. 结论速览（TL;DR）

1. **根因只有一个：`JsonWriter.computeLineFontSize` 是"按字符"统计字号取众数的，而它统计的字符里包含了
   `<sup>` / `</sup>` 这两个 HTML 标记里的 `s`、`u`、`p` 字母，以及角标本身的字符。**
   `TextLineProcessor` 早先把角标 chunk 的 value 包成了 `<sup>( 1 )</sup>`；`computeLineFontSize` 直接
   `chunk.getValue().charAt(i)` 逐字符遍历，`isFontSizingChar = Character.isLetter || isDigit` 把标记里的
   `s/u/p` 当成拉丁字母计入，于是角标块以**小字号**被计了 **7 次**（`s u p 1 s u p`），压过标题 5 个 CJK 字的
   **大字号 5 次**，众数从"标题字号"翻转成"角标字号" 7.579。
2. **两层污染叠加**：① 标记字符串 `s/u/p` 纯属误伤（它们根本不是可见文本）；② 角标真实内容 `1` 即便剥掉标记也
   仍会以小字号计入。只解其一不够，必须两者都排除。
3. **修复放在 `computeLineFontSize` 单点即可**：先剥标签、再把角标块的字号收进独立池，只有"整行都是角标"时才回退
   用该池。`<sup>/<sub>` 由 `TextLineProcessor` 生成，直接复用它作判据最稳妥，不新增视觉启发式。
4. **段落级 font_size 一并被修好**：heading/list/caption/TOC/paragraph 五类的行级都走 `computeLineFontSize`，
   段落级聚合 `computeFontSizeFromCollection(lineFontSizes)` 喂的正是修正后的行值，无需另改。
5. 端到端验证：同一行 font_size **7.579 → 13.0**；`JsonWriterLineFontSizeTest` 8 个用例全绿。

## 3. 完整定位过程（从问题到根因）

### 3.1 先回忆既有"行字号"策略，锁定嫌疑方法

`SearchMemory` 命中的既有规范（"行字体大小计算规则"、"PDF 解析中字体大小的双阶段众数/平均数计算策略"）说明：
本项目**已经**把行级 font_size 改为"取 chunk 集合的众数/平均"，且早先为**目录点引导线（dot leader）**做过
"从按 chunk 改按字符统计"的修复（见关联记忆 2026-10-08 那篇）。所以本次不是不了解字号从哪来，而是要看
**按字符统计的规则为什么在本样本上翻车**。

`grep computeLineFontSize` → 全部落在 `JsonWriter.java`，共 5 处调用：heading(L723)、list(L772)、caption(L821)、
TOC(L858)、paragraph(L932)；本例 `source_type=heading` 走 L723。

### 3.2 读按字符统计的实现，发现它把标签也算进去了

`JsonWriter.computeLineFontSize`（原实现核心）：

```java
for (TextChunk chunk : textChunks) {
    String value = chunk.getValue();               // ← 直接取原始 value
    double size = chunk.getFontSize();
    for (int i = 0; i < value.length(); i++) {     // ← 逐字符
        char ch = value.charAt(i);
        if (!Character.isWhitespace(ch)) allSizes.add(size);
        if (isFontSizingChar(ch)) significantSizes.add(size);   // isFontSizingChar = isLetter||isDigit
    }
}
if (!significantSizes.isEmpty()) return computeFontSizeFromCollection(significantSizes); // 众数优先
```

`computeFontSize` 的取法：四舍五入到 3 位后找**唯一众数**，无唯一众数才取平均。也就是说
"哪种字号的字符数最多且唯一"就取谁。

### 3.3 关键：`value` 里为什么会有 `<sup>` —— 回溯到 TextLineProcessor

`grep 上角标/sup` → `TextLineProcessor`（带 `imagesDirectory` 的 `processTextLines` 重载）里有一段角标识别，
把检测到的上/下标 chunk 的 value **就地包裹**：

```java
// TextLineProcessor.java（行内 chunk 读序排序后）
if (prevChunk.getFontSize() - currentChunk.getFontSize() > 2.5) {   // 前大后小 → 疑似角标
    ...
    currentChunk.setValue("<sup>" + currentChunk.getValue() + "</sup>");   // 上标
    // 或 currentChunk.setValue("<sub>" + ... + "</sub>");                 // 下标
}
```

`grep processTextLinesCustom|processTextLines` 确认调用方：`DocumentProcessor.java:661` 用的正是
**带 imagesDirectory 的两参重载**（即含角标包裹的这条自定义路径），所以本 PDF 的角标 chunk 在到达
`JsonWriter` 之前就已经是 `<sup>( 1 )</sup>` 形态。

`JsonWriter.getText` 里只做 `text.replaceAll("</sup><sup>", "")`（合并**相邻**两段角标），单个 `<sup>…</sup>`
标记**原样保留**在 chunk.getValue() 里 —— 这解释了 `computeLineFontSize` 为什么会看到 `s/u/p`。

### 3.4 把数（本样本实测的计数）

标题块 `預 期 時 間 表`：`isFontSizingChar` 命中 `預 期 時 間 表` = **5 个** 大字号（空格不算 letter/digit）。
角标块 `<sup>( 1 )</sup>`：命中的是 `s u p`（来自 `<sup>`）+ `1` + `s u p`（来自 `</sup>`）= **7 个** 小字号。

```
significantSizes = [大,大,大,大,大,  小,小,小,小,小,小,小]
                                     └──── 7 个小字号 ────┘
唯一众数 = 小字号 = 7.579   →   整行被判成角标字号（缺陷原形）
```

5 < 7，众数被角标（含误伤的标签字母）抢走，标题真实字号 13.0 完全落选。

### 3.5 用 DebugSample 端到端复现取证

无 Python PDF 库（`pip list` 无 pdfplumber/PyMuPDF），改走 Java：

```powershell

$env:CLASSPATH = "$core\target\classes;$deps"   # deps 取自 cp.txt，避免命令行超长/转义

```

产物 `tmp_output/20260507AN202606291826520711.json`，用脚本 walk 出含"預…期…時"的行，拿到上面
`font_size = 7.579`、`content = '預 期 時 間 表 <sup>( 1 )</sup>'` 的基线证据。

### 3.6 反向验证：新单测真的抓得住老 bug

在测试里按真实几何构造 `chunk("預 期 時 間 表",16.0)` + `chunk("<sup>( 1 )</sup>",8.0)`，
用反射调私有 `computeLineFontSize`：旧实现返回 **8.0**（被标签字母+角标抢位），新实现返回 **16.0**；
"整行只有角标"用例如 `chunk(" ",16.0)+chunk("<sup>( 1 )</sup>",8.0)` 则应回退到 **8.0**，
锁死"除非整行都是角标"这条语义。

## 4. 根因

| 层 | 事实 | 定性 |
|---|---|---|
| 统计口径 | `computeLineFontSize` 按 `chunk.getValue()` 逐字符，`isFontSizingChar=isLetter\|\|isDigit` | **代码缺陷：未排除非可见的标记字符** |
| 触发源 | `TextLineProcessor` 把角标块包成 `<sup>…</sup>`/`<sub>…</sub>`，`getText` 又不删除单个标记 | **上游表示约定**（把排版语义塞进 value 文本） |
| 计数翻转 | 标题 5 个大字号 vs 角标块 7 个小字号（含误伤 s/u/p） | **众数判据被污染的直接后果** |
| 传播 | 段落级 `computeFontSizeFromCollection(lineFontSizes)` 复用行值 | 派生：行错则段落错 |

与 2026-10-08 "目录点引导线抢字号" 属同族：**按字符统计字号时，混进正文的非正文字符（点线 / 标签字母）以数量优势抢走众数**。
区别在于那次是 `.` 引导线小字号，本次是 `<sup>` 标记的 `s/u/p` 被误当字母。

## 5. 修复清单

### `JsonWriter.computeLineFontSize`（主修复）

遍历每个 chunk 前：

1. `boolean isScript = isScriptChunk(value)` —— `value.startsWith("<sup>") || value.startsWith("<sub>")`；
2. `String display = stripScriptTags(value)` —— 去掉 `<sup></sup><sub></sub>`，**只对可见字符计数**；
3. 字符计数按"是否角标块"分流到两对池：正文 `significantSizes/allSizes` vs 角标 `scriptSignificantSizes/scriptAllSizes`。

取值优先级（新增的两条角标回退插在正文之后）：

```
significantSizes（正文字母数字）  → 非空即用（本例=13.0）
→ scriptSignificantSizes（整行皆角标时）
→ allSizes（正文非空白）
→ scriptAllSizes（角标非空白）
→ 兜底：per-chunk sizes（全空白/空块，防 0.0）
```

新增两个私有工具方法 `isScriptChunk(String)` / `stripScriptTags(String)`，并给 `computeLineFontSize`
补了说明角标处理的 javadoc。因 `TextLineProcessor` 未在本文件 import，javadoc 的 `{@link}` 用**全限定名**
`org.opendataloader.pdf.processors.TextLineProcessor`（与本文件既有 `{@link}` 写法一致），避免 javadoc 解析失败。

### `JsonWriterLineFontSizeTest`（+3 用例，5 → 8）

- `superscriptMarkerIsIgnoredForATitleLine`：标题 16.0 + `<sup>( 1 )</sup>` 8.0 → 期望 16.0
- `subscriptMarkerIsIgnoredForATitleLine`：标题 16.0 + `<sub>( 2 )</sub>` 8.0 → 期望 16.0
- `lineMadeEntirelyOfSuperscriptKeepsTheMarkerSize`：空格 + `<sup>( 1 )</sup>` 8.0 → 期望 8.0（整行皆角标）

## 8. 经验教训

1. **凡"按字符统计某属性"的逻辑，先确认统计口径里混进了哪些"非可见字符"。**
   本例 `computeLineFontSize` 把 `<sup>` 标记的 `s/u/p` 当正文，与前次把 dot leader 的 `.` 当正文是同一类坑：
   **表示层的标记/装饰字符污染了内容层的统计**。用 `value` 计数前必须剥离所有非渲染文本。
2. **排版语义被编码进 value 文本时，下游每一处按 value 遍历的代码都得重新审视。**
   `TextLineProcessor` 用 `<sup>` 字符串承载"这是角标"，但 `JsonWriter` 有多处 `charAt` 遍历 value
   （`getText`、`computeLineFontSize`、`isChinese` 判邻接…），一处没考虑标记就会出错。更稳的做法本可以是
   在 chunk 上带一个布尔标志而非塞进 value；本次以最小改动在统计侧剥离，未回炉改表示层。
3. **"角标/装饰"类应显式定义"忽略它，除非它是唯一内容"的两段式回退。**
   把角标字号单列一池、正文池空时才回退，既满足"忽略角标"又不让"纯角标行"塌成 0.0。
4. **改 pom/删测试这类"扩大改动面"的动作要显式征得同意。** 它们与本缺陷无关，但会挡住验证；先隔离说明、
   再按用户选择处理，避免把不相关风险混进一次修复。
5. **PowerShell 跑 Maven/Java 的老坑复用**：长 classpath 用 `$env:CLASSPATH`（取自 `cp.txt`）而非命令行拼接；
   含点号的 `-D` 参数、含空格的 `-join`、含括号的 commit message 都要走"写文件/脚本"或 `--%`/`-F` 规避
   （详见既有 tool_experience / common_pitfalls 记忆）。
