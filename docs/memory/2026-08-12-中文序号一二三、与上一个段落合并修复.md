# 中文序号 "一、" "二、" "三、" 与上一个段落合并的根因分析与修复

**日期**：2026-08-12
**分支**：valueonline-20260722
**问题文件**：`docs/pdf/202303251679660111823147-11.pdf`（第 1 页）

---

## 现象

PDF 第 1 页包含：

```
备查文件目录
一、载有公司负责人、主管会计工作负责人、会计机构负责人（会计主管人员）签名并盖章的财务报表；
二、报告期内公开披露过的所有公司文件的正本及公告原稿；
三、其他备查文件。
以上备查文件的备置地点：公司董事会办公室。
```

解析后 "一、载有公司负责人…" 和 "二、报告期内…" 被合并到同一个
`source_type: paragraph` 的 item 中，但 "三、其他备查文件。" 仍正确独立成段。
（与 2026-08-12 修复 "1、" 时的症状类似。）

期望："一、" 和 "二、" 应当各成一段，与 "三、" 行为一致。

---

## 根因（比上次 "1、" 修复更深一层）

`ParagraphProcessor.prejudgeParagraphs()` 的 merge 判断流程如下：

1. `prejudgeParagraphs()` 内部的多条 `else if` 分支按顺序检查是否需要 break。
2. **line 325-326 的分支（左右对齐且 `prevLastLineLeftX ≈ nextFirstLineLeftX`）被命中**：
   - "一、" 和 "二、" 的 `leftX` 都是 `74.664`
   - 所以进入内层 if-else
3. 内层三个条件：
   - line 327-329：`SENTENCE_ENDING_PUNCTUATION` 包含前置行末字符 → "；" 不在 → False
   - line 331-333：下一行有缩进 (`nextFirstLineLeftX - nextTwoLeftX > 10`) → 0 > 10 False
   - line 334 (else) → **直接 merge，没有 isLabeledLine 检查 �**

之前 "1、" 修复（`docs/memory/2026-08-12-中文序号1、与上一个段落合并修复.md`）
**没有触发这个 bug**，因为：
- "产投资风险…具体如下：" 的 `leftX = 56.664`，"1、前期…" 的 `leftX = 84.744`
- 两个 `leftX` 不同 → line 325-326 outer condition **False** → 根本没进入内层分支
- merge 落到后续的 `areLinesOfParagraphsWithLeftAlignments()`（那里有 `isLabeledLine` 检查）
- 上次加的正则 `^\d+、.*` 就够了

但 "一、" 和 "二、" 都是 `leftX = 74.664`，**几何条件刚好把合并推进到
`prejudgeParagraphs()` 的 inner else —— 这是个没有 isLabeledLine 防护的死角**。

## 关键教训

`prejudgeParagraphs()` 的 inner else 是个合并死角 — 当前后两行 `leftX` 相同、
margin 相似、且前置行不以句末标点结尾时，会**直接合并**而**不经过任何
`isLabeledLine` 防护**。下次若出现类似 "中文标点 + 序号" 场景，需要同时：
1. 扩展 `BULLET_REGEXES`
2. 确认 `prejudgeParagraphs()` 的 inner else 不绕过该检查

（本次修复通过在 inner else 前增加 `isLabeledLine` 检查，把这个死角堵上了，
后续扩展 BULLET_REGEXES 时不再需要单独打补丁。）
