## 定位过程

### 第一步：确认受影响的表格形态

`202304291682681121000817-176.pdf` 中的表格只有上下横线和内部竖线，**左右两侧没有竖线边框**。这种表格在 PDF 中很常见，尤其是财务附注类表格。

### 第二步：锁定 Layer 2 改动

当前 `veraPDF-wcag-algs` 中的修改有两处：
1. `LinesPreprocessingConsumer.java`：对 `getStrokeColor()` 做空值保护，并将 `null` 视为黑色。
2. `TableBorder.java` 的 `calculateXCoordinates()`：新增 Layer 2，删除"无竖线支撑"的边缘 X 坐标。

由于用户报告的是"表格识别不出来"（`TableBorderBuilder` 数量或表格被丢弃），而 `LinesPreprocessingConsumer` 的颜色处理与边框 builder 数量无关，首先怀疑 Layer 2。

### 第三步：复现单元测试

在 `TableBorderDanglingLineTest` 中新增一个最小复现：
- 上边框：x=100 → 300，y=400
- 下边框：x=100 → 300，y=100
- 内部竖线：x=200，y=100 → 400
- 左右无竖线

运行后发现 `TableBorder.getNumberOfColumns()` 为 0，确认复现。

### 第四步：分析 `calculateXCoordinates()`

原 `calculateXCoordinates()` 流程：
1. 对所有顶点按 X 聚类，得到候选 X 坐标列表。
2. 对首尾坐标调用 `hasVerticalLineSupport(x, builder)`。
3. 若不支持，则删除该边缘坐标。

对于两侧无竖线的表格：
- x=100 和 x=300 这两个边缘坐标仅来自上下横线的端点。
- `hasVerticalLineSupport()` 只检查 `builder.getVerticalLines()`，竖线只有 x=200。
- 因此 x=100、x=300 都被删除，仅剩 x=200。
- `xCoordinates.size() < 2` → `createMatrix()` 中 `numberOfColumns < 1` → 表格被丢弃。

而目标 PDF 的悬空线场景：
- 最右侧竖线在 x=300，悬空线端点在 x=350（或 x≈539.62）。
- x=350 只有一条横线端点支撑，删除它正是我们想要的行为。

所以问题本质是：**Layer 2 无法区分"单条悬空线端点"和"合法的部分边框表格边缘"**。

### 第五步：设计区分条件

关键观察：
- 悬空线：通常只有 **1 条**横线越过边界，产生孤立端点。
- 部分边框表格边缘：通常有 **多条**横线（上边框、下边框，甚至内部行分隔线）在同一 X 处结束。

因此，除竖线支撑外，若某边缘 X 坐标有 **至少两条不同横线的端点** 支撑，则应保留。

### 第六步：验证方案

在 `TableBorder.java` 中新增 `hasHorizontalEdgeSupport(x, builder)`：
- 遍历 `builder.getHorizontalLines()`。
- 统计左端点或右端点与候选 X 距离 ≤ `VERTICAL_LINE_SUPPORT_EPSILON` 的横线数量。
- ≥2 条返回 true。

边缘裁剪条件改为：
```java
while (... && !hasEdgeSupport(x, builder)) { ... }
// hasEdgeSupport = hasVerticalLineSupport || hasHorizontalEdgeSupport
```

单元测试验证：
- 悬空线场景：x=350 只有 1 条横线支撑，仍被删除。
- 部分边框场景：x=100 和 x=300 各有 2 条横线（上下边框）支撑，被保留。

## 改动清单

### 1. `veraPDF-wcag-algs/src/main/java/org/verapdf/wcag/algorithms/entities/tables/tableBorders/TableBorder.java`

**(a) `calculateXCoordinates()` 边缘裁剪条件改为组合判断：**

```java
while (candidateXCoordinates.size() > 2 &&
        !hasEdgeSupport(candidateXCoordinates.get(0), builder)) {
    candidateXCoordinates.remove(0);
    candidateXWidths.remove(0);
}
while (candidateXCoordinates.size() > 2 &&
        !hasEdgeSupport(candidateXCoordinates.get(candidateXCoordinates.size() - 1), builder)) {
    int lastIndex = candidateXCoordinates.size() - 1;
    candidateXCoordinates.remove(lastIndex);
    candidateXWidths.remove(lastIndex);
}
```

**(b) 新增/调整支撑判断方法：**

```java
private boolean hasEdgeSupport(double xCoordinate, TableBorderBuilder builder) {
    return hasVerticalLineSupport(xCoordinate, builder)
            || hasHorizontalEdgeSupport(xCoordinate, builder);
}

private boolean hasVerticalLineSupport(double xCoordinate, TableBorderBuilder builder) {
    for (LineChunk verticalLine : builder.getVerticalLines()) {
        if (Math.abs(verticalLine.getCenterX() - xCoordinate) <= VERTICAL_LINE_SUPPORT_EPSILON) {
            return true;
        }
    }
    return false;
}

private boolean hasHorizontalEdgeSupport(double xCoordinate, TableBorderBuilder builder) {
    int count = 0;
    for (LineChunk horizontalLine : builder.getHorizontalLines()) {
        if (Math.abs(horizontalLine.getLeftX() - xCoordinate) <= VERTICAL_LINE_SUPPORT_EPSILON ||
                Math.abs(horizontalLine.getRightX() - xCoordinate) <= VERTICAL_LINE_SUPPORT_EPSILON) {
            count++;
            if (count >= 2) {
                return true;
            }
        }
    }
    return false;
}
```

**(c) 常量注释更新：** `VERTICAL_LINE_SUPPORT_EPSILON` 现在也用于横线端点距离判断。

### 2. `veraPDF-wcag-algs/src/test/java/org/verapdf/wcag/algorithms/semanticalgorithms/TableBorderDanglingLineTest.java`

新增回归用例 `testPartialBorderTableKeepsEdgeColumns()`：
- 构造只有上下横线 + 1 条内部竖线的表格。
- 断言 `getNumberOfColumns() == 2`。
- 断言左右边缘分别为 x=99.5 和 x=300.5。

## 关键决策与坑点

- **为什么用横线端点数量而不是 Y 跨度？** 悬空线通常只有 1 条；合法边缘至少有上下两条边框。用数量 ≥2 即可区分，无需额外 Y 跨度阈值，逻辑最简。
- **`VERTICAL_LINE_SUPPORT_EPSILON` 复用**：该常量 1.0 pt 对横线端点同样合适，避免引入新阈值。
- **为什么不在 `LinesPreprocessingConsumer` 层截断悬空线？** 之前尝试过 Layer 1，会破坏 `TableBordersTests` 中依赖现有贪婪合并行为的用例，风险更高。在 `TableBorder` 层做 X 坐标过滤更局部、更可预测。
- **`null` 颜色处理的小插曲**：在加空值保护时最初把 `null` 视为"非黑色"，导致 `TableBordersTests` 中两份无颜色信息的测试 fixture 被错误过滤（`af_css_js_sort_table`、`TLC2-Tables`）。后改为把 `null` 视为黑色/未知，回归测试才全绿。
