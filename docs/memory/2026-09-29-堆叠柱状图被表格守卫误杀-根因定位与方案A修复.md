## 2. 定位过程

### 2.1 确认漏图发生在"识别层"而非"输出层"

对比项只有 `image` 缺失、`lattice_table`/文本完全不变，且缺失图的 bbox 位置没有冒出任何替代内容
→ 不是 JSON 序列化问题，而是这几页从未生成 image chunk。

### 2.2 找到嫌疑代码：`BarChartProcessor` 里的表格 veto

`processChartGroups`（`BarChartProcessor.java`）里有一段**未在任何日记/备份补丁中出现过的守卫代码**：

```java
if (liesInsideTable(pageContents, groupBox) || looksLikeTableGrid(group)) {
    skipped[i] = true;
    continue;
}
```

配套常量：`TABLE_OVERLAP_RATIO=0.5`、`MIN_TABLE_GRID_RECT_COUNT=6`、
`TABLE_GRID_ROW_TOLERANCE=3.0`、`MIN_TABLE_GRID_ROW_COUNT=3`。

**这段守卫的来历**：不在任何 `tmp_debug/*.patch` 备份和 `.codebuddy/memory` 日记里，
是 2026-09-28 会话直接写进工作区的改动（当时 `tmp_debug/ab_veto.ps1` 还在对 `TABLE_OVERLAP_RATIO`
做 0.5↔2.0 的 A/B），**没有单测、没有在 20260507 这份招股书上回归过**。
（教训：工作区里随时可能有这种"幽灵改动"，遇到回归差异要先 `git diff` 排雷。）

### 2.3 查清守卫当初保护的是什么

`tmp_output_p20230420_guard` 就是守卫的验证运行（当时只跑了 3 页）：20230420 文档的
p137/195/243 上，**填充单元格表格**（表内底色块被识别成 bar_chart 复合块）曾被裁成柱状图截图。
守卫的两个判据：
- `liesInsideTable`：图形区 ≥50% 落在 `TableBorder`/`Table` 内 → 不截图；
- `looksLikeTableGrid`：组内 bar_chart/rectangle 分量**底边 Y 聚类 ≥3 簇且分量数 ≥6** → 认为是填充表格网格，不截图。

→ 守卫本身有必要，不能直接回退。

### 2.4 确认误杀机制：堆叠柱段底边 Y 各不相同

用探针 `tmp_debug/probe_src/org/opendataloader/pdf/processors/P111115Dump.java` dump 这几页
bar_chart 复合块的 component bbox，发现 4 页**全是堆叠柱状图**：

- p111：11 个分量、底边 4 簇（基线段 6 个底边 Y 相同，3 层堆叠段各 1 个不同底边）；
- p113：7 根柱 × 3 层 = 21 个分量，底边 3 簇；
- p114/p115：同类 3 层堆叠。

堆叠柱里，**除贴基线的段外，每段的起止 Y 由下方各段高度之和决定，各不相同** →
底边 Y 簇数 = 层数 ≥3，分量数 ≥6 也必过 → `looksLikeTableGrid` 恒真 → `skipped[i]=true` 跳过截图。
而普通柱图（p110）所有柱段共享同一基线，底边只有 1 簇，不会误中。

### 2.5 因果验证：临时禁用 veto，图片全部回归

临时给 veto 加 `-DdisableTableGridVeto` 开关（验后已恢复）重跑 6 页：
p111/p113/114/115 的 image 全部回归，bbox 与 after7_full **逐点一致**；
p110/p117 本来就正常、不受影响。
→ 确认唯一凶手是 `looksLikeTableGrid`（`liesInsideTable` 在这 4 页不触发）。
产物：`tmp_output_p111_115_noveto/`（对照）、`tmp_output_p111_115_check/`（复现）。

## 3. 根因

`looksLikeTableGrid` 的"底边 Y 多簇 = 表格行"假设对**堆叠柱状图不成立**：
堆叠段底边天然各不相同（层数 = 簇数），一个几何特征同时是"表格行"和"堆叠层"的证据，
单看底边簇无法区分两者。守卫作者（09-28）只验证了它保护 20230420 填充表格的场景，
没有在堆叠柱样本上回归。

## 4. 修复（方案 A，用户选定；未提交）

改动**仅 `BarChartProcessor.java`**（改动前备份：`tmp_debug/barchart_table_grid_guard_backup.patch`）：

1. `looksLikeTableGrid` 里先收集分量 `BoundingBox`（原来只收底边 Y），数底边簇**之前**先调 `isStackedBarComponents` 豁免；
2. 新增 `isStackedBarComponents(List<BoundingBox>)`：
   - 按 x 列分组（左右边差 ≤ `STACK_COLUMN_X_TOLERANCE`=1.0pt）；
   - 每列内分量按底边排序，若**垂直精确成链**（上段底边 = 下段顶边，gap ≤ `STACK_CHAIN_GAP_TOLERANCE`=0.5pt）则该列记为链；
   - 成链列数 ≥ `MIN_STACKED_COLUMNS`=2 → 判堆叠柱状图，`looksLikeTableGrid` 直接返回 false。
3. 区分依据：堆叠段是同一条填充路径画的，实测首尾 gap=0.0；而守卫要防的填充单元格表格，
   行间永远有网格线间隙，不会成链。要求 ≥2 列成链，是防止单列零间隙单元格误豁免。

新增 2 个单测（`BarChartProcessorTest`，守卫原来一个测试都没有）：
- `stackedBarChartIsNotVetoedAsTableGrid`：两段精确相叠 + 基线单段的 7 分量组必须出图；
- `filledCellTableGridIsStillVetoed`：4 列 × 3 行、行间 2pt 网格间隙的 12 个填充单元格仍被 veto。
