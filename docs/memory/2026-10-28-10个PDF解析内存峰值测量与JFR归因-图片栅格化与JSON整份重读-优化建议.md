## 一、结论先说

1. **峰值最高的不是最大最厚的文件**：59 页 / 35.45MB 的 `20250417…158` 堆峰 **2189MB**，而 765 页 / 14.05MB 的 `20230228…328` 只有 1552MB。决定峰值的是**文档内容形态**（大位图 + 渐变填充 vs 纯文字），不是页数或文件体积。
2. **峰值中 44%~71% 是垃圾而非存活数据**。所有 20 次运行 **0 次 Full GC、0 次 OOM**：G1 一直在把瞬时对象及时清掉，峰值是"GC 前一刻的分配水位"。因此"加内存"不是最优解，**降低分配速率/分配量**才是。
3. 内存飙升可拆成四类数据，按量级排序：
   - **① veraPDF/PDFBox 解析期建模型**：每个文件 2.9~6.9GB 分配（`byte[]` 解压流、`double` 字符串解析、`BoundingBox`/`Vertex`/`COSReal`/`StreamInfo` 逐 token 包装），并留下 **790~1185MB 存活**几何/语义对象，直到写盘结束才释放。
   - **② 图片栅格化**：每个待导出 `ImageChunk` 都要把**整页按 144 DPI 渲染成 RGB 位图**（实测整页 ≈ 10.6MB/张，300 DPI 截图 ≈ 23.9MB/张），再裁子图、再 PNG 编码。`20250417` 该阶段分配 **7.44GB**（`int[]` 4.20GB，其中 `AxialShadingContext.getRaster` 2.21GB）。
   - **③ JSON 输出期的整体复制**：把**整份 JSON 重新反序列化成通用 `Map`**（实测存活 +229MB），再 pretty-print 整体回写，再把 `data` 序列化成一个巨大 `String` 写 .js（该阶段分配 2.04GB，`Arrays.copyOf(byte[])` 446MB + `StringBuilder` 360MB）。
   - **④ 正则/装箱抖动**：JSON 阶段 `Pattern.compile` 分配 164.8MB（`replaceAll("\\s+")` 按条目反复编译）、存活 `Matcher` 29 万个；`Double`/`Long` 百万级装箱；veraPDF 侧 153 万个 `LinkedList`（多为空链表）。
4. 同一个 PDF 在整条链路里被**完整解析 3~4 遍**（PDFBox 修 ToUnicode → veraPDF → PDFBox 提取路径框），**每个做图片渲染的线程再各自加载一份**（`StaticContainers.getImagesUtils()` 是 `ThreadLocal`）。这是"分配量大"的结构性来源。
5. **降低内存最有效的第一刀是关掉/降低图片导出分辨率**（`20250417` 堆峰 −52.7%）；**第二刀是去掉整份 JSON 重读**（`20230228` 常驻 −229MB、该阶段分配 −2GB 级）。

### 6.2 图片栅格化：`20250417` 的元凶（该阶段分配 7.44GB）

```
int[]   4,196.3 MB (56.4%)  ← AxialShadingContext.getRaster 2,207MB + DataBufferInt 1,472MB
byte[]  1,638.7 MB (22.0%)  ← DataBufferByte / ByteInterleavedRaster.getByteData
float[]   796.2 MB (10.7%)  ← AxialShadingContext.getRaster
```

机制（`ImagesUtils.write` → veraPDF `getPageSubImage` → `renderPage`）：

1. 每个 `ImageChunk` / `SemanticPicture` 都要先拿到"整页栅格"：`RENDER_DPI = 144`、`ImageType.RGB`（`veraPDF-wcag-algs/.../ImagesUtils.java:41,160`）。
2. 实测整页尺寸（导出 PNG 反推）：`1656×2231` → **≈10.6MB/张 RGB**；`20230325` 单张导出 `3840×2160` → 23.7MB；`20250417` 的 300 DPI OCR 截图 `2481×3367` → **≈23.9MB**（`int` 栅格 33MB）。
3. 渲染后还要：裁子图（再分配一份）→ PNG 编码（`DataBufferByte` + zlib 缓冲）→ 落盘。页面若有大面积渐变，`AxialShadingContext.getRaster` 再按瓦片分配 `int[]`（`20250417` 2.21GB）。
4. **每个工作线程各自一份 PDFBox 文档**：`saveImageChunk` 在 `BarChartProcessor`/`FlowchartProcessor`/`GraphicRegionProcessor`(×2)/`ConsecutiveImageProcessor`/`LineArtProcessor` 中被调用，而 `StaticContainers.getImagesUtils()` 是 `ThreadLocal`，首次访问 `new ImagesUtils(true)` 内部会 `Loader.loadPDF(...)` 整个 PDF。

产出侧证据（每文件 base 运行）：`20250417` 170 张图 **104MB**（最大 10.5MB）；`20230325` 221 张 **73MB**（最大 13.5MB）；`20230228` 101 张 9.5MB；`20260507` **3092 张**但仅 5.1MB（大量小图，故峰值低、耗时高）。

### 6.4 正则/装箱/空集合抖动

- `BookmarkQualitySelector.java:299` 的 `text.replaceAll("\\s+", "")` 按条目反复编译正则；同类还有 `CatalogBookmarkProcessor:850,859`、`JsonWriter:735,759`。JSON 阶段 `Pattern` 分配 164.8MB、存活 `Matcher` 29 万个。
- `Double`（153 万）/`Long`（99 万）装箱各 35MB/23MB 常驻。
- veraPDF 侧 153 万个 `LinkedList`（仅 43 万个 `LinkedList$Node` → 绝大多数是空链表），196 万个 `COSReal`。

## 八、代码级根因

1. **同一 PDF 完整解析 3~4 遍**（`DocumentProcessor.preprocessing`，L1152~1228）：
   `repairBrokenToUnicodeIfNeeded`（PDFBox 全量）→ `new PDDocument(...)`（veraPDF）→ `document.parseChunks()` → `extractPagePathBoxes(...)`（内部另一处 `Loader.loadPDF`，L1363）→ `ShapeRecognizer.recognize` → `LinesPreprocessingConsumer.findTableBorders`。
2. **每个渲染线程各自再加载一份 PDF**：`StaticContainers.getImagesUtils()`（`StaticContainers.java:269-279`，`ThreadLocal`）→ `ImagesUtils(true)` → `Loader.loadPDF`。4 线程 ≈ 4 份 PDFBox 文档 + 主线程 `ImagesUtils.write` 一份。
3. **截图路径每次开一次整文件**：`PopplerRenderer.getPageSizeInPixels` 为拿页面像素尺寸 `Loader.loadPDF(pdf)`（L320），每张截图一次。
4. **全文 `contents` 常驻**：`List<List<IObject>>` 从 Loop1 一直活到 `JsonWriter`/`MarkdownGenerator` 结束；`pageArtifacts[i] = document.getArtifacts(i)` 又是全页预取。几何对象（`BoundingBox`/`Vertex`/`LineChunk`/`StreamInfo`/`COSReal`）因此 800MB~1.2GB 全程不释放。
5. **图片固定 144 DPI 整页 RGB 渲染**（`veraPDF.../ImagesUtils.java:41,160`），且 `--image-resolution` **没有接线**：`Config.getImageResolution()` 全仓库无消费方，`DocumentProcessor:658` 用的是 `new ImagesUtils()`（无参 → `imageResolution=null` → 落到 `RENDER_DPI=144`）。
6. **JSON 三重整体复制**（`JsonWriter.java`）：
   `L386` 首份 JSON 落盘 → `L394-399` 用 Jackson 把整份 JSON 读成通用 `Map` → `L476` `writerWithDefaultPrettyPrinter().writeValue(file, map)` 整体回写 → `L501` `writeValueAsString(map.get(DATA))` 拼出大 `String` 写 .js（实测 16.5MB JSON → 9.6MB .js，中间是 16MB 级 `String` + 倍增的 `StringBuilder`）。
7. **`--image-output off` 不阻止 OCR 截图 pass**：noimages 运行仍产出 `_ocr-*.png`（`JsonWriter` 截图路径不看 `isImageOutputOff`）。
8. **正则未预编译**：`BookmarkQualitySelector:299` 等按条目 `replaceAll`。

## 九、优化方案

### A. 不改代码（运维/参数层，可立即验证）

| 措施 | 实测依据与预期 |
|---|---|
| 按需 `--image-output off` | `20250417` 堆峰 −52.7%、耗时 −22%；`20230325` 只省 20% 时间。只要文本/JSON 的场景应默认关 |
| `--image-format jpeg` | PNG 编码需 zlib 缓冲 + `DataBufferByte` 拷贝，大图场景更省临时内存 |
| `pdf.threads=2` | 4 线程收益不稳定（`20230318`/`20230420`/`20250417` 的 t4 峰值反而更低），2 线程减少"每线程一份文档 + 一张整页栅格"的并发量，进程峰更可控 |
| `--pages` 分批 | 常驻量与当前批次页数正相关，`20230228`(765 页) 最受益 |
| 不要并发跑多文件 | 单进程私有峰 0.8~2.5GB，4 并发≈10GB |
| 只生成需要的格式 | 关掉 markdown/html/text 减少同一 `contents` 的多次遍历与字符串拼装 |
| JVM 微调（可选，需 A/B） | `-XX:G1HeapRegionSize=8m`（减轻 6~10MB 栅格的 humongous 占位与碎片）、`-XX:G1NewSizePercent=8 -XX:G1MaxNewSizePercent=25`（缩小 eden → 峰值更低，但 GC 更频繁，可能损失 5~15% 吞吐）。注意：真正的 10~24MB 整页栅格要 region>2×size 才不算 humongous，不要指望靠调 region 解决，仍需靠降低 DPI/关图片 |

### B. 需要改代码（**未经批准未执行**）

按"收益/风险"排序：

1. **去掉整份 JSON 重读**（`JsonWriter:394-399`）：书签/OCR 阶段改用内存模型或流式遍历。预期：`20230228` 常驻 −229MB、该阶段分配从 2.04GB 级降到一半以下。
2. **`writeValueAsString(data)` 改为 `mapper.writeValue(writer, data)` 直写 .js**（`L501`）。预期：消除 35MB 级 `String` 与倍增 `StringBuilder`（实测该阶段 `Arrays.copyOf(byte[])` 446MB + `StringBuilder` 360MB）。
3. **把 `--image-resolution` 接到 `ImagesUtils`**（`DocumentProcessor:658` 传入 `config.getImageResolution()`）。144→96 DPI 栅格面积 −55%（10.6MB/页 → 4.7MB/页）。
4. **单文档共享一个 veraPDF `ImagesUtils`**，并把"渲染→裁切→编码"改成按页流水、写完即 `flush`；PNG 直接用 `ImageOutputStream` 落盘，省掉 `ByteArrayOutputStream` 二次拷贝；对无图页直接跳过渲染。
5. **合并解析次数**：`extractPagePathBoxes` 复用 veraPDF 已解析的 content stream（或在 `parseChunks` 时顺带收集路径框），消灭第 3 遍全量 PDFBox 解析（每遍 1~2GB 分配）。
6. **`contents` 分页流水化 + `pageArtifacts` 惰性获取**：按页处理、写完即释放，把 800MB~1.2GB 常驻压到"单页/单批"。
7. **预编译正则**为 `static final Pattern`（`BookmarkQualitySelector:299`、`CatalogBookmarkProcessor:850,859`、`JsonWriter:735,759`）。预期：JSON 阶段 `Pattern` 164.8MB 基本消失。
8. **矢量密集页做对象上限/合并**：现有 `MAX_LINES_PER_COLOR_FOR_CHAIN_RECOGNITION=5000` 只挡住了 `ShapeRecognizer` 建链，`COSReal`/`BoundingBox`/`StreamInfo`/空 `LinkedList` 仍按 22 万线的规模常驻；需在 chunk 阶段裁剪或合并。
9. **无 OCR 服务时彻底跳过截图 pass**（当前 `--image-output off` 仍生成 `_ocr-*.png`；`20250417` 那张 300 DPI / 10.5MB 截图就来自这里）。

## 十、复现方法（脚本复用价值）

脚本均在 `.agents/tmp-probe/memprof/`（JDK17 编译到同目录 `classes/`，classpath 由 `mvn -o -pl opendataloader-pdf-core dependency:build-classpath` 生成 `cp_core.txt`）：

```powershell
# 1) 单/批量测量（输出 summary.csv / heap_timeline.csv / gc.log / proc_samples.csv）
& .\.agents\tmp-probe\memprof\run-memprof.ps1 `
    -Pdfs @("$PWD\docs\pdf\202504171785131172233015158.pdf") `
    -Threads @(2,4) -Mode base            # Mode: base | noimages | jsononly

# 2) 阶段归因（把 100ms 堆序列与日志阶段标记对齐）
& .\.agents\tmp-probe\memprof\analyze-heap.ps1

# 3) 阶段切分 JFR 分配归因（按对象类 + 最内层栈帧聚合）
& .\.agents\tmp-probe\memprof\run-with-jfr.ps1 -Pdf <pdf> -Threads 4
& .\.agents\tmp-probe\memprof\analyze-jfr.ps1 -RunDir <runDir> -Top 12

# 4) 存活对象直方图（extraction / json_written / json_map_live 三个时点）
& .\.agents\tmp-probe\memprof\run-with-histogram.ps1 -Pdf <pdf> -Threads 4
```

踩过的坑（脚本里已修）：

- `-Djava.util.logging.SimpleFormatter.format` 含空格，必须整段加引号，否则被拆成主类 `%4$s` 报"找不到或无法加载主类"。
- JUL 日志实际写 **stderr**，只读 stdout 会拿不到 `Processing N pages` / `Created *.json`；应合并读取或用 `Select-String` 逐个文件读并容忍独占占用。
- PowerShell 双引号里 `` `r?`n `` 不是正则转义；改用 `[regex]::Match` 直接匹配整段文本。
- `$e.time` 若为 `[DateTime]` 没有 `ToUnixTimeMilliseconds()`，需 `[DateTimeOffset]::new($dt)` 转换。
- 控制台中文乱码：脚本内设 `[Console]::OutputEncoding = [Text.Encoding]::UTF8`，并直接用当前 PowerShell 会话执行（`& script.ps1`），不要 `powershell -File` 再套一层。
- `jcmd JFR.stop` 在 JVM 退出瞬间会失败（`Can't stop an already stopped recording`），但 `phaseN.jfr` 通常已落盘，仍可分析。
