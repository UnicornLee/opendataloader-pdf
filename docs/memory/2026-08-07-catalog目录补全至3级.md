# opendataloader-pdf 任务记忆 — 2026-08-07

## 目标（Goal）
- 在 `catalog_bookmarks` 存在且未达 3 级时，依据 `page_num` 与 `related_id` 为其补充子目录至 3 级。
- 方案已获批，已实现并通过一致性验证（catalog 最深 3 级、L3 与 page 树逐节点一致）。

## 约束与偏好（Constraints & Preferences）
用户 7 条要求：
1. 已够 3 级不处理；一级或二级无子目录需抽取补充。
2. 范围判定：目标目录 T、相邻同级 S：`page_num == T.page_num` → `related_id > T.related_id`；`T.page_num < page_num < S.page_num` → `related_id` 不限；`page_num == S.page_num` → `related_id < S.related_id`。
3. 倾向缓存 `page_bookmarks` 首次收集的目录集，补子目录直接截取。
4. 收集到的目录集后续处理与 `page_bookmarks` 一致。
5. 不清楚处须澄清。
6. 改码前先给思路，获同意后才改（本期已满足）。
7. 可用 `org.opendataloader.pdf.DebugSample` 跑解析。

4 项澄清用户已作答：
- **切片源 = 清洗前的原始候选集**（非最终 `page_bookmarks` 树），须对其再应用 `page_bookmarks` 的清洗/校验逻辑。
- 锚点 = `page_num` + `related_id` 精确匹配；匹配失败时退化文本匹配。
- catalog L1 已有部分 L2 → 只补缺失 L3，保持现有 L1/L2 结构。
- 无锚点 catalog 项（`本次发行概况`/`重要声明`/`目 录` 等前页项）→ 保持原样不补；"目标 L2 已有子级"也跳过。

## 实现（终版，已通过验证）
### 代码改动
- `PageBookmarkProcessor`：
  - 移除第一版的 `extractPageChildrenForRange` / `sliceCandidates`（对外 page/relId 范围切片，因无法精确复现 page 树索引区间而废弃）。
  - 新增 `extractChildrenForAnchor(data, catalogStartPage, catalogEndPage, anchorPage, anchorRelatedId, level)`（公开静态，对 catalog 的补录入口）：
    1. `collectJsonCandidates` 收集 + 按阅读序排序（与全文档路径同源）；
    2. `indexOfCandidate` 按 `(page=pageIndex+1, relatedId)` 精确解析锚点索引 A（复用 `createBookmark` 的编号规则，匹配成功）；
    3. 复算祖先模板：L1 模板 = `selectTemplateForLevel(all, 0, size-1, 1, empty)`；level≥3 时再按父 L1 区间复算 L2 模板，`usedTemplates={l1}` 或 `{l1,l2}`；
    4. 子目录上界 = page 树结构内"下一个同层已清洗节点"的索引：由 `cleanedIndicesOf`（对模板命中候选做 `cleanCandidates`/`cleanCandidatesLocal` 清洗并回填原始索引）+ `lastIndexBefore` / `nextIndexAfter` 计算（L2 用父 L1 区间内下一清洗 L2，末尾 L2 用下一 L1 索引-1；L1 用全局下一清洗 L1）；
    5. `extractLevel(all, A+1, childEnd, level, usedTemplates)` 只建一层子级（level 由调用方显式给 2 或 3，`level+1>3` 自然停止，L3 恒为叶子）→ **最多 3 级**，且逐节点等于 page 树对应子级。
  - 新增私有辅助：`indexOfCandidate`、`cleanedIndicesOf`、`lastIndexBefore`、`nextIndexAfter`。
- `CatalogBookmarkProcessor.fillCatalogChildrenFromPageData`（原地变更 catalog 树）：
  - 不再用 catalog 同级做切片边界（消除 catalog L2 集 87 vs page L2 集 83 的偏差来源）。
  - catalog L1 无子级且 page 有锚点+子级 → `extractChildrenForAnchor(..., level=2)` 补 L2；
  - catalog L2 无子级且 page 有锚点+子级 → `level=3` 补 L3；
  - 无锚点 / 已有子级 → 跳过，保持既有 catalog L1/L2 结构。
  - 日志 `Level.INFO`：`[CatalogBookmark] complemented N catalog bookmark group(s) from page data`。
- `JsonWriter`：`map.put("catalog_bookmarks", …)` 前调用 `fillCatalogChildrenFromPageData(data, catalogStartPage, catalogEndPage, catalogBookmarks, pageBookmarks)`。

## 关键决策（Key Decisions）
- 切片入口放 `PageBookmarkProcessor` 并复用既有流水线 → 与 `page_bookmarks` 完全同源同清洗。
- 边界必须来自 **page 树结构**（锚点 + 同层下一节点索引 + 祖先模板上下文），不能用 catalog 同级。
- **以 `level` 参数直接指定目标层级（2/3）并只建一层**，根治"重建树导致 5 级"问题。
- 锚点仅是 page 树索引命中判据；无锚点项与"已有子级"项均跳过，不破坏既有 catalog 结构。
- 不做深拷贝：从原始候选切片构建全新独占对象，天然与 page 树独立。
- 验证脚本教训：对比 L2 必须遍历 page 树的 **L2 层**（L1.children），不能拿 L2 去匹配顶层 L1；`maxDepth`/`Get-Depth` 等辅助函数需在脚本内正确定义。
