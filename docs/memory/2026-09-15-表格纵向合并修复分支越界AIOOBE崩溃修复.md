即：某数组长度 5，访问索引 5 → 访问的是"最后一个元素的下一个位置"。

### 第二步：确认运行的 jar 与源码一致

opendataloader-pdf 依赖 `org.verapdf:wcag-algorithms:1.31.33`（`java/pom.xml` 中 `verapdf.wcag.algs.version`），即团队 fork `D:\Code\JavaCode2\veraPDF-wcag-algs` `mvn install` 到 `D:\Maven_Repo` 的 jar。用 `javap -c -l` 对照本地仓库 jar 的字节码行号表，确认第 465 行与磁盘源码一致。

### 第三步：用字节码精确锁定越界的数组（关键一步）

源码 `TableBorder.java:464-471` 处于"纵向合并修复分支"，可疑的数组引用有两类：

- `rows[rowNumber + 1]`（下方行，访问 rows 数组）
- `rows[rowNumber].cells[colNumber + 1]`（右邻单元格，访问 cells 数组）

单看源码无法确定崩的是哪一个。对 jar 做反汇编，偏移 768（行号表对应 line 465）的字节码为：

```

772: getfield cells
775: iload 6        // colNumber
777: aaload
```

结论：越界的是 **cells 数组**（长度 = numberOfColumns = 5），访问 `cells[colNumber + 1]` 时 `colNumber` 是最后一列（索引 4）。

## 根因总结

**fork 提交 `7417e9a` 引入的复制粘贴 bug**：`processMergedCells` 的纵向合并修复分支（单元格向下合并、但下方单元格水平范围不一致时对齐 span）误用了右邻单元格引用 `rows[rowNumber].cells[colNumber + 1]`，正确目标应为下方单元格 `rows[rowNumber + 1].cells[colNumber]`。处理到最后一列时 `cells[colNumber + 1]` 越界，AIOOBE 导致整个文档解析崩溃（表格边框预处理无异常兜底）。

修复后 `rows[rowNumber + 1]` 是安全的：同分支上方原有代码（`TableBorder.java:459`）本就访问它；单元格 span 以矩阵边缘为锚点传播（初始 `rowSpan = numberOfRows - rowNumber`、`colSpan = numberOfColumns - colNumber`，传播循环保持恰好到边），不会溢出底边/右边，因此无需额外边界保护。

## 关键决策与坑点

- **用户贴出的代码片段不可信**：用户贴的 `TableBorder.java` 片段中该分支写的是 `rows[rowNumber + 1]`（即"已修复"形态），与磁盘源码和 jar 字节码均不符。排查时一律以磁盘源码 + `javap` 字节码为准。
- **`javap -c -l` 是定位"哪一行哪个数组越界"的利器**：AIOOBE 消息只给 index/length，源码层面 `rows[i+1]` 与 `cells[j+1]` 两种引用都可疑，字节码立刻分清。
- **运行 classpath 的小技巧**：`mvn dependency:build-classpath -Dmdep.outputFile=cp.txt` 生成 classpath 后直接 `java -cp` 运行 `DebugSample1`，绕开 IDE。Maven 为 offline 模式，本地仓库在 `D:\Maven_Repo`。
- **复现完整成本约 6 分钟**：extraction ~1.3 min（崩溃发生在 preprocessing，早早就崩），全量输出 ~4 min；paddle OCR 服务（192.168.1.97）当时可连通。
- **未提交 git**：修复在 fork 仓库工作区中未提交（`git diff` 仅此一处 8 行），建议提交信息如 `fix: correct below-cell reference in processMergedCells vertical merge repair`。
- **同类风险已评估**：横向修复分支引用 `cells[colNumber + 1]` 是语义正确的（横向合并对齐的就是右邻）；span 传播以矩阵边缘为锚，不会溢出，故未加额外防御性边界检查。
