## 二、根因定位（证据链）

### 阶段 0：定界 —— 走 JSON 路径

`JsonWriter` 在解析完成后调用 `CatalogBookmarkProcessor.extractCatalogBookmarksFromJson` →
`resolveCatalogBookmarkTargets` → `fillCatalogChildrenFromPageData` → `BookmarkQualitySelector.select`。
顶层键里 `catalog_bookmarks` 缺失而 `page_bookmarks` 存在，说明**选中来源是 catalog**（选中源键会被移除），
所以 `bookmarks` 就是 catalog 树（含从页面数据补全的子项）。
日志 `[CatalogBookmark] detected catalog page range from JSON: 6-6 (1 pages, 19 toc items)` 与输出吻合。

### 阶段 1：目录实际跨两页

用 pdfplumber 逐页 layout dump（`tmp_output/probe/toc_474.txt`）看到：

### 阶段 2：复刻 `matchTocLine` 证明第 7 页被判为非目录页

用 Python 按 `CatalogBookmarkProcessor.matchTocLine` 的 5 类判据（CHINESE / ARABIC_RANGE / ARABIC /
ROMAN / pageLabels）逐行重放（`tmp_output/probe/tocpage_probe.py` → `tocpage_probe.txt`）：

| 页 | 文本行数 | 匹配行数 | ratio | 结论 |
|---|---|---|---|---|
| idx5（第 6 页） | 21 | 19 | 0.905 | `isTocPage()` = true → 开启 range |
| idx6（第 7 页） | 14 | **3** | **0.214** | false（阈值 0.4）→ `detectJsonRanges` 直接 `continue` |

第 7 页只有 3 条阿拉伯页码行能匹配，11 条附录式引用全部落空 → ratio 不足 → 该页既不能 extend
也不能 open（`detectJsonRanges` 对 `!isTocPage()` 是直接跳过），range 停在 6-6。

### 阶段 3：为什么 `I-1 / II-1 / IX-1 / EGM-1` 匹配不上

```java
// 改动前（CatalogBookmarkProcessor:107-121）
ARABIC_TOC_PATTERN        = ^(.*?)[\s\.]+(\d{1,5})$          // I-1 的 "1" 前是 '-'，不是空白/点
ROMAN_TOC_PATTERN         = ^(.*?)[\s\.]+([IVXLCDMivxlcdm]+)$ // I-1 含数字
CHINESE_PAGE_TOC_PATTERN  // 需要「第 X 页」
ARABIC_RANGE_TOC_PATTERN  // 需要 数字—数字
+ findLabelSuffix(text, label)   // 要求 label 是文本的**后缀**，且前面是空白或 '.'
```

- `I-1`：ARABIC 要求 `[\s\.]+数字$`，而 `1` 前是 `-`；ROMAN 要求后缀纯罗马字，`I-1` 含数字；都不匹配。
- pageLabels 兜底也失效：本 PDF `/PageLabels` 只有 `{/S: /D}`（纯阿拉伯数字标签，实测 723 页全部
  `getPageLabel()` 为空/数字），且 `findLabelSuffix` 在 `1` 前面看到的是 `-`，返回 -1。
- 内容路径（`analyzePages` / `collectAllLines`）共用同一个 `matchTocLine`，所以现象一致。

### 阶段 4：为什么「股本」的切片是**开区间**

第 7 页丢失后，`股本` 成了 catalog 的**最后一条**，于是
`fillCatalogChildrenFromPageData` 给它的 L2 切片没有上界：

```
[PageBookmark] catalog slice level=2 bounds=(473,1)-(-1,-1) candidates=287
                                                      ↑ nextSibling == null → nextPage = -1
```

切片从 p473 一直吃到文末 p723，把附錄一（p570-583 的 35~38）、附錄七的软件著作权清单（p671-673 的 1~34）、
法定及一般资料（p699-702 的 1~13）全部卷了进来。

### 阶段 5：287 个候选怎么变成「35/36/37/38 + 1..34」

1. `matchPrefix` 是 `text.startsWith(pattern.constant)`（最长常量优先），所以
   `"35.  金融工具（續）"`（常量 "35"）与 `"1     激光雷達…"`（常量 "1"）、`"1.  遺產稅"` 命中**同一个
   `TemplateKey`（NUMBER + ARABIC）**，只是一组候选。
2. `cleanCandidatesLocal` Step 2 按**读序**切「值连续段」：
   `[35..38]`(p570-583)、`[1..8]`(p667 专利表行)、`[1..34]`(p671-673)、`[1..13]`(p699-702)。
3. Step 3 按**起始值**排序（读序被丢弃）：`[1..8]`、`[1..34]`、`[1..13]`、`[35..38]`。
4. Step 4 定点合并：种子 `[1..34]`（max=34）→ 找到 `min == 35` 的 `[35..38]` → **接上**，
   链值域 `[1..38]`，长度 38 胜过 `[1..34]`(34)、`[1..13]`(13)、`[1..8]`(8) → Step 5 胜出。
   （若 `[35..38]` 单独成链，会被 Step 4.8「链首值必须=1」丢掉，所以它只能靠"接在 `[1..34]` 后面"存活。）
5. `childAnchorIndices`（`PageBookmarkProcessor:1007-1010`）最后把 anchors 按**读序**
   （`pageIndex` 升、`topY` 降）重排 → p570-583 的 35~38 排在 p671 的 1 之前 →
   **这就是用户看到的"35 / 36 / 37 / 38 在最前面"**。

即：**值域相邻 ≠ 文档相邻**。两组毫不相干、仅数值恰好接续的序列被"向后连"的单向规则粘成一条链，
再被读序重排暴露成乱序。

### 阶段 6：解析失败的下游后果（实施过程中发现，形成第三处根因）

把第 7 页并入后，13 条新条目的 `original_page_num` 全是 0（`parseOriginalPageNum("I-1")` 是纯
`Integer.parseInt`，失败即 0），而：

```java
// 改动前（CatalogBookmarkProcessor:1805-1814）
Integer catalogHint = bookmark.getOriginalPageNum();
if (title == null || title.trim().isEmpty() || catalogHint == null || catalogHint <= 0) {
    return 0;                       // ← 无数字提示 → 放弃解析
}
```

→ `page_num` 停在 `resolvePageIndex("I-1") + 1 = 1` → `fillCatalogChildrenFromPageData` 拿 page=1 当锚点，
切出 `catalog slice level=2 bounds=(1,2)-(589,1) candidates=387`，**116 个垃圾子树节点**，
`BookmarkQualitySelector` 指标劣化为 `dup=0.207 / nonMono=0.19`、catalog score 5.081 → **3.105**。

进一步定位为什么 13 条里 12 条能解析、唯独 `附錄二` 不行：

```
目录行   ：附錄二   － TECHSTAR的財務資料
正文页眉 ：附錄二                 T E C H S T A ☑的財務資料
                                   codepoints: … 0x41('A'), 0x2611('☑'), 0x7684…
```

正文页眉被字体 ToUnicode 损坏：字母间插空格（`\s` 已在归一化时删掉）且 **`R` 变成了 `U+2611`**。
归一化后 `附錄二－TECHSTAR的財務資料` vs `附錄二TECHSTA☑的財務資料`：公共前缀 3、公共后缀 5，
差值 = 9 + 6 = 15 > `MAX_FUZZY_TITLE_GAP=2` → EXACT/PREFIX/FUZZY 全失败 → 解析失败 → page=1。

## 三、根因（三条，互相独立又叠乘）

1. **`matchTocLine` 缺少「附录式页码引用」分支**：`I-1 / II-1 / IX-1 / EGM-1` 这类
   「字母 + `-` + 数字」的附录页引用没有任何正则能识别，`/PageLabels` 也是纯阿拉伯数字、帮不上忙。
   结果：多页目录中"只列附錄"的第 2 页 ratio 3/14=0.214 < 0.4 → 不判为目录页 → 该页 13 条全部丢失。
2. **Step 4 连链只判"值域相邻"、不判"文档顺序"**：`[1..34]` 与 `[35..38]` 分属不同附录却被粘成一条链，
   再按读序重排 → 「股本」子项顺序与归属全错。
3. **无数字提示的条目被整个放弃解析**：`catalogHint <= 0` 直接 `return 0`，
   `page_num` 落到回退值 1；而当正文标题还因字体缺字（`R`→`☑`）匹配不上时，
   连"按标题解析"这条退路也没有，于是产生以 page=1 为锚点的 387 候选 / 116 节点垃圾子树。

## 四、修复实施

改动集中在 2 个主文件 + 2 个测试文件（`git diff --stat` = **+474 / −13**）。

### 4.1 新增附录式页码引用正则 —— `CatalogBookmarkProcessor:135-137`

```java
// Appendix-style page references: "Title …… I-1" / "IV-1" / "IX-1" / "EGM-1".
private static final Pattern APPENDIX_PAGE_TOC_PATTERN =
        Pattern.compile("^(.*?)[\\s\\.]+([A-Za-z]{1,16})\\s*-\\s*(\\d{1,5})\\s*$");
```

- 分支插在 ROMAN 之后、pageLabels 兜底之前（`CatalogBookmarkProcessor:587-598`），
  `TocMatch.rawPage = group(2) + "-" + group(3)`（如 `I-1`、`EGM-1`）。
- 前缀 `[A-Za-z]{1,16}`：**同时接受小写罗马字与更长字母缩写**（用户第 1 条要求）。
- 要求「非空标题 + 空白/点引导符」分隔，所以正文里孤立的 `COVID-19` 不会被当成目录行
  （`testAppendixPageReference_requiresTitleAndSeparator` 固定住这一点）。

### 4.2 去掉 `catalogHint <= 0` 早退，无数字提示改按文档顺序解析

`CatalogBookmarkProcessor:1869`（守卫只保留 null 判断）与 `:1906-1909`：

```java
// With no usable hint the distance falls back to the physical
// page, which ranks the matches by document order (earliest first).
int distance = catalogHint > 0 ? Math.abs(physicalPage - catalogHint) : physicalPage;
```

由于 `distance` 退化为物理页号本身，排序等价于「取 ≥floor 的**最早**命中」，
正是附录/前言这类"章节自成一页序"的起页语义。Constraint 1（≥印刷页）在 hint≤0 时不过滤任何命中，
Constraint 2（floor，不倒退）仍生效。

副作用（用户已确认接受）：所有 `original_page_num == 0` 的条目（罗马页码前言、附录引用）都从"不解析"
变为"按标题+顺序解析"。实测本文件 `預期時間表` 1→2、`20150113…` 同类条目页码也更准。

### 4.3 Step 4 / Step 4.7 增加「读序单调」守卫 —— `PageBookmarkProcessor`

用户口径「候选目录根据连续性分组，将能够连起来的组连起来，**只能向后连，不能向前连**」：

```java
// :1602-1606  以 Step 1 的 sorted 下标建立读序表
Map<Candidate, Integer> readingOrder = new IdentityHashMap<>();
for (int i = 0; i < sorted.size(); i++) {
    readingOrder.put(sorted.get(i), i);
}

// :1620-1621  Step 4 并入分组时，除"值相邻"外还要求"读序在链尾之后"
if (!seeded || (chainMax + 1 == groupMin
        && startsAfterChainEnd(chain, group, readingOrder))) {
```

- 新增 `startsAfterChainEnd`（`:1731-1745`）：取「链尾分组最后一个候选」与「待并入分组第一个候选」
  的读序下标比较；下标取不到时返回 true（保持历史行为，避免丢组）。
- Step 4.7 的 value=1 前插同样加守卫：`prependValueOneOrphansOntoValueTwoChains(chains, readingOrder)`
  （`:1655`、`:2026-2027`、`:2048-2049`）+ `isPrependable`（`:2078-2087`，
  要求 orphan 读序早于目标链首）。
- 为什么用 `IdentityHashMap`：`Candidate` 没有覆写 `equals/hashCode`，但显式用身份语义更稳妥且更快。

### 4.4 附录标记兜底（实施中新增的必要补充）—— `CatalogBookmarkProcessor:163-167 / 1914-1933 / 1985-2077`

```java
private static final Pattern SECTION_MARKER_PATTERN =
        Pattern.compile("^(附錄|附件|Appendix|Annex)\\s*"
            + "([0-9]{1,3}|[IVXLCDMivxlcdm]{1,8}|[一二三四五六七八九十]{1,4})");
private static final String NUMERAL_CHARS = "0123456789IVXLCDMivxlcdm一二三四五六七八九十";
```

- 触发条件：**hint=0 且标题在正文里完全匹配不到**（`matches.isEmpty()`，`:1919-1932`）。
- 做法 `findSectionMarkerHit` → `scanSectionMarker` → `startsWithMarker`：只在
  「每页**第一个** text 项且 `source_type == heading`」的**页首标题**上，用标题的附录标记
  （`附錄二` / `AppendixII`）做前缀匹配，取 ≥floor 的最早一页；
  `startsWithMarker` 用 `NUMERAL_CHARS` 做**边界守卫**，`附錄一` 不会误配 `附錄十一` 的页。
- 为什么必须做：否则 `附錄二` 因 `R`→`☑` 无法解析，`page_num` 落到 1，整棵 catalog 退化成
  387 候选 / 116 垃圾节点、score 5.081→3.105、`dup/nonMono` 变差。
- 为什么不用「PDF outline（`self_bookmarks`）当 hint」这条备选：
  `fillCatalogChildrenFromPageData` 的 javadoc 明确写过"不要跨源复用"（曾因复用 page 树导致越界切片），
  且需要改 `JsonWriter` 两处调用点；标记兜底自包含、不引入跨源依赖。若日后要换成 outline 方案，
  改动点是 `JsonWriter`（两处 `extractCatalogBookmarksFromJson` 调用前的 self 转换）。

## 八、调试方法与踩坑

### 本轮最大坑：`git stash` 做基线会让 `target/classes` 停在被 stash 的版本

`check_hf_baseline.ps1` 里 stash 后 `mvn test` 会用**基线源码**重建 `target/classes`；`git stash pop`
只恢复源码，不回滚 class。表现是"所有修复突然全部失效"（range 又变回 6-6、`股本` 又出现 35/36/37/38）。
**stash 往返之后必须重新 `mvn -o -q -pl opendataloader-pdf-core compile`**。

### 有效的定位/复现手法

- **用 Python 复刻 Java 正则**（`probe/tocpage_probe.py`）：直接对 JSON 的 items 重放
  `matchTocLine` 的 5 类判据，几秒内得到"每页文本行数 / 匹配行数 / ratio"，比反复跑 50s 的端到端快得多；
  结论与 Java 侧日志一致（3/14 = 0.214）。
- **反射/切片探针**：`probe/TmpBookmarkTreeProbe.java` 直接调用真实的
  `extractCatalogBookmarksFromJson` / `fillCatalogChildrenFromPageData` / `extractPageBookmarksFromJson`
  dump 三棵树；差异用 `probe/diff_474_sections.py`（按 section 计数）→ `probe/show_changed_parents.py`
  （按"直接父节点 + 全部子项"逐条对照）二层定位。
- **PDF outline 交叉验证**：`self_bookmarks` 是 PDF 自带数据，用来核对附录落页（480/482/495/498/586/…）。
- **`-Dtest=<Class>#<method>`** 单跑用例做"关掉修复必须失败"的逆向验证，比 git stash 往返快且安全。

### 环境踩坑

- `cd java` 之后重定向要写 `..\tmp_output\xxx.out`（写 `tmp_output\xxx.out` 会 `DirectoryNotFoundException`）。
- `cp.txt` 是单行 ~4KB，Windows `cmd` 的 `set /p` 会截断到 ~1024 字符 → 用 PowerShell
  `$env:CLASSPATH = 'classes;' + (Get-Content cp.txt -Raw)`，或 `tmp_output/cp_one.txt` + `-cp $cp`。
- PowerShell 读文件回写时必须显式 `-Encoding utf8`（否则中文乱码/被安全策略拦截）。
- 控制台显示中文乱码时，用 `-Encoding utf8` 读或直接看文件（文件本身是 UTF-8）。
