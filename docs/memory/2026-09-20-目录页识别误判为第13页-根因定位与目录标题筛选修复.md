# 2026-09-20 — catalog_page_range_start 误判为第 13 页（应为第 2 页）：根因定位与"目录标题"筛选修复

但解析结果里 `catalog_page_range_start/end` 是 **13/13**，`catalog_bookmarks` 里塞了 12 条
形如 `九月 0.218 0` 的"目录条目"。

   即"**任意标题 + 空白/点串 + 行尾 1~5 位数字**"就算一条目录条目，标题部分不受任何约束

2. **页级** `JsonPageTocInfo.isTocPage()`（2121 行）：`命中数 ≥ catalogBookmarkMinTocLines(=3)`
   且 `命中数 / 该页文本行数 ≥ catalogBookmarkMinTocRatio(=0.4)`。
3. **区间级** `detectJsonRanges`（1299 行）+ `selectBestJsonRange`，
   评分 `JsonPageRange.score()`（2153 行）`= totalTocLines * (1 + ln(1 + pageCount))` —— **纯比命中条数**。

## 根因

一句话：**目录页判定只看"行尾是不是数字"，不看这行是不是目录条目；区间择优只看命中条数。**

拆成三层，缺一层都不会误判：

1. **行级过松**：`ARABIC_TOC_PATTERN` 允许"任意标题 + 纯空白分隔 + 行尾数字"，
   于是表格里的 `九月  0.218 0.115` 这类数据行全部算目录条目（表内小数提供了"点"，
   所以"必须有点引导"这类想法也拦不住）；
2. **页级只看比例**：股价表页 12/28=0.4286 刚好越过 0.4，且这类页的"数字行"天然比真目录页多；
3. **区间级只比条数**：`totalTocLines` 直接决定胜负，12 > 6，真目录被顶掉。

同理，真目录页第 2 页之所以"看起来弱"，是因为它只有 6 条条目（8 行文本里的 6 行）。

## 修复实施

文件：`java/opendataloader-pdf-core/src/main/java/org/opendataloader/pdf/processors/CatalogBookmarkProcessor.java`

### 1. 新增"目录标题"判据

```java
// 139 行
private static final Pattern CATALOG_HEADING_PATTERN = Pattern.compile("目\\s*[录錄]");
```

用 `find` 而不是 `matches`（用户要求"内容包含"），`\s*` 允许两字之间出现空格
（实测语料里存在 `目  錄`、`目   录`、`目 录`、`目录`、`目錄` 五种写法）。

### 2. 每个页面记录"标题行"与"首个目录条目"的位置

`PageTocInfo`（内容路径）与 `JsonPageTocInfo`（JSON 路径）各加两个字段：

```java
double firstTocTopY = Double.NEGATIVE_INFINITY;  // 该页最靠上的目录条目
double headingTopY  = Double.NEGATIVE_INFINITY;  // 该页最靠上的"目录/目錄"标题行

boolean hasCatalogHeadingAboveFirstToc() {       // 2029 / 2133 行
    return headingTopY > firstTocTopY;
}
```

位置约定：JSON 路径用 `-y0`（`getJsonItemLines` 里已经这么转），内容路径用 verapdf
`TextLine.getTopY()`，**两者都是"越大越靠上"**，因此 `headingTopY > firstTocTopY` 就是
"标题在第一个目录条目之上"。两个默认值都是 `-infinity`，没有标题的页永远不成立。

采集点：`analyzePages`（499 行）与 `analyzeJsonPages`（1236 行）。

### 3. "单行段落"的判定（JSON 路径）

```java
// 1260 行
private static boolean isSingleLineJsonItem(Map<String, Object> item) {
    Object contentObj = item.get(JsonName.CONTENT);
    return contentObj instanceof List && ((List<?>) contentObj).size() == 1;
}
```

用**原始 content 数组长度**（空行也计入）而不是 `getJsonItemLines` 的结果（它会丢掉空行）。
这样"埋在 11 行段落里的 `目錄`"不算标题（正是 `20260507AN…` 那种情况）。

内容路径没有"段落"概念（`contents` 里每个 `IObject` 就是一行 `TextLine`），
故该路径只做位置判断，代码里已注释说明。

### 4. 只在"区间起始页"要求标题（关键的取舍）

`detectRanges`（617 行）与 `detectJsonRanges`（1299 行）改成：

```java
for (info : pageInfos) {
    if (!info.isTocPage()) continue;
    if (current != null && info.pageIndex == current.endPage + 1) {  // 续页直接延伸
        current.endPage = info.pageIndex;
        current.totalTocLines += ...;
        continue;
    }
    if (current != null) { ranges.add(current); current = null; }     // 断开先结算
    if (info.hasCatalogHeadingAboveFirstToc()) {                      // 只有带标题的页能开新区间
        current = new PageRange(info.pageIndex, ...);
    }
}
```

**为什么不能要求每一页都有标题**：目录只在第一页印标题。若逐页要求，
`202302281677505819604328` 的区间会从 `12-15` 被截断成 `12`（只剩 26/103 条条目）。
现在的语义是"不满足条件的页不能**新建**区间，但可以**延伸**已有区间"。

### 5. 两条路径同步

`extractCatalogBookmarksFromJson`（JSON，生产在用）与 `extractCatalogBookmarks`（内容路径，
目前只有 `BookmarkUtils.getCatalogBookmarks` 可达、无 main 调用方）是同一套逻辑的两份拷贝，
本次两处都改了，避免将来启用内容路径时行为不一致。

## 附带发现与遗留

1. **`20260507AN202606291826520711` 会丢目录**（`8-9 → none`）：该页（第 8 页）的形态是
   一个 11 行段落，第 1 行 `預期時間表…i`、第 2 行 `目錄…iv` —— `目錄` 自己就是一条目录条目，
   既不是"单行段落"，也不在首个条目之上，两条判据都不过。放宽方向（尚未实施）：
   ①只要求"存在含'目录'的独立一行"；②只要求"该页出现含'目录'的行"。
   实测**必须两条同时放宽**才能救回该文档，而现行 4 个误判页一个都不含"目录"，所以放宽到
   "页面含'目录'即可"仍能拦住全部误判，只是拦截强度下降。
2. **罗马数字目录条目不参与正文页码解析**：`parseOriginalPageNum` 对非纯数字返回 0，
   `resolveCatalogBookmarkTarget` 见 `catalogHint <= 0` 直接 return，所以 `責任聲明 .... ii`
   永远停在 `page_num=1`（正文实际在第 3 页）。本次未动。→ 次日由"相似性兜底匹配"任务部分暴露/处理。
3. `minTocRatio = 0.4` 对"数据行页"没有防护作用（0.4286 就能过线），本次没有调它。
4. 内容路径 `extractCatalogBookmarks` 无调用方，改动只有编译与逻辑对称保证，无单测覆盖。
5. 未加 `Config` 开关：标题筛选是硬编码常量，要放宽/关闭需改
   `CATALOG_HEADING_PATTERN` 或 `hasCatalogHeadingAboveFirstToc()`。
