# 2026-09-22 柱状图截图吞并上方正文、截图下方又重复正文 —— 根因定位（未改代码）

样本：`docs/pdf/20260507AN202606291826520711.pdf`（423 页，香港招股书）第 111 页
（本文中"第 N 页"= JSON 的 `page_index`（1-based）= 流程图日志里的 `Page N`）。

## 1. 现象（用户报障 + 复现）

第 111 页是"全球光電互連市場規模"一节：正文 3 段 + 柱状图（标题"全球光電互連銷售額（按產品類型拆分），2021年至2030年（估計）"）+ 图表下方数据表 + 首尾各一行"資料來源：弗若斯特沙利文"。

解析结果（`tmp_output/20260507AN202606291826520711.json`，`page_index=111`）：

| id | 类型 | bbox（y 自上而下） | 内容 |
|---|---|---|---|
| 3 | image | y[69.87, 588.20] x[64.59, 515.38] | **一张几乎覆盖整页正文区的截图** |
| 4 | text | y[125.81, 229.64] | 正文第 1 段（8 行） |
| 5 | text | y[242.81, 281.64] | 正文第 2 段 |
| 6 | text | y[294.81, 333.70] | 正文第 3 段 |

两个症状：
1. 截图上边界 69.87 ≈ 正文区顶部，把 3 段正文、节标题"全球光電互連市場規模"、首行"資料來源"全部截了进去（用户期望最多截到图表标题 y≈348）；
2. 被截进去的 3 段正文**同时**留在文本层（id 4~6），在 Markdown/JSON 里排在图片之后 → 视觉上"图片下方又重复了一遍正文"。

## 2. 定位过程

### 2.1 谁生成了这张截图

`DocumentProcessor` 的 chart/formula 并行循环依次调用
`BarChartProcessor` → `PieChartProcessor` → `FlowchartProcessor` → `ConsecutiveImageProcessor`。
`FlowchartProcessor` 是唯一会打印 bbox 的：

```
Page 111: detected flowchart cluster with screenshot bbox [64.5906568, 205.5008, 515.3775, 723.8347]
```

该 bbox 为 `(leftX, bottomY, rightX, topY)`（PDF 下起算），换算成 JSON 的 y（= 793.701 - y）正好是
`x[64.59, 515.38] y[69.87, 588.20]` —— **就是这张截图**，即元凶是"流程图"分支，不是 `BarChartProcessor`。

### 2.2 该页图形为什么没被 `BarChartProcessor` 收走

`ShapeRecognizer` 日志（Page 111 wanted 16 个 shape：15 个 `rectangle` + 1 个 `polyline`，**没有 `bar_chart`**）。
原因是该柱状图是**堆叠柱**：

- `detectBarGroups()` 按"基线"（`min(bottomY, topY)` 取整到 2pt）分桶 → 同一系列（同色）的柱段各年基线不同 → 桶里只剩 1~2 根 < `MIN_BAR_COUNT`(3)；
- 即便组出来了，`guessFilledShapeType` 的竖柱分支要求"同左右边 **且高度相近**"，`isValidBarGroup` 还要求
  `hasBarGaps`（**注释里明确写了要排除 stacked/adjacent 矩形**）→ 堆叠柱在设计上就不会被判为 `bar_chart`。

于是该页柱状图没有任何"图表"身份，只能落到 `FlowchartProcessor` 手里。

### 2.3 流程图簇为什么会长到整页

用同包探针 `tmp_debug/probe_src/.../FlowDbg.java` 复现（重放到 chart/flowchart 之前的 contents，dump 前后清单），
得到该页 chart 阶段的完整清单（57 项），关键两项：

```
[  4] LineArtChunk  x[  70.87, 127.56] y[  70.87, 572.35] w= 56.69 h=501.48  children=0
[ 49] ShapeChunk[polyline] x[84.90, 510.38] y[493.95, 561.51]
[ 50] TableBorder           x[84.90, 510.38] y[493.95, 561.51]
```

- 图形分组共 9 组：组 0~7 是柱段（1~2 个矩形），**组 8 = 轴线 polyline + 4 个图例色块**（5 个 shape）；
- 组 8 的 bbox（= 表格区域 y[493.95, 561.51]）与 `[4]` 这个**几乎贯穿整页、宽 56.69pt 的线稿 chunk** 相交 →
  `collectOverlappingContents()` 把它当成"图形内容"收了进来 → 簇 bbox 瞬间被拉到 y[70.87, 572.35]；
- 框变大后，`dropBodyTextBlocks()` / `containsBodyText()` 的"正文否决"全部失效
  （3 段正文是被**跳过收集**的，从不进 `collectedContents`，守卫看不到它们）；
- `isRegularTable()` 的"整块就是表格 > 0.3 否决"也失效：表格只占新 bbox 的 13%；
- 最后 `absorbInteriorText()` 把**完全落在框内**的文本全部收回：节标题、图表标题、单位、所有刻度/图例文字、
  首尾两行"資料來源" → 全部从文本层删除（用户看到"正文没了/只剩图"）；
- 3 段正文 x 到 524.46 > 框右边界 510.38 → `contains(box, 1, 1)` 不成立 → **不被收回**，
  但仍落在截图矩形内 → 于是"图里一份、文本层一份"→ 重复。

bbox 四条边都能对上：
- 上 = `[4]` 的 top（70.87）、下 = 末行"資料來源"的 bottom（587.20）、
- 左 = "資料來源"的 leftX（69.59）、右 = `polyline` 的 rightX（510.38）。

### 2.4 触发点：一个"差 2.8pt"逃过背景过滤的装饰线稿

`ContentFilterProcessor.processBackgrounds()` 用 `isBackground()` 过滤页面级背景：

```java
width  > 0.5*pageWidth && height > 0.1*pageHeight   // (1)
|| width > 0.1*pageWidth && height > 0.5*pageHeight // (2)
```

`[4]` 实测 w=56.69（页面宽 595.28 的 **9.5%**）h=501.48（页面高 793.70 的 63.2%）：
**第 (2) 条只差 2.84pt（阈值 59.53）没通过** → 没被当背景删掉，留在 contents 里等着被流程图簇收走。
（该页日志确实有 `Detected background on page 111`，说明别的线稿被删了，唯独这个漏网。）

另外实测该线稿**渲染后不可见**：截图对应区域像素 87% 纯白 255，无任何可见线条 → 纯装饰/不可见路径。

### 2.5 因果验证（实验）

在前述探针里加开关：调用 `FlowchartProcessor` 之前删掉"高度 ≥ 400pt 的叶子 LineArtChunk"（只有 `[4]` 命中）：

- 结果：**该页完全不再裁剪**（无 REMOVED、无 ImageChunk），
  表格 `TableBorder`、3 段正文、节标题、首尾"資料來源"全部保留；
- 说明 `[4]` 是唯一触发器：没有它，组 8 的簇只剩表格区域 → 表格占簇面积 ≈ 100% → `isRegularTable()` 直接否决，不会裁剪。

### 2.6 影响面

`TallLineArtScan`（同包探针，逐页只跑到 Loop 1）扫描全文 423 页：

```
page 111: leaf line-art x[70.87,127.56] yTopDown[70.87,572.35] w=56.69(0.095) h=501.48(0.632)
SUMMARY pages=423 pagesWithTallLeafLineArt=1 totalTall=1
```

→ 该文档只有第 111 页存在这种"逃过背景过滤的高瘦线稿"。（其他文档是否有同类，需另跑语料。）

## 3. 根因结论

1. **直接触发器**：第 111 页左侧一条 `56.69 × 501.48pt` 的不可见装饰线稿，因宽度差 2.84pt 未通过
   `ContentFilterProcessor.isBackground()` 的"页高窄条"判据，残留在页面内容里；
2. **放大器**：`FlowchartProcessor.collectOverlappingContents()` 把这种与图形组相交的**非文本、非图形**大对象
   一并吞入，簇 bbox 从表格大小（67.56pt 高）膨胀到 518pt 高；
3. **守卫失灵**：框一变大使 `isRegularTable()`（表格占比）与 `containsBodyText()`（正文否决）同时失效；
   `absorbInteriorText()` 再把框内所有文本（节标题、图表标题、首尾"資料來源"）收回并删除；
4. **重复的直接原因（与本页触发器相互独立）**：正文段落因**超出截图右边界**不满足"完全包含"判据，
   既不收回、也不排除 → 被截图覆盖的同时留在文本层 → 输出里出现两遍。
5. 背景：该图是**堆叠柱状图**，当前 `ShapeRecognizer` 设计上不把堆叠柱判为 `bar_chart`（`hasBarGaps` 明确排除），
   所以它永远不会被 `BarChartProcessor` 正常截图（相邻第 110/112 页的普通柱图/Tab 图都能正常处理）。

## 4. 修复方案（待用户选择，尚未实施）

| 方案 | 位置 | 效果（第 111 页） | 主要风险 |
|---|---|---|---|
| A 收紧背景过滤 | `ContentFilterProcessor.isBackground()` 增加"页高窄条"判据（如 `w > 0.05*pageWidth && h > 0.5*pageHeight`） | 已用实验验证：不再裁剪，表格/正文全部保留 | 全文档生效；其他文档可能删掉"细长的合法图形"（需语料回归） |
| B 限制簇生长范围 | `FlowchartProcessor.collectOverlappingContents()` 只收"基本落在图形簇附近"的对象（按距离/重叠比） | 同上（簇保持表格大小 → 被表格否决） | 影响所有流程图裁剪；需语料回归 |
| C 截图覆盖不变式 | `FlowchartProcessor` 裁剪前检查：截图框是否半覆盖"会留在文本层"的内容；有则①放弃裁剪 或 ②把框缩到不含这些内容（并把框外的已收集项放回文本层） | ①同 A；②裁剪范围缩到 y[333.70, 587.20]（含图表标题+图+表），首行"資料來源"与节标题回到文本层 | 需与现有 `containsBodyText` 语义对齐，语料回归 |
| D 支持堆叠柱识别 | `ShapeRecognizer` 新增"同宽、上下相接的柱段列 = 堆叠柱状图"判据 | 由 `BarChartProcessor` 正常截图（期望接近 110/112 页效果） | 与现有 `hasBarGaps` 设计冲突，改动最大；且残留的"轴线+图例"组仍会走流程图分支，需配合 A/B/C |

倾向：**A（或 B）解决触发器 + C 解决"重复"这一类不变式**；D 作为独立图表覆盖任务另排。
