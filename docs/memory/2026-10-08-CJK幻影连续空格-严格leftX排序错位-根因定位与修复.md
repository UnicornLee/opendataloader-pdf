## 1. 现象

用户报告第 2 页这一段中间**不该有连续空格**：

```
如於[編纂]上午八時正前出現若干事件，[編纂（為其本身及代表]         [編纂]）可終止[編纂]於[編纂]項下的責任。…
                                       ↑ 这里 9 个空格，且 ] 的位置也不对
```

肉眼可见的两处异常：

1. `]` 出现在 `（為其本身及代表` **之后**，正确应为 `[編纂]（為其本身及代表[編纂]）`；
2. `]` 与下一个 `[編纂]` 之间有 **9 个连续空格**。

原文 PDF 里这两处**都没有任何空白**——空格是解析器自己造出来的，故称"幻影空格"。

同类错位在全文共 **17 处**（按括号内容分五种变体：`（為其本身及代表`、`（或`、`（未計及`、`（「`、`（以較晚者為準）`）：

| `data[65]` items3 | 第 66 页 | 1 |

## 2. 结论速览（TL;DR）

1. **根因只有一个：`TextLineProcessor` 用严格 `boundingBox.leftX` 给行内 chunk 排序。**
   全角 CJK 字形（`（`）的 em box 起点在墨迹**左侧**（left side bearing），其 leftX 恒比紧邻其左、
   在内容流中**先绘制**的 `]` 偏左 **0.273pt**，于是 `]` 被排到整个 CJK 串之后。
2. **9 个空格是缺陷 1 的派生后果，不是独立缺陷。**
   行合成 `getTextLineWithSpaces` 与 `JsonWriter.getText` 都是拿"**前一个** chunk 的右端"量间隙。
   被挤到后面的 `]`（右端 212.78）与下一个 `[編纂]`（左端 266.57）之间算出 **53.79pt 幻影间隙**，
   远超插空阈值 `fontSize × TEXT_LINE_SPACE_RATIO = 6.5 × 0.17 = 1.105`，于是插入合成空格 chunk，
   最后 `getSpaceStr` 按 `ceil(53.79 / 6.5) = 9` 吐出 9 个空格。
3. **只修排序即可，间隙侧不需要任何兜底。** 排序正确后 `] → （` 的间隙变成 **−2.435pt**，
   `width / fontSize < 0.4` → `getSpaceStr` 返回空串，幻影空格自然消失。
4. **量化分桶（`Math.round(leftX / step)`）不可用**：它不能保证"|a−b| < step 就一定同桶"。
   只有 leftX 恰好落进同一桶的行被修好，跨桶的行（`132.590/0.52=254.98→255` vs
   `132.863/0.52=255.51→256`）照旧出错，而修没修好取决于绝对坐标落在桶的哪一侧。
   必须**先按 leftX 排序、再与"簇首值"比较**做聚类。
5. **不能改用比较器写"死区"（差值小于容差即返回 0）**：那违反传递性，
   `List.sort`（TimSort）可能抛 `Comparison method violates its general contract`。
   正确做法是生成**单调 key** `clusterId × count + streamIndex`。
6. **间隙测距侧的“顺手加固”全部被证伪并回退**（详见第 6 节）：`JsonWriter` 的 `coveredRightX`（B1/B2）与
   `getTextLineWithSpaces` 的 `coveredEnd`（B3）会把第 93/94 页前投資表格的**真实列间隙吞掉**，
   造成 `869,565  10,000,000` 粘成 `869,56510,000,000`。最终只保留**排序**修复，
   `getTextLineWithSpaces` 至今保持原版 `previousEnd` 测距。
7. **同一个根因在 `JsonWriter` 的表格单元格路径上还有一份**（阶段二）：
   `groupChunksByLine` 之前先对扁平化后的 chunk **逐个按 topY 预排序**、行内再**严格按 leftX 排序**，
   同样是“窄括号被全角 CJK 抢位”的形态。现已与段落路径共用 `ReadingOrderSortUtils`。

## 3. 完整定位过程（从问题到根因）

### 3.1 先把"空格从哪来"的候选路径列全

解析链路：PDFBox 内容流 → `TextChunk`（**流顺序**）→
`TextLineProcessor.processTextLines`（行分组 → **行内排序** → 插合成空格 chunk）→
`ParagraphProcessor` → `JsonWriter.getText` / `assembleGroupText`（`getSpaceStr` 决定空格个数）。

会产出空白的只有三处：`TextLineProcessor.getTextLineWithSpaces`、`JsonWriter.getText`、
`JsonWriter.assembleGroupText`。三处都用 `chunk.getLeftX() - prevChunk.getRightX()` 这类
"**与前一个 chunk 右端**"的距离当间隙，所以第一嫌疑不是"间隙算错"，而是"**前一个 chunk 是谁**"错了。

### 3.2 用 DebugSample 复现并确认排序错位

按用户指示改 `DebugSample` 的启用行指向目标 PDF，classpath 用
`mvn -o dependency:build-classpath` 导出后直接 `java -cp target\classes;<cp> org.opendataloader.pdf.DebugSample`
（约 3 分钟），拿到基线 JSON 备份为 `tmp_output/_before_fix.json`。

读 `TextLineProcessor`：

```java
// 原代码
private static final Comparator<TextChunk> TEXT_CHUNK_COMPARATOR =
    Comparator.comparingDouble(o -> o.getBoundingBox().getLeftX());
...
textLine.getTextChunks().sort(TEXT_CHUNK_COMPARATOR);   // 两处调用点
```

排序键是 **boundingBox.leftX 的严格全序**，与内容流顺序无关，且**没有任何 tie 容差**。
这就是缺陷 1 的位置。

### 3.3 几何取证：pdfplumber 看不见，改用 pdfminer 抓内容流

**弯路 1**：先用 `pdfplumber` 取字符坐标，结果 `[` `]` `編纂` **一个都提不出来**
（`HGARCP+TimesLTStd-Bold`、`DRLNDX+MSungHK-Bold` 的 ToUnicode 未被 pdfminer 解码）。
→ 说明"用高层库比对文本再定位坐标"这条路在本样本上不通。

**弯路 2**：`_probe_stream2.py` 想按中文子串过滤内容流算子，失败——
自定义 PDFDevice 拿到的解码结果是**原始字节 repr**，不是中文。
→ 改用 CID 十六进制过滤：`0789` = `為`、`5b`/`5d` = `[`/`]`，成功导出
`tmp_output/_stream_all.txt`（339 个绘制算子，按 y 分组）。

关键证据（第 2 页 y=249.14，即 `items[18]`）：

```
op 283 x=194.804  HGARCP+TimesLTStd-Bold   BRACKET-[ 5b
op 284 x=194.804  DRLNDX+MSungHK-Bold      CJKBOLD 11dc1632        ← 編纂
op 285 x=210.618  HGARCP+TimesLTStd-Bold   BRACKET-] 5d            ← ]
op 286 x=210.345  PMJXPZ+MSungHK-Light     CJK 0080|<50>|0789…      ← （為其本身及代表
op 287 x=266.570  HGARCP+TimesLTStd-Bold   BRACKET-[ 5b            ← 下一个 [編纂]
```

**`]` 先绘制（210.618），`（` 后绘制但 leftX 更小（210.345），差 0.273pt。**
逐行核对全文同类行，偏差**恒为 0.273pt**（同一对字体的固定 left side bearing）：

| 行 (y) | 所属段落 | `]` leftX | `（` leftX | Δ |
|---|---|---|---|---|
| 249.14 | 第2页 items[18] | 210.618 | 210.345 | 0.273 |
| 294.13 | 第2页 items[17] | 86.817 | 86.544 | 0.273 |
| 321.13 | 第2页 items[16]② | 233.945 | 233.672 | 0.273 |
| 348.14 | 第2页 items[16]① | 132.863 | 132.590 | 0.273 |
| 348.14 | 第2页 items[16]③ | 354.422 | 354.149 | 0.273 |

对照：**当下一个 chunk 不与 `]` 抢 leftX 时（y=213.15 的 86.735 vs 86.735）根本不产生问题**——
这解释了为什么全文只有这一类段落出错。

### 3.4 把"排序错位"和"9 个空格"接上（阈值数学）

错位后行内顺序为 `…[編纂（為其本身及代表` → `]` → `[編纂]…`，于是：

```
间隙 = [編纂] 的 leftX 266.570 − ] 的 rightX 212.78 = 53.79 pt
插空阈值 = fontSize 6.5 × TextChunkUtils.TEXT_LINE_SPACE_RATIO 0.17 = 1.105 pt   → 插入合成空格 chunk
空格个数 = ceil(53.79 / 6.5) = ceil(8.275) = 9                                    → 正好 9 个空格
```

（`JsonWriter.getSpaceStr(double width, double fontSize)`：`ratio<0.4` 空串、`<1` 一个空格、
否则 `repeat(ceil(ratio))`。）

两个异常由同一个根解释完毕，与"PDF 里有没有空白"无关。

### 3.5 方案演进：量化分桶 → 聚类

**第一版（已废弃）：量化 key `Math.round(leftX / step)`，step = max(0.5, 0.08×fontSize)。**
跑完全文只有 leftX 恰好落进同一个桶的少数行被修正，跨桶的行照旧出错：

```
210.618 / 0.52 = 405.03 → 405
210.345 / 0.52 = 404.51 → 405      ← 同桶，这一行修好了

132.863 / 0.52 = 255.51 → 256
132.590 / 0.52 = 254.98 → 255      ← 差值 0.273 < 容差 0.52，却跨了桶，这一行没修好
```

**第二版（最终）：leftX 聚类 + 簇内保持流顺序。**
先把 leftX 升序走一遍，与"**当前簇的簇首 leftX**"相差 ≤ 容差就并簇；
再给每个 chunk 生成单调 long key `clusterId × count + streamIndex` 排序。
数学上保证：同一簇内按流顺序、簇之间按 leftX 从左到右，且比较器是合法全序。

落地后**全文 17 处同类段落全部修正**，且**全文 31005 个字符串条目零增删**。

### 3.6 反向验证：新单测真的能抓到老 bug

光看"新代码通过"不足以证明测试有效。做法：临时在 `sortChunksByReadingOrder` 开头插回
旧的严格 leftX 排序并 `return`，单跑该测试类：

```
expected: <]（為其本身及代表[編纂]）>
but was:  <（為其本身及代表] [編纂]）>      ← ] 被挤到 CJK 之后 + 幻影空格，缺陷原形
```

确认有效后删除临时代码，并核对 `git diff --stat` 回到 `TextLineProcessor.java 80 ++++--`（即 +76/−4）
原样（`Select-String 'TEMP-BASELINE'` 无匹配）。

测试用真实几何构造：字号 6.5（阈值 1.105），三个 chunk 按流顺序入列
`]`（210.618–212.78）、`（為其本身及代表`（**210.345**–266.0）、`[編纂]）`（266.57–290.0）。

### 3.7 阶段二：抽为共享工具，推广到表格单元格路径

阶段一只修了段落路径，复盘时发现同一个缺陷在 `JsonWriter` 的**表格单元格**路径上独立存在一份：

```java
// 旧代码（已删）
cellItemContents.sort(Comparator.comparingDouble(IObject::getTopY).reversed());  // 逐 chunk 预排 topY
...
private static void flushGroupSortedByLeftX(List<IObject> group, List<List<IObject>> sink) {
    group.sort(Comparator.comparingDouble(IObject::getLeftX));                   // 行内严格 leftX
}
```

逐 chunk 预排 topY 尤其危险：同一视觉行上字高不同的字形（窄 `)` 与全角 CJK 串）topY 不相等，
预排会把它们拆到不同行组，后面的行内 leftX 排序再错位一次——**同一个缺陷的两个副本在相邻两行代码里**。

重构要点：

| 动作 | 说明 |
|---|---|
| 新增 `ReadingOrderSortUtils.sortByReadingOrder(List<T>, ToDoubleFunction<T> leftXGetter, double fontSize)` | 算法逐字搬过来，泛型化以便两个调用方共用；常量改名 `X_TIE_MIN`(0.5) / `X_TIE_FACTOR`(0.08) |
| `TextLineProcessor.sortChunksByReadingOrder` 改为薄包装 | 保留方法名与两处调用点，只转发给共享工具，传 `chunk.getBoundingBox().getLeftX()` |
| `JsonWriter` 删除逐 chunk topY 预排序 | 改为对**整个行组**按 `getGroupMaxTopY` 降序排（重排行而非重排 chunk），行内流顺序不被破坏 |
| `flushGroupSortedByLeftX` → `flushGroupInReadingOrder` | 行内改用共享工具；字号取行组内 `TextChunk` 的**最大字号**（`getGroupFontSize`） |

**为何两处必须共用一份实现**：段落与表格单元格是把同一批 chunk 两条路径重组为文本，
若一侧聚类、另一侧严格排序，JSON 里的单元格文本就会与处理器生成的段落文本不一致。

新增单测 `JsonWriterTableCellGroupingTest.narrowBracketIsKeptBeforeWideCjkRunOnTheSameVisualLine`
（与段落路径的反向验证同一几何），该测试类从 1 个用例变为 2 个。

⚠️ **阶段二尚未重跑全文 PDF**（第 7.1 节的所有数字均为阶段一口径），见第 9 节遗留项。

## 4. 根因

| 层 | 事实 | 定性 |
|---|---|---|
| 排序键 | `Comparator.comparingDouble(o -> o.getBoundingBox().getLeftX())`，无容差、与流顺序无关 | **代码缺陷（几何排序假设过强）** |
| 触发条件 | 全角 CJK em box 起点在墨迹左侧，leftX 比相邻先绘制的窄字形偏左 0.273pt（固定值，随字号线性变化） | **PDF 字体度量特性** |
| 空格放大 | 间隙测距只看"前一个 chunk 右端"，chunk 顺序一错就量出跨整个 CJK 串的距离 | **派生后果**（非独立缺陷） |
| 首次方案失败 | `Math.round(x/step)` 分桶不保证"|a−b|<step ⇒ 同桶" | **算法选型错误** |

## 6. 走过的弯路：三处"顺手加固"全部回退

| 尝试 | 目的 | 结果 | 教训 |
|---|---|---|---|
| `JsonWriter.getText` / `assembleGroupText` 引入 `coveredRightX`（B1/B2） | 让间隙测距跳过"已被前面 chunk 覆盖"的右端 | 幻影空格确实减少，但第 93/94/152 页表格的**真实列间隙被吞**：`869,565  10,000,000` → `869,56510,000,000`；另有一处 13 空格塌成 3 空格 | 修 A 类缺陷时**不要顺手改 B 的测距**；间隙"看起来多余"不等于"是幻影"，表格列间隙是合法的 |
| `getTextLineWithSpaces` 的 `coveredEnd`（B3） | 同上，在行合成阶段兜底 | 回退 B1/B2 后第 93/94 页**仍粘连**，定位到 B3 才是实际元凶 | 兜底散落在多层时，回归要**逐层剥离**才能归因准 |
| 量化分桶排序 | 用最小改动实现"近似同列视为同序" | 只有同桶的行被修正，修没修好取决于绝对位置落在哪个桶，**不稳定** | 分桶适用于"归类"，不适用于"判定两个值是否该视为相等" |

结论：**根因单点修复 > 多层兜底**。排序修对之后，所有兜底都是纯风险。

## 8. 经验教训

1. **"间隙算错"先怀疑"前一个是谁"。**
   三处空格来源都按 `当前.leftX − 前一个.rightX` 量距，这类公式对**顺序**极其敏感。
   看到"两个本来相邻的 chunk 之间冒出巨大间隙"，第一反应应该是顺序被重排过，而不是测距写错。

2. **按几何坐标排序必须带容差，且要清楚"排序键要表达什么语义"。**
   这里要的是"**视觉上属于同一列/紧邻关系**"，而 `leftX` 是 em box 左沿，
   不等于墨迹左沿。CJK 全角字形的 left side bearing 会让 em 起点系统性偏左，
   所以"紧邻"必须靠容差 + **流顺序**（PDF 绘制顺序本身就是视觉顺序的强先验）来定。

3. **量化分桶 ≠ 容差比较。**
   `round(a/s) == round(b/s)` 在 a、b 落在桶边界两侧时为假。要做"容差归组"只能
   **排序后与簇内参考值（簇首）逐项比较**，别无捷径。

4. **绝不能用"死区比较器"。**
   `if |a-b| < eps return 0` 不满足传递性，TimSort 可能抛
   `Comparison method violates its general contract`。要引入容差就把容差**前置成聚类**，
   最终比较仍是单调 key。

5. **同一轮改动引入多处"相关优化"会毁掉归因能力。**
   本轮 B1/B2/B3 三处兜底叠加时，表格粘连无法判断是谁造成；
   回退 B1/B2 后仍粘连才锁定 B3。**先只修根因、跑全文回归，再决定要不要兜底**，
   顺序反了就要全部推倒。

6. **全文级回归要盯"零增删 + 分类指标"，不能只看目标段落。**
   目标段修好、而 `869,56510,000,000` 这类粘连在别页出现，只比对第 2 页完全发现不了。
   有效手段：条目总数守恒 + "space-only 变化数" + 按缺陷形态定制的正则指标（破碎括号、粘连数字）。

7. **本样本高层库不可靠时，回到内容流取证。**
   pdfplumber/pdfminer 的文本提取漏掉 `[編纂]`，但 `Tj/TJ` 算子的**绘制 x** 是真实可信的。
   按 CID 十六进制（而非解码后的中文）过滤算子，是定位 ToUnicode 不完整字体的可靠手法。

8. **新单测要做反向验证。**
   把实现换回旧行为、确认测试失败并打印出缺陷原形，才能证明它真的守住了这个 bug，
   而不是恰好被新实现满足。

9. **修完一处根因，要横向搜索"同一假设有几份副本"。**
   本轮只修了段落路径，而 `JsonWriter` 里独立存在同构的严格排序代码
   （`Comparator.comparingDouble(IObject::getLeftX)` 与逐 chunk `getTopY` 预排序）。
   有效做法：修完全文回归后，`grep` 一次全仓的
   `comparingDouble(.*get(LeftX|TopY)` 类调用点，逐个判定是否同样需要容差，
   而不是等下一个样本把它们再暴露出来。收敛为单一共享工具（`ReadingOrderSortUtils`）
   是防止副本重新长出来的正确做法。

## 9. 遗留

1. **第 93/94 页前投資表格残留差异**：`[  ]%編纂` 这类，根因是**多行表格被压成单一 TextLine**
   造成的列交错（与本次是不同缺陷，本次反而改善了其中的 `[  ]編纂 前投資` → `[編纂]前投資`）。
   需单独立项，方向在 `TextLineProcessor` 的行切分/表格列归属。
2. **容差 0.5pt / 0.08×字号是样本驱动的经验值**：0.273pt 偏差 << 0.5pt 下限，安全余量充足；
   但尚未在跨字号语料（极小字号脚注、大字号标题）上扫过，若出现新的紧邻字形对偏差 > 0.5pt 需上调。

   风险极低，但属已知权衡。
